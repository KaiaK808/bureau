# Bureau drift inventory — 2026-09-25

## Summary

The two installations are siblings forked from the same pre-v2 template generation and have never been resynced: all three trees share exactly the incident set EXP-123…EXP-671, and the two local sets (slidefactory EXP-799…1478, msc EXP-1281…1379) do not overlap in a single tag — no hardening was ever invented twice. Only one of 23 shared scripts is byte-identical across all three (`setup-merge-drivers.sh`); `bureau-config.sh` alone differs by 815 non-comment lines template↔slidefactory. The template has since moved a whole generation ahead structurally — 14 files implementing a `leases.json` ownership runtime that neither installation contains — while both installations moved ahead operationally on hardenings the template never received. The single most consequential difference is one line: `[ "$BUILD_OK" = false ] && VERDICT="REQUEST_CHANGES"` is still live and byte-identical at `template/code-review-pipeline.sh:400` and `slidefactory/code-review-pipeline.sh:380`, and it is unconditional — so a merely broken build environment silently downgrades a BLOCK carrying `security_issues: 1` into routine rework, skipping `needs-human` entirely. msc fixed it (`apply_build_failure`) after logging it as a CRITICAL with "stiller Datenverlust"; two of three trees still ship it. A close second: the template amends `[skip ci]` into every iteration commit (`implement-pipeline.sh:513-514`) and squash-merges with no `--body` (`merge-pipeline.sh:366`), so CI never runs on the push to main — both installations guard against this, by two different mechanisms, and the template has neither. Direction is therefore not a single arrow: template ahead on runtime and on four quietly-lost capabilities, slidefactory ahead on Linear reliability and input safety, msc ahead on review-verdict integrity — and the merge is harder than it looks, because the two installations have assigned incompatible meanings to exit code 20.

## The four known fixes

### 1. CI-skip-marker guard — CORRECTED: two different fixes, in two different trees, neither complete

The brief treats `sanitize_ci_markers` and `squash-marker-check.sh` as one fix. They are two independent answers to the same incident class, and they live in **different** installations.

- **slidefactory — detect and halt.** `scripts/squash-marker-check.sh` (125 lines) reads every commit message in `<base>..HEAD` and reports any line matching `scripts/ci-skip-markers.txt` (7 markers). `check_squash_range()` in `bureau-config.sh` wraps it and distinguishes three outcomes — `clean`, `found` (exit 3), and `unchecked` (any other exit, which also halts: "halting rather than passing it on unchecked"). `implement-pipeline.sh:186` raises a `CI_MARKER` halt state before hand-off; `comment_on_branch_pr()` posts the finding on the PR. slidefactory also **removed the marker injection entirely** — `implement-pipeline.sh` there contains no `[skip ci]` amend at all. Origin: EXP-1462 / EXP-1465, explicitly dated and narrated.
- **msc-planner — neutralise at the merge.** `scripts/merge-body.sh` defines `sanitize_ci_markers()` (defangs all 7 GitHub-honoured forms case-insensitively, idempotently, byte-identical when no marker is present) and `build_merge_body()` (never returns empty → the caller never falls back to GitHub's commit-list default). Sourced by `merge-pipeline.sh:8` and `code-review-pipeline.sh`; used at `merge-pipeline.sh:404` and `code-review-pipeline.sh:479`. Origin: EXP-1318 / B38, with the evidence cited inline ("Beleg 6/6, 29.07.").
- **Template — neither, and it manufactures the hazard.** `implement-pipeline.sh:513-514` amends `[skip ci]` onto every iteration commit; `merge-pipeline.sh:366` runs `gh pr merge "$PR_NUMBER" "--$BUREAU_MERGE_STRATEGY"` with no `--subject`/`--body`. GitHub then composes the squash message from the branch commit list, finds the marker, and creates **no CI run for the push to main**.

**Cost of the gap:** the template as shipped can land unverified code on `main` silently. slidefactory is safe because it neither injects nor tolerates the marker; msc is safe at the merge but still injects at `implement-pipeline.sh:527-528`, so its protection depends entirely on `merge-body.sh` being sourced — and its rebase branch (`merge-pipeline.sh:408`) is explicitly outside the guarantee.

### 2. Worktree dependency restore — confirmed, msc only

`restore_worktree_deps()` at `msc-planner/scripts/bureau-config.sh:1473`. Called at `implement-pipeline.sh:232`, `code-review-pipeline.sh:126`, `qa-pipeline.sh:96`, each as `restore_worktree_deps "$(pwd)" || exit 21`. Absent from template and slidefactory (slidefactory is Python/`pytest`, so `node_modules` does not apply — its absence there is correct, not drift).

Cause: `reset_worktree`'s `git clean -fdx` removes gitignored `node_modules`, and nothing reinstalled it, so every build check ran without dependencies and every APPROVE was downgraded by `apply_build_failure` — four consecutive runs on EXP-1374, review could never complete. The implementation carries four non-obvious hardenings, each annotated as a review finding: `--ignore-scripts` (a PR's lifecycle scripts would otherwise execute pre-review on a machine with `.env` access — marked CRITICAL), atomic install via temp dir + `mv` (a half-populated directory made Turbopack fail with an internal error), `cp -Rc` clone rather than a symlink (Turbopack panics on symlinked `node_modules`), and a SHA-256 stamp of both manifests in `node_modules/.bureau-lock` under `--git-common-dir` (not `$REPO_DIR`, which points at the PR-controlled worktree). Origin: EXP-1375, gated by `worktree-deps.test.sh`.

**Cost of the gap:** template-derived Node installations silently review against a broken build.

### 3. Team-scoped label lookup — CORRECTED: present in BOTH installations, by different methods

- **Template — name-blind, the bug.** `bureau-config.sh:709` and `:743`: `issueLabels(filter: { name: { eq: "$name" } }, first: 1)` then `.nodes[0].id`. With the same label name in two teams, it returns whichever the server lists first — an id that will not attach to the issue.
- **slidefactory — server-side filter.** `bureau-config.sh:846` and `:883` add `or: [ { team: { key: { eq: "$BUREAU_TEAM_KEY" } } }, { team: { null: true } } ]`, still `first: 1`. Correct team, but with both a team label and a workspace label present it takes whichever the server returns first — priority is not expressed. Origin: commit "chore(bureau): scope label lookup to the team, filter in-flight count by project (#98)", 2026-09-04 — deliberate, though not tied to a numbered incident.
- **msc — client-side strict priority.** `_resolve_label_id()` at `bureau-config.sh:594` fetches `first: 20` with `team { key }` and selects in order: the issue team's own label, else a workspace-level (`team == null`) label, else nothing. It further separates **failure from absence** — non-zero transport exit, empty body, a GraphQL `.errors` envelope, a malformed node, or an empty `id` all return rc 2 with empty stdout, so `remove_issue_label` can never acknowledge an idempotent release while the label is still attached. The `.errors` type check is explicitly narrower than a length check because jq answers `length == 0` for `{}`, `""`, `0` and `false`. Origin: EXP-1340, gated by `label-lookup.test.sh` (17 cases, incl. a counter-test T15b that proves the mutation check itself can fail).

**Cost of the gap:** the template cannot reliably attach `needs-human` in a multi-team workspace, and worse, reports success when it did nothing. msc's version is the one to carry upstream; slidefactory's is a partial fix.

### 4. Safe `.env` parsing — confirmed, slidefactory only; the count of 16 is exact

`scripts/bureau-env.sh` exists only in slidefactory. Count verified with
`grep -rlE '(^|[^a-z])(source|\.)[[:space:]]+[^[:space:]]*\.env' <scripts-dir> | wc -l`
→ **template 16, slidefactory 0, msc-planner 16**. The 16 are identical in both trees: `bureau-status.sh`, `code-review-pipeline.sh`, `complete-issue.sh`, `copy-pipeline.sh`, `crosscheck-specs.sh`, `grab-issue.sh`, `implement-pipeline.sh`, `merge-pipeline.sh`, `qa-pipeline.sh`, `queue-loop-supervised.sh`, `queue-loop.sh`, `rebase-pipeline.sh`, `shepherd.sh`, `spec-pipeline.sh`, `spec-review-pipeline.sh`, `ux-pipeline.sh`. slidefactory converted exactly those 16 to `bureau_load_env`.

`bureau_load_env` parses rather than executes, and carries three hardenings beyond the obvious one, each traceable: it disables a running `set -x` before the first expansion and restores it on every return (no secret reaches a trace); it restricts assignment to an allowlist (`bureau_env_key_allowed`); and it accepts values for the six arithmetic-bound keys only as `0` or leading-zero-free digits (`bureau_env_key_numeric`), because bash re-evaluates variable *content* inside `$(( ))`, so `KEY=x[$(cmd)]` would execute `cmd` in the reading script — the last remaining path from a `.env` value to a command. Leading zeros are rejected specifically because bash reads `08` as octal and aborts. Written for bash 3.2 (no `local -`, no `declare -g`). Origin: EXP-1469, extended by EXP-1478.

**Cost of the gap:** in template and msc, a single `KEY= value` line in `.env` executes `value` as a command, and bash echoes it in the "command not found" message — into a log that reaches Linear or GitHub.

## Structural gap: the newer runtime

The template is Bureau **v2.0.0** (tag `v2.0.0`, commit `d7fd2d6`, 2026-09-07). It contains 14 files that exist in **neither** installation:

`bureau-runtime.py` (488) · `bureau-worker.sh` (51) · `bureau-supervision.py` (207) · `bureau-provider.py` (249) · `bureau-doctor.py` (167) · `bureau-monitor.py` (30) · `bureau-tick.sh` (104) · `bureau-app.sh` (22) · `bureau-stage.md` · `bureau-schedule.mjs` · `bureau-schedule-cli.mjs` · `bureau-implement.schema.json` · `bureau-qa.schema.json` · `bureau-review.schema.json`

The ownership model is real and implemented, not merely documented. `bureau-runtime.py` holds a `Store` class whose state is `<git-common-dir>/bureau/leases.json`, guarded by `fcntl.flock(LOCK_EX)` (line 79), with `claim` / `release` / `assert_owner` / `finish_execution` and a `workers/` registration directory keyed by a SHA-256 of the resolved workspace path. App leases deliberately carry no TTL. `bureau-worker.sh` re-execs itself through `bureau-runtime.py … exec` before touching the worktree, so ownership is claimed *before* any `reset`, and its EXIT trap preserves unfinished work rather than resetting over it.

**Neither installation runs this, and neither runs a substitute.** There is no `bureau/` directory in either repo, no `leases.json`, no `flock`, no `O_EXCL`, no lock directory. The only occurrences of the word "lease" in either installation are the English words "release"/"released" in unrelated comments. Both run the pre-v2 shape: `shepherd.sh` and `queue-loop.sh` call `reset_worktree` directly and then `cd "$wt"` + `bash scripts/<pipeline>.sh` — no claim, no registration, no assertion. Concurrency safety rests entirely on `free_branch_from_other_worktrees` and the `max_concurrent_issues` cap.

**What adoption would mean.** Both installations are on config **schema v1** (`.bureau.json` `version: 1`); the v2 runtime reads v2 keys with v1 fallback (`start-bureau-v2.sh` uses `.agents.workbench_runner // .agents.runner // "claude"`), and the skill README states v1 configs remain supported with an optional migration. So adoption is a `/bureau-init --resync-scripts` plus an optional schema migration — not a rewrite. The real cost is that a resync would overwrite the 23 shared scripts and destroy every local hardening listed above unless those are carried upstream first. That ordering is the whole decision.

**Neither installation ever attempted a resync.** Each was scaffolded exactly once and never refreshed: msc at `fd5c7da` "Foundation: Trichter-Basis + Bureau-Pipeline (EXP-1270)", 2026-07-20; slidefactory at `a56bf7d`/`5dd6dbb` "chore(bureau): pipeline scaffold for the core fork (bureau-init, speckit 0.7.5)", 2026-09-04. `git log --all --grep='resync|bureau-init|v2.0.0|upstream' -i` returns no other commit in either repo. So the old shape is inheritance, not rejection — slidefactory was scaffolded three days *before* the v2.0.0 tag existed and has stayed on the pre-v2 template while actively developing against it (last `scripts/` commit 2026-09-21, EXP-1478). msc's last `scripts/` commit is 2026-08-21; it is effectively frozen.
