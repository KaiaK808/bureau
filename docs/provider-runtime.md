# Background providers

Current app tasks use the app's selected model. Background jobs use `bureau-provider.py` through the `run_stage_for` shell function. The function passes prompts and system context through private files; the adapter builds argv arrays, streams the prompt on stdin, keeps provider diagnostics in separate logs, and returns only the final result. Legacy `claude_cmd_for_stage` remains for compatibility; shipped pipelines no longer execute its command strings.

```json
{
  "version": 2,
  "agents": {
    "runner": "codex",
    "spec": true,
    "implement": true,
    "qa": true,
    "code_review": {"enabled": true, "runner": "claude"},
    "providers": {
      "codex": {"reasoning_effort": "high", "timeout_seconds": 2400}
    },
    "workbench_panes": 0
  },
  "repo": {"test_command": "bash scripts/bureau-test.sh"}
}
```

Runner precedence: `BUREAU_RUNNER_STAGE`, stage runner, default runner, then Claude. Unknown runners are errors. Model precedence: provider-specific stage environment override (`BUREAU_CODEX_MODEL_IMPLEMENT`), generic stage environment override, stage model, provider model, default model when it belongs to the selected default runner, provider environment default, then Claude's legacy environment fallback. With no model setting the provider CLI chooses its configured default. A Claude default does not leak into a Codex stage. Use actual model identifiers available to the account; reasoning settings remain subject to the selected provider/model's support.

Reasoning effort precedence: `BUREAU_REASONING_STAGE`, `agents.STAGE.reasoning_effort`, then `agents.providers.PROVIDER.reasoning_effort` of the selected runner. Codex gets the value as `-c model_reasoning_effort=…` and accepts `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` and `ultra`, subject to the model's support. Claude gets it as `--effort <value>`, also behind the Headroom wrap, and accepts only `low`, `medium`, `high`, `xhigh` and `max`; any other value on a Claude stage fails as a configuration error (22) before any provider call, because the Claude CLI only warns about an unknown effort and runs with its own default. A Claude stage without a configured effort gets no `--effort` flag, so its effort comes from the operator's Claude settings. `--describe` reports the resolved value as `reasoning` for both runners.

That model precedence applies to version 2 configurations. Version 1 (including configurations without a version) preserves the older rule: generic `BUREAU_MODEL_*`, `agents.model` and stage `model` fields belong to Claude and are ignored for Codex. Set Codex models through `BUREAU_CODEX_MODEL_STAGE`, `agents.providers.codex.model` or `BUREAU_CODEX_MODEL_DEFAULT`. A migrated configuration can retain this behavior with `agents.model_compatibility: "v1"`, including after future runner environment overrides. Remove that marker from a version 2 configuration, or explicitly set it to `"v2"`, only after reviewing generic model fields for their selected providers. Other marker values are rejected.

`agents.STAGE.sandbox` or `agents.providers.PROVIDER.sandbox` can select `read-only` or `workspace-write`; `BUREAU_SANDBOX_STAGE` overrides them. Code review and research default to read-only; spec review needs workspace-write because it repairs spec artifacts. Bureau does not turn off the Codex sandbox. Normal app/OS restrictions still apply. Codex leaves Git commits/pushes to the deterministic executor; successful implementation also runs `repo.test_command` outside the nested model sandbox. QA runs the configured command independently too. Permission/environment failures are reported separately from failed project tests.

The adapter itself starts without the Bureau secrets, and the agent process and its login check start without them too: by default without `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`, `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, any variable that carries one of their values, `BASH_ENV` and `ENV`; with `repo.untrusted_env: "clean"` with only the base variables plus the provider's own login and network variables (see the [configuration reference](configuration.md) and [SECURITY.md](../SECURITY.md#code-from-the-branch-and-bureau-secrets)). An invalid `repo.untrusted_env` returns 24 before the login check. Authentication uses `codex login status` or `claude auth status --json` before creative work, without a probe generation. Missing executables/login return 16. Provider errors or malformed final results return 22; quota 23; environment/permission problems 24; timeout 124; cancellation 130. Timeout and cancellation finish by killing the provider process group even if its immediate CLI process has already exited. A process the agent started in a session of its own is outside that group and can outlive the call: Claude Code starts its Bash tool shells detached (checked in 2.1.286), so a command one of them runs, a git commit with long hooks for example, can still be running after a timeout. The implement stage's next pass is told to check for that before it removes a git lock (see [troubleshooting](troubleshooting.md#exit-124-timeout--a-provider-pass-hit-its-time-limit)). Per-stage/provider `timeout_seconds` defaults to 3600 per call (900 before v3.1); doctor warns when an enabled spec, spec review, UX, QA or review stage gets less than 1800 s. Implementation uses its existing iteration/total bounds through `BUREAU_STAGE_TIMEOUT`; since v3.2 a pass that times out is one pass of the loop, and the stage ends with 124 only when no pass is left ([troubleshooting](troubleshooting.md#exit-124-timeout--a-provider-pass-hit-its-time-limit)).

Opt-in `agents.STAGE.silence_timeout_seconds` (default `0`, off) stops a call without useful provider activity with `25` and `timeout_kind: silence`, independently of wall-clock `124` and cancellation `130`. Optional `silence_child_timeout_seconds` grants an identified live tool process a longer window measured from the last useful event. Initial association handles shell wrappers, environment prefixes and `cd … &&`; process birth identities and observed descendants then retain that association across exec. A background Bash task keeps its association after its initial result and while `TaskOutput` awaits it, until the child finishes. Provider liveness and an unfinished tool event alone grant no extra time. With the watchdog off, a successful validated result stays successful even when a background child holds stdout past the reader join; reader failures still invalidate execution evidence for gate recovery.

Parallel review lets every current provider call finish on ordinary ticket withdrawal, with silence enabled or disabled. Sibling cancellation requires an actual silence failure or explicit cancellation. Review joins all writers before consuming the shared withdrawal latch and recording its partial paid round. Silence and cancellation drain identified owned descendants; process inspection supports macOS libproc and Linux procfs/subreaper, with inherited ownership markers or ancestry sampled before detachment required to identify detached children. Resync all runtime scripts together, including `bureau-activity.py`, and restart drivers before enabling the watchdog. Local qualification uses fake providers and services; live CLI compatibility remains a separate adopting-repository check.

For Codex calls whose process exits successfully, a top-level `error` event is a recovered notice only when a later `turn.completed` follows it. An unrecovered `error` or any `turn.failed` returns 22, even if a final message exists. Recovered errors remain in `stdout.log`; a successful run records `recovered_errors.count` and `recovered_errors.first_message` (at most 200 characters) in `result.json`, and usage comes from the last `turn.completed`. A final message and any configured schema validation are still required. A failing process keeps its authentication, quota and environment classification.

JSON schema contracts cover implementation iterations, Spec Review (`bureau-spec-review.schema.json`), UX (`bureau-ux.schema.json`), QA, and the merged review verdict. Both plain JSON and legacy fenced JSON are parsed; Claude envelopes are unwrapped. A provider's diagnostic stream cannot supply the verdict. Raw prompt/output/error evidence and metadata remain under `logs/provider-runs/RUN/`. `result.json` there also names the provider's own record of the call, which outlives a timeout: since v3.2 every Claude call starts with a fresh `--session-id`, and `session_id`, `transcript` (`<config_dir, else CLAUDE_CONFIG_DIR, else ~/.claude>/projects/<slug>/<session id>.jsonl`; when Claude placed it elsewhere under `projects/`, the file found there) and `transcript_found` record it. The slug is Claude Code's own project-directory name, reproduced from its 2.1.286 binary: the resolved working directory with every UTF-16 code unit other than an ASCII letter or digit replaced by `-` (an emoji becomes `--`), and a name over 200 characters cut to 200 plus `-` and a base-36 hash of the path. Should a later Claude version name the directory differently, the search for the session id under `projects/` still finds the file. The flag is passed only to a Claude CLI that lists it in `claude --help`; the adapter asks once per binary (resolved path, size and modification time, kept in `logs/provider-runs/.claude-cli.json`) and asks again after an update. A CLI without it runs the stage as before v3.2, without the flag, and `result.json` then has `session_id: null`, `transcript_found: false` and a `transcript_note` saying why. Behind a wrapper or shim that does not change (mise, asdf, a script of one's own) the CLI can change without the key: a cached "no" is therefore asked again after a day, and when a call with the flag fails because the CLI answers `error: unknown option '--session-id'` (a downgrade), the adapter records "no", keeps that attempt's logs as `session-id-rejected.stdout.log`/`.stderr.log`, and runs the call once more without the flag right away (the refused call stopped at argument parsing, before any model call); `result.json` then carries `session_id_rejected: true`. For Codex, `session_id` is the thread id of the first `thread.started` event in `stdout.log` and `transcript` the matching rollout file under `<CODEX_HOME or ~/.codex>/sessions/`, or `null` with a `transcript_note` when Codex reported no thread id. The stage log carries the path as `Bureau provider transcript: …`. The transcript holds the whole session, tool output included; it stays where the CLI wrote it, outside `logs/`. Optional `session.cost_tracking` preserves the legacy usage envelope interface. Unknown dollar cost stays unavailable for Codex.

When a successful Claude envelope has no object in `structured_output` and the stage expects a schema, the adapter reads that session's transcript and uses the input of its last `StructuredOutput` tool call. The existing schema validation applies to that last input; an invalid later call never falls back to an earlier valid one. A recovered completion records `structured_source: "transcript"` in `result.json`. An object in the envelope takes precedence without reading the transcript. With no transcript or no such call, the envelope is handled as before (22 for a prose-only result); calls without a schema do not attempt recovery. Codex still reads its final message from `final.txt`.

Every provider invocation attempts to write a version 1 receipt under `<git common dir>/bureau/evidence/v1/runs/RUN_ID/receipts/PROVIDER_ATTEMPT_ID.json`. The metadata-only receipt includes a digest of the validated structured result (never its free text), normalized/provider exits, issue/stage/phase identity, start/end HEAD, timestamps and pointers to the original provider files. Code review additionally records `review_inputs` with `head`, `base` and `validation_head` commit IDs pinned by the pipeline after its local validation merge. Older receipts without this optional metadata remain readable; acceptance briefs cannot correlate their unpublished merge HEADs. Manifest/link/diagnostic failures are observational; receipt persistence before forwarding success remains mandatory. `result.json` links it through `receipt`, `provider_attempt_id` and `stage_attempt_id`. Standalone adapter calls get their own evidence run/attempt; a rejected `--session-id` retry gets another provider attempt. Background calls inherit the driver's run and stage-attempt identity. A stopped stdout consumer cannot erase an already persisted completion. Advisory `insights.jsonl` observations are the store's bounded free-text exception, subject to a best-effort pre-persistence content filter; see [stage insights and privacy](stage-protocol.md#advisory-stage-insights).

If successful output becomes missing or prose-only between persistence and forwarding, the adapter reconciles only the exact attempt's receipt, reads the original provider result, verifies its full digest and schema, and requires matching run, ticket, stage attempt, stage/phase, schema hash and current end HEAD. A missing or changed original fails recovery. It records `structured_source: "receipt"`. There is no latest-receipt scan or fallback to another specialist/ticket/attempt. An invalid provider result is still 22 without valid same-attempt evidence (Claude's same-session transcript recovery above remains first); provider failures, timeout 124 and cancellation 130 cannot be promoted by a previous receipt or committed work. A success receipt write failure emits no successful output; error receipts are best effort. Original `logs/provider-runs/` and transcript pointers remain diagnostic locations; durable receipts and gate digests survive disposable-worker cleanup. See [the shared evidence schema and retention](stage-protocol.md#versioned-background-evidence).

Claude `/goal` and Headroom are Claude capabilities. Claude stages with tools pass `--disallowedTools ScheduleWakeup,CronCreate,CronDelete,RemoteTrigger,Monitor`, also behind Headroom, so a deferred turn cannot replace the stage's final structured result with prose. A Codex implementation uses the portable bounded loop even when the old goal flag is enabled. Interactive bench panes use `agents.workbench_runner` or the default runner; zero panes omits the bench. Optional upstream summaries are disabled by default; enabling `agents.upstream_summary` uses a tool-free Claude (`--tools ''`, without the deny list) or read-only Codex pass.

A failed worker with uncommitted or unpublished progress loses its disposable registration. Its checkout remains available for inspection/resume instead of being erased by the next tick. A clean failure can retry normally. See [ownership and resume](stage-protocol.md).

QA, spec review and copy publish newly created files as well as tracked edits through the shell executor. Local credentials/configuration and provider evidence remain outside these commits. Already-staged private files block publication without changing the index; inspect and unstage them before retrying. Commit or push failures stop routing so that the next stage cannot receive an unpublished result.

Validation currently uses fake executors and real local Git/test commands. Run a representative live ticket in an adopting repository before relying on unattended Codex or mixed-provider operation.

## Claude configuration directory

A headless Claude stage otherwise runs with the operator's personal Claude Code setup: the default configuration directory brings the global `CLAUDE.md`, hooks, plugins and user-scope MCP servers, and each of those servers starts extra processes for every stage call. An installation can give its Claude stages a lean profile of their own instead, with `agents.providers.claude.config_dir` in `.bureau.json` or `BUREAU_CLAUDE_CONFIG_DIR` in the process environment (the environment wins). Claude Code reads settings, instructions, MCP configuration, session history and the login from the directory `CLAUDE_CONFIG_DIR` names (see "Log in with multiple accounts" in Claude Code's authentication documentation; on macOS the Keychain entry is keyed to that directory too), so the profile needs its own login: run `CLAUDE_CONFIG_DIR=<dir> claude` once and log in. The value is an absolute path to an existing directory or starts with `~/` (the home directory); anything else is a configuration error that ends the call with 22 before any provider call. When set, the adapter puts `CLAUDE_CONFIG_DIR=<dir>` into the environment of the `claude` child (also behind the Headroom wrap and under `repo.untrusted_env: "clean"`) and of its `claude auth status --json` check, and nowhere else; the transcript recorded in `result.json` is looked up there too. When unset, the child's environment is exactly what it was before. Codex stages ignore both settings. `--describe` reports the resolved directory as `config_dir` for Claude stages (`null` when unset). Doctor lists the directory of every enabled Claude stage under `claude_config_dirs`; for a configured one it runs `claude auth status --json` there and warns when it does not report `loggedIn: true`, and a stage without one shows the inherited directory as `configured: false`, not checked.

## Codex implementation sandbox gate

Codex may abort or fail a configured gate inside its sandbox even when it passes outside. For these holds, report `NEEDS_HUMAN` with an exhaustive `notes.needs_human` array: each gate entry has `kind: gate`, `command` equal to the exact `repo.test_command`, and a free-text `reason`. Include independent product, security and human-decision holds with their corresponding kind and empty command. Never change/skip tests or disguise other holds as gates. Existing `SANDBOX_GATE:` reason syntax remains supported, with the same machine-proof requirement.

The adapter observes live Codex command execution items and repository HEADs. Repository-root cwd comes from exactly one matching, ordered rollout begin/end pair sharing a call ID and matching command/exit/output. It recognizes only the exact configured command or an absolute system `/bin/bash` or `/bin/sh` in the exact `-c`/`-lc` form. `env` wrappers require absolute `/usr/bin/env`, explicit system-only PATH and `bash`; relative/agent-owned shells, arbitrary flags, missing/duplicate/reordered/ambiguous events and agent tool requests are not execution proof.

The planner requires a matching metadata-only completion receipt, canonical result digest, configured-command digest and failed/aborted execution at HEAD A, with current HEAD still A when unpublished or exactly B after an explicit executor publication recorded under the evidence lock for the same provider/stage attempt (allowlisted IDs, HEADs, sole-parent verification, `Bureau-Generated: true` trailer flag and timestamp), reverified for exactly one hop with the outside rerun/reservation at B, including QA's final run. The prefix alone grants no eligibility. It reserves at most one outside rerun per gate/HEAD/stage attempt, including incomplete runs, then revalidates immediately before running system Bash with pipefail, secret filtering and the stage timeout. Green clears only those gate holds; unknown commands, stale HEAD, missing evidence and product/security/human holds stay blocked, even with contradictory COMPLETE/GREEN. With commits beyond origin/main, implement still runs the post-implement hook and squash-range check before this gate. Red/abort restores NEEDS_HUMAN and includes a normal stage-log pointer; hook failure remains 14. Merge authorization is unchanged.

The shared evidence store contains only allowlisted execution identities/measurements and digests: no raw command, output, ticket/result prose or copied log. Outside logs live under `logs/outside-gates/` and are outside evidence retention. Gate reconciliation uses the result and command digests plus gate IDs, independently of original provider log availability. Completion-output recovery still needs its original result as described above. Optional evidence failures disable gate recovery without changing provider outcomes. Cancellation 130 is captured before later evidence I/O and wins over write/read/validation failures. See the [exact reconciliation contract](stage-protocol.md#sandbox-only-gate-recovery).

Gate-run responses use `outside gate green` for verified success and `outside gate red, aborted or incomplete` for failed, timed-out, cancelled or incomplete runs. `gate evidence unavailable` means evidence reconciliation failed; `outside gate execution failed` means command execution failed, and `outside gate termination uncertain` means cleanup could not confirm termination. Every signalling error except ESRCH remains uncertain unless the shared EPERM re-probe observes ESRCH within its deadline; an exited leader or an empty process listing cannot clear it. Both gate recovery and conflict validation reject uncertainty, return `eligible: false` and `green: false` and retain any outside-log pointer. Every claimed reservation prevents another execution. Cancellation is latched before termination and retains exit 130 / `abort: kill`; timeout retains 124 / `abort: timeout`. An otherwise successful uncertain gate exits 25 with `failure_cause: human_hold`; no passing rerun record is persisted. Implementation and QA propagate uncertain-gate 25, 124 and 130 immediately, keeping the log pointer and stopping before routing or further publication. Signal handlers are restored on every path.

The shared `bureau-process.py` helper gives provider, acceptance, conflict, dispatcher, runtime and inline post-implement callers the same termination handling. After a termination signal fails with EPERM it re-probes only with `killpg(group, 0)`, using a single two-second monotonic deadline and backoff from 10 ms to at most 100 ms. ESRCH within that deadline proves the group is gone, including when macOS briefly returns EPERM for an unreaped zombie-only group. During these re-probes the owning caller reaps its direct child through the live process handle, allowing provider cleanup to finish before dispatcher shutdown; reaping alone never proves group absence. Successful probes and further errors do not reset the deadline or clear the original uncertainty; without ESRCH by the deadline, termination stays uncertain and ownership remains held. The error path never consults process listings. A direct leader kill remains best effort. Exit checks use the same shared deadline and backoff after both successful signal-0 probes and EPERM, allowing asynchronously killed members to exit before inspection. ESRCH within the deadline proves absence. Only when the deadline expires with a successful last probe does the check use bounded macOS/Linux `ps -axo pgid=,stat=` inspection: no visible non-zombie members means gone; a live member or unavailable, timed-out or malformed inspection remains uncertain. EPERM or another error at the deadline stays uncertain without consulting process listings. A failed termination signal still requires ESRCH to clear its uncertainty; exit-check inspection cannot override that failure. Outside gates also require the leader to be reaped. Before spawning, outside gates and dispatcher helpers fsync a record in `<git common dir>/bureau/process-holds/`; a lock distinguishes an active call from unfinished work. Uncertainty leaves that record intact, retains leases and worktree registration without cleanup, and makes a restarted dispatcher refuse with exit 25 and `human_hold`. Worker EXIT cleanup checks the same hold before detaching the branch or removing registration, while preserving its original exit. This remains durable when later writes fail. A failed initial hold write prevents launch. Stop and inspect the writers, reconcile saved work and explicitly remove their hold files before releasing the run or restarting dispatch; existing `dispatch-termination.json` holds also require explicit removal. Stored IDs are never signalled during release or reconciliation. Conflict validation leaves an uncertain merge/index/worktree in place for the operator. Runtime registration writes an interrupted record before spawning and clears that flag only with successful registration; failed cleanup retains ownership. Dispatcher cancellation escalates after five seconds, bounds stdout drain and leader reaping to one second each and retains 130. Resync the complete scripts scope after comparing installed drift. Qualification uses fake services and local fixtures; hosted cross-platform and live installation checks remain separate.

A Codex child without `TMPDIR` gets a private `bureau-codex-*` directory under resolved `/tmp`, outside the repository regardless of `TEMP` or `TMP`. Allocation follows the stop handlers; removal follows the child on completion, timeout, interruption or exceptions. The provider's own environment is unchanged. Removal failures are reported without failing the run. An existing `TMPDIR` passes through unchanged; Claude gets no added directory.

## Codex QA sandbox gate

QA uses the same proof, planner, reservation and runner. Report an exhaustive `blockers` array with `kind`, exact test `command` and free-text `reason`; product/security/human holds must also be included. The existing NEEDS_HUMAN `coverage_notes` prefix `SANDBOX_GATE:` remains one input, subject to the same failed-execution/current-HEAD proof. Typed blockers take precedence. Optional canonical fields stay optional for Claude and old results; the Codex wire projection makes them required/nullable and removes only declared optional nulls before canonical validation. Receipt recovery applies that same normalization to the original Codex file before comparing its canonical result digest.

The configured command or existing deterministic QA fallback is shared by the provider observer and QA shell. The initial shell run and its flake retry remain unchanged. After publication, an eligible hold uses Phase 3 as its one outside rerun; no extra final run is added. QA reads the outside log from the normal stage log directory, never from evidence. Green hands off to Build Review; red returns to Build, with output/pointer in the normal QA log/comment. An independent hold remains NEEDS_HUMAN even when the suite passes; a later squash-range failure also retains its hold. A Codex RED with missing/unknown/stale proof cannot be promoted merely because a normal final suite passes. Claude behavior remains unchanged.

Resync provider, evidence, gates, config, implement/QA and schemas together, reconcile installation drift and restart drivers. A prefix without failed-execution proof now stays blocked. No configuration migration or exit-code change. These are local fake-provider/real-Git tests; representative live CLI/event and adopting-repository qualification remains pending. The store is not tamper-proof and neither an outside green nor a gate receipt authorizes a merge.
