# Background providers

Current app tasks use the app's selected model. Background jobs use `bureau-provider.py` through the `run_stage_for` shell function. The function passes prompts and system context through private files; the adapter builds argv arrays, streams the prompt on stdin, keeps provider diagnostics in separate logs, and returns only the final result. Legacy `claude_cmd_for_stage` remains for compatibility; shipped pipelines no longer execute its command strings.

```json
{
  "version": 2,
  "agents": {
    "runner": "codex",
    "spec": true,
    "implement": true,
    "qa": true,
    "code_review": {"enabled": true, "runner": "claude"},
    "providers": {
      "codex": {"reasoning_effort": "high", "timeout_seconds": 2400}
    },
    "workbench_panes": 0
  },
  "repo": {"test_command": "bash scripts/bureau-test.sh"}
}
```

Runner precedence: `BUREAU_RUNNER_STAGE`, stage runner, default runner, then Claude. Unknown runners are errors. Model precedence: provider-specific stage environment override (`BUREAU_CODEX_MODEL_IMPLEMENT`), generic stage environment override, stage model, provider model, default model when it belongs to the selected default runner, provider environment default, then Claude's legacy environment fallback. With no model setting the provider CLI chooses its configured default. A Claude default does not leak into a Codex stage. Use actual model identifiers available to the account; reasoning settings remain subject to the selected provider/model's support.

Reasoning effort precedence: `BUREAU_REASONING_STAGE`, `agents.STAGE.reasoning_effort`, then `agents.providers.PROVIDER.reasoning_effort` of the selected runner. Codex gets the value as `-c model_reasoning_effort=…` and accepts `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` and `ultra`, subject to the model's support. Claude gets it as `--effort <value>`, also behind the Headroom wrap, and accepts only `low`, `medium`, `high`, `xhigh` and `max`; any other value on a Claude stage fails as a configuration error (22) before any provider call, because the Claude CLI only warns about an unknown effort and runs with its own default. A Claude stage without a configured effort gets no `--effort` flag, so its effort comes from the operator's Claude settings. `--describe` reports the resolved value as `reasoning` for both runners.

That model precedence applies to version 2 configurations. Version 1 (including configurations without a version) preserves the older rule: generic `BUREAU_MODEL_*`, `agents.model` and stage `model` fields belong to Claude and are ignored for Codex. Set Codex models through `BUREAU_CODEX_MODEL_STAGE`, `agents.providers.codex.model` or `BUREAU_CODEX_MODEL_DEFAULT`. A migrated configuration can retain this behavior with `agents.model_compatibility: "v1"`, including after future runner environment overrides. Remove that marker from a version 2 configuration, or explicitly set it to `"v2"`, only after reviewing generic model fields for their selected providers. Other marker values are rejected.

`agents.STAGE.sandbox` or `agents.providers.PROVIDER.sandbox` can select `read-only` or `workspace-write`; `BUREAU_SANDBOX_STAGE` overrides them. Code review and research default to read-only; spec review needs workspace-write because it repairs spec artifacts. Bureau does not turn off the Codex sandbox. Normal app/OS restrictions still apply. Codex leaves Git commits/pushes to the deterministic executor; successful implementation also runs `repo.test_command` outside the nested model sandbox. QA runs the configured command independently too. Permission/environment failures are reported separately from failed project tests.

The adapter itself starts without the Bureau secrets, and the agent process and its login check start without them too: by default without `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`, `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, any variable that carries one of their values, `BASH_ENV` and `ENV`; with `repo.untrusted_env: "clean"` with only the base variables plus the provider's own login and network variables (see the [configuration reference](configuration.md) and [SECURITY.md](../SECURITY.md#code-from-the-branch-and-bureau-secrets)). An invalid `repo.untrusted_env` returns 24 before the login check. Authentication uses `codex login status` or `claude auth status --json` before creative work, without a probe generation. Missing executables/login return 16. Provider errors or malformed final results return 22; quota 23; environment/permission problems 24; timeout 124; cancellation 130. Timeout and cancellation finish by killing the provider process group even if its immediate CLI process has already exited. A process the agent started in a session of its own is outside that group and can outlive the call: Claude Code starts its Bash tool shells detached (checked in 2.1.286), so a command one of them runs, a git commit with long hooks for example, can still be running after a timeout. The implement stage's next pass is told to check for that before it removes a git lock (see [troubleshooting](troubleshooting.md#exit-124-timeout--a-provider-pass-hit-its-time-limit)). Per-stage/provider `timeout_seconds` defaults to 3600 per call (900 before v3.1); doctor warns when an enabled spec, spec review, UX, QA or review stage gets less than 1800 s. Implementation uses its existing iteration/total bounds through `BUREAU_STAGE_TIMEOUT`; since v3.2 a pass that times out is one pass of the loop, and the stage ends with 124 only when no pass is left ([troubleshooting](troubleshooting.md#exit-124-timeout--a-provider-pass-hit-its-time-limit)).

JSON schema contracts cover implementation iterations, QA, and the merged review verdict. Both plain JSON and legacy fenced JSON are parsed; Claude envelopes are unwrapped. A provider's diagnostic stream cannot supply the verdict. Raw prompt/output/error evidence and metadata remain under `logs/provider-runs/RUN/`. `result.json` there also names the provider's own record of the call, which outlives a timeout: since v3.2 every Claude call starts with a fresh `--session-id`, and `session_id`, `transcript` (`<config_dir, else CLAUDE_CONFIG_DIR, else ~/.claude>/projects/<slug>/<session id>.jsonl`; when Claude placed it elsewhere under `projects/`, the file found there) and `transcript_found` record it. The slug is Claude Code's own project-directory name, reproduced from its 2.1.286 binary: the resolved working directory with every UTF-16 code unit other than an ASCII letter or digit replaced by `-` (an emoji becomes `--`), and a name over 200 characters cut to 200 plus `-` and a base-36 hash of the path. Should a later Claude version name the directory differently, the search for the session id under `projects/` still finds the file. The flag is passed only to a Claude CLI that lists it in `claude --help`; the adapter asks once per binary (resolved path, size and modification time, kept in `logs/provider-runs/.claude-cli.json`) and asks again after an update. A CLI without it runs the stage as before v3.2, without the flag, and `result.json` then has `session_id: null`, `transcript_found: false` and a `transcript_note` saying why. Behind a wrapper or shim that does not change (mise, asdf, a script of one's own) the CLI can change without the key: a cached "no" is therefore asked again after a day, and when a call with the flag fails because the CLI answers `error: unknown option '--session-id'` (a downgrade), the adapter records "no", keeps that attempt's logs as `session-id-rejected.stdout.log`/`.stderr.log`, and runs the call once more without the flag right away (the refused call stopped at argument parsing, before any model call); `result.json` then carries `session_id_rejected: true`. For Codex, `session_id` is the thread id of the first `thread.started` event in `stdout.log` and `transcript` the matching rollout file under `<CODEX_HOME or ~/.codex>/sessions/`, or `null` with a `transcript_note` when Codex reported no thread id. The stage log carries the path as `Bureau provider transcript: …`. The transcript holds the whole session, tool output included; it stays where the CLI wrote it, outside `logs/`. Optional `session.cost_tracking` preserves the legacy usage envelope interface. Unknown dollar cost stays unavailable for Codex.

Claude `/goal` and Headroom are Claude capabilities. A Codex implementation uses the portable bounded loop even when the old goal flag is enabled. Interactive bench panes use `agents.workbench_runner` or the default runner; zero panes omits the bench. Optional upstream summaries are disabled by default; enabling `agents.upstream_summary` uses a tool-free Claude or read-only Codex pass.

A failed worker with uncommitted or unpublished progress loses its disposable registration. Its checkout remains available for inspection/resume instead of being erased by the next tick. A clean failure can retry normally. See [ownership and resume](stage-protocol.md).

QA, spec review and copy publish newly created files as well as tracked edits through the shell executor. Local credentials/configuration and provider evidence remain outside these commits. Already-staged private files block publication without changing the index; inspect and unstage them before retrying. Commit or push failures stop routing so that the next stage cannot receive an unpublished result.

Validation currently uses fake executors and real local Git/test commands. Run a representative live ticket in an adopting repository before relying on unattended Codex or mixed-provider operation.

## Claude configuration directory

A headless Claude stage otherwise runs with the operator's personal Claude Code setup: the default configuration directory brings the global `CLAUDE.md`, hooks, plugins and user-scope MCP servers, and each of those servers starts extra processes for every stage call. An installation can give its Claude stages a lean profile of their own instead, with `agents.providers.claude.config_dir` in `.bureau.json` or `BUREAU_CLAUDE_CONFIG_DIR` in the process environment (the environment wins). Claude Code reads settings, instructions, MCP configuration, session history and the login from the directory `CLAUDE_CONFIG_DIR` names (see "Log in with multiple accounts" in Claude Code's authentication documentation; on macOS the Keychain entry is keyed to that directory too), so the profile needs its own login: run `CLAUDE_CONFIG_DIR=<dir> claude` once and log in. The value is an absolute path to an existing directory or starts with `~/` (the home directory); anything else is a configuration error that ends the call with 22 before any provider call. When set, the adapter puts `CLAUDE_CONFIG_DIR=<dir>` into the environment of the `claude` child (also behind the Headroom wrap and under `repo.untrusted_env: "clean"`) and of its `claude auth status --json` check, and nowhere else; the transcript recorded in `result.json` is looked up there too. When unset, the child's environment is exactly what it was before. Codex stages ignore both settings. `--describe` reports the resolved directory as `config_dir` for Claude stages (`null` when unset). Doctor lists the directory of every enabled Claude stage under `claude_config_dirs`; for a configured one it runs `claude auth status --json` there and warns when it does not report `loggedIn: true`, and a stage without one shows the inherited directory as `configured: false`, not checked.

## Codex implementation sandbox gate

A Codex implement turn normally uses `workspace-write`, where socket bind/listen, network access or the per-user temporary directory can be denied. Finish the other work and report `NEEDS_HUMAN` with one `notes.needs_human` object per affected task. Its string `reason` must begin with `SANDBOX_GATE:` and name the failing tests and denied operation. Never change, skip or deselect tests to bypass the sandbox; code failures and other blockers must not use this prefix.

Only a non-empty array with every reason prefixed qualifies. The provider passes that Codex result to the shell even when it contains “Operation not permitted”. The shell accepts one JSON object or a cost envelope whose `result` string holds one object; fenced JSON, trailing garbage, multiple values and malformed or mixed reasons do not qualify. With `repo.test_command` configured and commits beyond `origin/main`, the stage promotes to COMPLETE before the post-implement hook and squash-range check. If both allow completion, it runs the tests once after the final push, outside the Codex sandbox via `bureau_untrusted_env bash --noprofile --norc -c`, without Bureau secrets. Green hands off to QA or Build Review; red or an emptied command restores NEEDS_HUMAN. The summary comment records the decision. Hook failures still halt with exit 14; other intervening halts and Claude behaviour stay as before.

A Codex child without `TMPDIR` gets a private `bureau-codex-*` directory under resolved `/tmp`, outside the repository regardless of `TEMP` or `TMP`. Allocation follows the stop handlers; removal follows the child on completion, timeout, interruption or exceptions. The provider's own environment is unchanged. Removal failures are reported without failing the run. An existing `TMPDIR` passes through unchanged; Claude gets no added directory.

## Codex QA sandbox gate

When the QA runner resolves to Codex (including `BUREAU_RUNNER_QA=codex`), its prompt notes that socket bind/listen, network access and the per-user temporary directory can be denied inside the sandbox. The initial test output in the prompt comes from the shell outside it. Never change, skip or deselect a test to bypass the sandbox. If the sandbox alone prevents confirmation of the suite, report status `NEEDS_HUMAN` with string `coverage_notes` beginning with `SANDBOX_GATE:` and naming the tests and denied operation. A correctness bug or a harness broken outside the sandbox stays NEEDS_HUMAN without the prefix. QA uses its existing schema; there is no needs-human array.

The provider passes a qualifying Codex QA result to the shell even when it contains “Operation not permitted”, instead of ending with 24. The shell accepts exactly one JSON object or a cost envelope whose `result` string holds exactly one object with status `NEEDS_HUMAN` and the prefixed notes; fenced JSON, trailing garbage, multiple values, missing or non-string notes and prefixes elsewhere in the notes do not qualify. After publication, the existing Phase 3 test run outside the sandbox via `bureau_untrusted_env bash --noprofile --norc -o pipefail -c` decides GREEN or RED: green moves to Build Review, red returns to Build, neither adds `needs-human`. No extra test run is added. The shell echoes the decision and puts it first in the summary comment; a later squash-range failure still sets NEEDS_HUMAN and puts its report first. Unprefixed blockers retain their existing handling even with a passing suite. Claude prompts and behaviour, other stages and exit codes stay unchanged.

Resync `qa-pipeline.sh`, `bureau-config.sh` and `bureau-provider.py` together and restart queue loops and supervisors. Keep `repo.test_command` set to the full project gate: the prefix is the agent's diagnosis, and the outside run covers only that command's tests. Full-stage harness tests and mutation controls run in CI; live Codex QA acceptance remains pending.
