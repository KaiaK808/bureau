Bureau v3.2.0 — unexported secrets, implement work kept on origin, and queues that move past a waiting gate

Stable release · 2026-10-06 · source tag v3.2.0. The GitHub Release records the exact tagged commit. It is superseded by the patch release v3.2.1. v3.2.0 has the same runtime, installer, templates and tests as its candidate, v3.2.0-rc.1. The previous stable release is v3.1.0. Earlier releases: v3.1.0's candidates v3.1.0-rc.2 and v3.1.0-rc.1, v3.0.2, v3.0.1, v3.0.0 with its candidates v3.0.0-rc.2 and v3.0.0-rc.1, and the previous major release v2.0.0.

v3.2 is a minor release on v3.1.0 with eleven pull requests. It closes indirect paths to the Bureau secrets, retries timed-out implement passes and pushes their work before a failure ends the stage, brings review and QA findings into rework, lets queues move past a waiting merge gate, stops a run on a hang-up, and fixes stale spec-state reads and broken-pipe handling. The v3 exit-code contract stays; no exit code is new.

What changed since v3.1.0

  • The stages keep the .env keys unexported, and remote git runs without branch hooks (#49).
    • LINEAR_API_KEY, TELEGRAM_BOT_TOKEN and TELEGRAM_ALERT_CHAT_ID, and the stages' API_KEY copy, stay as unexported shell variables. Processes a stage, driver or the runtime starts no longer carry those .env keys, also when the operator's shell exported SHELLOPTS with allexport; a traced run (bash -x) no longer prints them. The runtime parses .env with the stages' reader instead of sourcing it as shell code for its Linear calls.
    • Every script reads only BUREAU_ENV_FILE, by default the .env next to .bureau.json in the main checkout, never a .env the branch commits. A relative value counts from the directory BUREAU_CONFIG names, without resolving a link; the scripts export the resolved absolute path so a runtime relaunch reads the same file. Doctor reads BUREAU_RUNNER_IMPLEMENT from that file too.
    • Bureau's own remote git commands (push, fetch, pull, ls-remote, clone, remote and submodule) keep the GitHub token variables for authentication but switch repository hooks off: hooks in a hooks directory and, with git 2.54 and later, configuration-defined hooks, including the empty hook name and a listing made with GIT_CONFIG in the environment. Local git commands keep their hooks and run without the tokens, as in v3.1. repo.remote_git_runs_hooks: true restores the shell's remote hooks, which then see the GitHub tokens; repositories with Git LFS need it. Doctor warns about a non-boolean value and about filter=lfs without true in the main checkout's top-level or listed nested .gitattributes, or .git/info/attributes.
    • A key set only in the operator's shell stays in the processes below it; keep the keys only in .env to get the protection. Stored logins, same-user files and commands branch code can name in .git/config remain outside this boundary (see SECURITY.md).
  • Python helpers are isolated, and doctor checks the same linked directories and implement runner as the stages (#47).
    • Every Python start in the shell runtime templates now carries python3 -I, including supervision's eight calls, the reset's ownership check, bureau-status.sh and bureau-app.sh. Empty or relative PYTHONPATH entries no longer let modules the branch committed stand in for the standard library there.
    • Doctor searches each directory in repo.worktree_links with the stages' find -L DIR -mindepth 1 -iname '.env*' -print -quit, without a depth limit. A hit (holds an env file, naming the first hit), a failing search or a missing find (not searched completely) is an error; the stages already skipped those links in v3.1. The search matches names, so a link under another name pointing at a .env file is not found; GNU find fails on a link loop, while macOS's BSD find skips it.
    • The missing repo.test_command warning appears only when implement resolves to Codex, including BUREAU_RUNNER_IMPLEMENT loaded from .env, and also when implement is disabled because the shepherd can force the stage on. Claude implementations no longer get the warning; doctor reads only that runner key from .env, never executes the file, and its effective-settings report still uses JSON and the process environment.
  • Implement retries a timed-out pass and keeps a failed pass's work on origin (#46).
    • Exit 124 becomes status=TIMEOUT for the pass, with its Git commits and the tasks it marked, the squash-range check and the usual push or deferral. The next pass checks the task list and branch first and reports COMPLETE only when the work and any feedback above it are addressed. The stage ends with 124 only when no pass is left under BUREAU_IMPL_MAX_ITER or BUREAU_IMPL_TOTAL_TIMEOUT; every other provider failure still ends it with that code.
    • Every way out before the end-of-run push now tries to push what origin lacks, in both push modes and from a first pass: a failed or timed-out last pass, a signal, a crash, unusable Linear and a failed /goal run. The EXIT trap is armed after the stage's own merge of origin/main; a stop before any implementation commit can therefore push that merge alone. The push is best effort, a refusal says the work is only in this worktree, and the original exit code stays even with stderr gone. On a stop the push shares the stage's process group and ends at the latest when its stop grace ends. A successful push at the end of a run confirms the branch, commit count and head.
    • Every stage's system text and scripts/bureau-stage.md forbid waiting for, polling or re-triggering CI or a merge gate inside the stage and committing CI results as evidence, taking precedence over project instructions. Missing, pending or failed CI does not change the status the agent reports for its own work; waiting belongs to the merge gate and the shepherd. /linear-implement asks for passing tests instead of passing checks.
    • Provider evidence gains session_id, transcript and transcript_found in result.json and a transcript log line, also for a timeout with empty stdout. Claude gets a fresh --session-id when its CLI supports it; an unsupported flag is omitted, a refusal behind an unchanged wrapper is retried once without it, and a cached unsupported answer is checked again within a day. Codex's thread id names its rollout file; a missing transcript does not fail the call.
  • A rework reads the newest review or QA findings (#53).
    • Implement now takes QA RED, QA NEEDS_HUMAN, build review BLOCK and the app runtime's VERDICT: BLOCK, alongside Changes Requested and FIXES_NEEDED. Every QA RED rework receives QA's summary, and a restart from build after a BLOCK or QA NEEDS_HUMAN receives those findings; comments posted by v3.1 count too.
    • The newest finding wins. An approval, QA PASSED or a halt comment does not retire an older finding; write a later FIXES_NEEDED before a build pass that should use another list or have nothing to fix. The prompt block is labelled --- Feedback to address (PRIORITY) ---, with “Address ALL fixes before remaining tasks.” kept. A QA bounce with every task already checked still hands back to QA without a commit, as before.
  • A waiting merge gate no longer holds its stage's queue, and a check stuck queued blocks after a grace (#48).
    • Review and merge pickers put a held ticket after other candidates while origin stays at the judged head, and still take it when nothing else in that stage can be picked. The hold starts at two poll intervals, at least 300 s, doubles with each further answer and is capped by agents.merge_gate_recheck_seconds (default 3600; 0 restores every poll). A push, a branch gone from origin or a record time in the future ends it; an unreadable record or origin warns and holds nothing. The merge stage marks both 2 and 25, without setting needs-human; the rebase picker is never held. The shepherd names its ticket, so the picker holds do not delay its retries.
    • A review gate-wait record keeps a passed build check for the same head, base and key (the command, repo.untrusted_env and repo.worktree_links), so a retry skips that check as well as reusing the approval. A changed input, a red check, a --no-merge stop or an approval kept after a blocked gate still runs the check.
    • A check run with status queued past agents.merge_ci_queued_grace_seconds (default 3600, measured from the check run's started_at) blocks the gate with 25 and a line naming the longest-queued check. The queue alerts hourly per ticket; an inline merge adds needs-human, and the shepherd halts. The PR gets one gate comment while only the age changes. An unreadable time, a running check, deployment approval, concurrency wait or pending commit status stays “not yet”; doctor validates both new keys with the gate's number rule.
  • The bounded tick moves on past a lone held ticket (#54).
    • An all-stage bureau-tick.sh --allow-merge passes over Build Review or Merge when its only pick waits on its merge gate, and no later stage in that tick takes that ticket, including rebase. It runs the next stage with work, or comes back to the stages passed over in order if no other stage has work; an expired hold is picked in its normal turn. --stage, the default --no-merge tick and the queue loop keep their behaviour. logs/bureau-tick.json still names only the stage and ticket that ran, with the same outcomes and exit codes.
    • The log gains the pass-over line, tick: no other stage has work — back to … and the picker's taken although it waits on its merge gate line. A usage throttle ends the tick before it comes back, so a Merge ticket passed over waits for its hold to run out. Tests now check that gate-waits' git ls-remote has no Bureau secrets and a failed Linear pick keeps exit 27 while a hold is active.
  • A hang-up stops a run like SIGTERM (#50).
    • Closing the terminal, ssh connection, tmux window or tmux session stops the runtime and provider with SIGHUP forwarded as SIGTERM; the shepherd, worker and queue supervisor trap it too. The same stop graces, exit 130, preserved work and resume steps apply. Writes to a terminal that is gone no longer break the protected cancellation paths; detaching tmux or starting under nohup still keeps a run going.
    • A child's exit 130 counts as interrupted at every runtime wrapper level. A signal to an inner process group now keeps the run's leases even if the shepherd ends before its stage, or between stages; release refuses while a recorded process group is alive. Kept leases on a queue lane's shared worktree block every ticket of that lane with 21 until released. Signalling the supervisor's process alone still leaves the stage in flight running; How to stop a run describes the whole-group stop and the resume steps. Implement's final failure-push behaviour is the later change in #46 above.
  • The shepherd confirms the intermediate Spec state before a bump to Triage (#51).
    • A moment-old Linear read after a successful spec stage could show the Spec state between its two moves; the shepherd treated it as confirmed and bumped the finished spec from Spec Review back to Triage. It now re-reads that intermediate state through the existing bounded confirmation before acting. A real Spec returned by spec review costs no extra wait; no setting or exit code changes, and the queue loop and tick do not bump.
  • Long stage text no longer fails through an early-exiting pipe reader (#56).
    • Spec uses and posts a long research digest with its marker near the top instead of dropping it as “no valid output”; review takes its verdict's first line without a broken pipe ending the stage with 141 or 1 after the paid review; upstream-port.sh accepts long commit messages instead of failing the title fetch with 18. A failing gh still ends the port with 18. Other converted sites use here-strings or readers that read to the end; two dry-run byte-truncation lines with ignored status stay allowed.
    • The scan in tests/test_pipe_early_exit.sh now covers templates/scripts/*.sh as well as tests, with the deliberate negative controls and two dry-run lines allowed. No configuration or exit-code changes.
  • Temporary Python test repositories stop git's detached maintenance before cleanup (#52).
    • The Python tests that commit or push into temporary repositories switch maintenance.auto off, including on their bare origins. A detached repack on git 2.54 or later could recreate files while cleanup removed .git and fail an otherwise passing test with “Directory not empty: '.git'”. Trace tests check that no maintenance or gc child starts; nothing installed changes.
  • Tests avoid early-exiting readers under pipes (#55).
    • head, grep -q/-m/-l, awk … exit and sed … q behind a pipe are replaced with a here-string, a file or a reader that reads to the end, apart from deliberate negative controls. Under pipefail the broken pipe sometimes failed test_needs_human_hold.sh on ubuntu and could let a hasnt check pass over a match. tests/test_pipe_early_exit.sh probes the real helpers on 1 MB inputs and scans for the pattern; nothing installed changes in this PR.

See the changelog for the full entries, configuration for the new keys, exit codes for the vocabulary and troubleshooting for stopping and resuming a run.

Upgrade an existing installation

From v3.1.0: select tag v3.2.0 in the source skill checkout and resync the scripts scope and the interfaces scope as one set (--resync-interfaces --resync-scripts). The scripts depend on each other, including bureau-env.sh, bureau-config.sh, the runtime, provider, supervision, doctor, stages, worker, shepherd, tick and queue drivers; #46 also changes templates/commands/linear-implement.md and templates/scripts/bureau-stage.md, so include the interfaces. Preserve local work and resolve customized-file conflicts as in migration; /bureau-init --update changes configuration only. From a v3.1 candidate or older release, go through Upgrade to v3.1 and the earlier upgrade notes too, selecting v3.2.0 and both scopes.

Check these before dispatch resumes; the complete operator list is in Upgrade to v3.2:

  • Git LFS before resync: set repo.remote_git_runs_hooks: true in repositories that use LFS, or Bureau's pushes leave the LFS objects off the remote; doctor warns when .gitattributes uses filter=lfs without it (#49). Other pre-push checks, including global secret scanners, no longer run during Bureau's remote git by default; use CI for them or deliberately enable the hooks, which then see the GitHub tokens.
  • One operator .env: move it next to .bureau.json or set BUREAU_ENV_FILE; a relative value counts from the directory .bureau.json is named in, and stages export an absolute path (#49). A branch's .env is not read, and a different .env in the working directory no longer overrides the chosen one. Scripts of an installation that depended on the three keys being exported must read .env themselves; keep secrets only in .env, since shell-only keys remain inherited. Allexport is switched off, and custom scripts that handle a key must hide it from their own traces.
  • Git wrappers and Python: remote git's leading arguments now include -c core.hooksPath=/dev/null, event switches and the shell's per-name hook switches (or --config-env for a name with =), before the subcommand (#49). The newly isolated Python starts ignore PYTHON* variables and user site-packages (#47).
  • Doctor: remove a linked directory that holds a .env* name or move the file out; an incomplete search is now an error too, and large linked directories are searched once per doctor run (#47). The missing-test-command warning follows the effective implement runner, including the runner key in .env, and is now Codex-only.
  • Implement time budget and pushes: timed-out passes can now use all BUREAU_IMPL_MAX_ITER passes (default 3) within BUREAU_IMPL_TOTAL_TIMEOUT (5400 s), instead of stopping after the first BUREAU_IMPL_ITER_TIMEOUT (1800 s); BUREAU_IMPL_MAX_ITER=1 or a total budget equal to one pass restores that ceiling, each also limiting productive runs (#46). Timed-out, failed or interrupted passes now push what origin lacks in both modes, including a failed /goal run, and a stopped first pass can push the stage's merge commit alone; with deferred pushes and an open PR this can cost one CI run. A push on a stop shares the existing grace and remains best effort. After a timed-out Claude pass a detached git process may still run; the next pass removes a lock only when none does, otherwise reports NEEDS_HUMAN.
  • Stage CI rule and evidence: waiting, polling, re-triggering CI and committing its results are forbidden even if project instructions ask for them; background stages get the rule from resynced scripts, app stages once scripts/bureau-stage.md is committed (#46). CI does not decide the agent's work status. Provider result.json gains the transcript fields; a CLI without --session-id runs as before, and deleting logs/provider-runs/.claude-cli.json is harmless.
  • Rework: the newest matching review, QA or operator finding is used, including v3.1 comments; an approval or QA PASSED does not retire one, so write a later FIXES_NEEDED for another list or nothing to fix (#53). After a timed-out pass, COMPLETE also requires that feedback to be addressed (#46).
  • Queued CI grace: a check queued past agents.merge_ci_queued_grace_seconds (default 3600 s) now blocks with 25, an alert, needs-human after an inline merge and a shepherd halt (#48). On a single self-hosted runner, measure job waits (created_at → started_at of Actions jobs) before keeping the default: readings so far include about 15 minutes for the third run in a busy queue and once 13 minutes queued on an idle runner. 0 blocks at once; 9999999 keeps v3.1's behaviour.
  • Gate holds: a held ticket goes after other candidates for two poll intervals (at least 300 s), doubling up to agents.merge_gate_recheck_seconds (default 3600); alone in its stage the queue still picks it each poll (#48). With other work waiting, a gate that turns green can wait up to one hold; lower the cap or use 0 for every poll, or run the named stage or shepherd for an immediate check. With a poll interval of an hour or longer the default cap is shorter than two intervals and nothing is held; raise it to at least two intervals there. Old v3.1 records count as the first wait and run the build check once more. The all-stage --allow-merge tick passes over a lone held ticket for other stages and comes back only if none has work; a usage throttle ends it before it comes back (#54).
  • Stops and resume: closing a terminal, ssh session or tmux pane/session now stops the run with 130; detach tmux or use nohup to keep it running (#50). An inner group's stop or any child's 130 now keeps interrupted leases; on a queue lane they block every pick in its shared worktree with 21 until released. After the stop, run python3 scripts/bureau-runtime.py release RUN_ID again until it no longer reports “Background process group still alive”, then follow the preserve/push/drop-or-adopt steps in troubleshooting. status shows interrupted leases, not process liveness. Signal the runtime's lease pid for a manual stop, or a queue pane's whole group; signalling the supervisor's process alone leaves the stage running.
  • Log watchers: replace pushing the deferred commits of <branch> (…) with pushing N commit(s) of <branch> that origin lacks before the stage ends (<why>), and accept the success confirmation pushed <branch> (<label>): N commit(s) origin lacked, head <sha> (#46). Its labels are end of run, end of run, retry, provider exit X, the stage ends before its end-of-run push and the run's commits, without the hook's rewrite; an unreadable comparison reports an unknown count. A timed-out pass logs iter N: status=TIMEOUT … (timed out after Ss), and final 124 keeps the prefix Provider pass failed with exit 124 (iter N timed out) and no pass is left: …. Follow the tick's pass-over and come-back lines (#54), and the rework label --- Feedback to address (PRIORITY) --- (#53); the exact tick examples are in migration.
  • Also changed: the shepherd re-reads a moment-old intermediate Spec after a successful spec stage before bumping to Triage (#51), and long research digests, review decision text and upstream commit messages no longer fail through an early-exiting pipe (#56); neither needs a setting. #52 and #55 change tests only.

Restart queue loops and supervisors after the resync. A loop sources its configuration once at startup, and a stage already running keeps the old scripts because the installer replaces files atomically. Run doctor (python3 scripts/bureau-doctor.py --mode background), then qualify a representative ticket before dispatch resumes.

Already on the candidate. From v3.2.0-rc.1: select tag v3.2.0; no resync is needed, because runtime, installer, templates and tests are identical (the manifest keeps naming rc.1 as its source until the next resync).

Compatibility and rollback

Dependencies and platforms are unchanged (Python 3.9+, Bash 3.2+, Git 2.26+, jq, curl; Node.js 18+ for the shared scheduler; Linux and macOS). Configuration schema versions 1 and 2 stay supported, the new keys are optional, and the manifest stays at version 1. The exit codes keep their meanings; a queued check past its grace now uses 25, and a hang-up or child's 130 keeps interrupted leases. Git LFS installations need repo.remote_git_runs_hooks: true before using v3.2.0.

To roll back to v3.1.0, point the source at tag v3.1.0 and resync the scripts and interfaces scopes as one set, or restore the private backup (rollback). That restores v3.1's gaps: the three .env keys are exported to stage children, a branch's .env can steer a stage, remote hooks run with the GitHub tokens, a timeout ends implement at its first pass, failed passes can leave work only in the worktree, rework misses QA and BLOCK findings, and a waiting gate can hold the queue. v3.1's supervision helper does not accept v3.2's new gate-wait arguments, so do not mix script versions. Rollback cannot undo commits, pushes, pull requests, labels, comments or Linear transitions made in between, or release interrupted ownership; the caveats of v3.1.0 still apply.

Validation and known limitations

Live acceptance in the maintainer's pilot installation. The pilot installation was resynced to v3.2.0-rc.1: 29 files updated, 0 conflicts and doctor without error. One ticket went from Triage to Done with the shepherd in 44 minutes: spec 15.5 min, spec review 2 min, build 12 min in one pass, QA 7 min, build review 8 min with APPROVE and merge 27 s. The squash merge was pinned to the head the review checked. There was no timeout, no needs-human and no return to Triage after the spec stage; the run's leases were empty afterwards, and the end-of-run push printed its new confirmation line.

Every one of the eleven pull requests was checked by an independent verifier before its merge; #49 was checked by a security verifier and a Codex cross-check over three rounds. CI is green on ubuntu and macOS on the tagged commit of v3.2.0-rc.1 (14fc936). Release preparation changes documentation only; runtime, installer, templates and tests are identical to that candidate.

Known limitations:

  • Process environments. Linux /proc/<pid>/environ and macOS ps -E for non-Apple binaries show the environment a process started with; v3.2's stage children no longer hold the .env keys, but shell-only secrets and the GitHub token variables of the operator's shell remain in Bureau's non-branch processes, where a background branch process of the same user can read them (#49).
  • Git and gh. Remote git keeps the GitHub tokens for authentication; credential helpers, filters, fsmonitor and gh can still run code named by the git configuration with those tokens, and enabling repo.remote_git_runs_hooks restores hooks that see them (#49).
  • Same-user access. The main checkout's .env and .bureau.json, gh auth token and git credential helpers stay readable by the same user; the default removes only the Bureau secrets and GitHub token variables, an SSH agent, cloud credentials and registry tokens stay unless repo.untrusted_env is clean, the agent's login reaches what it runs, relative PATH entries are not checked, a secret of 6 or 7 characters can remove an unrelated variable containing it, and a secret shorter than 6 is removed only as a whole value (#49).
  • A script or doctor started by hand in a stage worktree without BUREAU_CONFIG can read the branch's .bureau.json and the .env next to it before the main checkout's; drivers and the runtime pass BUREAU_CONFIG (#49).
  • The .env* scan matches names, so a link under another name pointing at a .env file is not found, and doctor does not read an operator's global core.attributesFile when warning about Git LFS (#47, #49).
  • A gate can stay “not yet” without an alert for reasons the queued-check grace does not cover (a required human review, a hold label, a pending commit status, a deployment approval or a head whose commit time is in the future); while other tickets wait the queues recheck about once an hour with the defaults, and the shepherd remains bounded by its wait budget (#48).
  • The comment cap can leave a code fence open when it cuts inside a code block (cosmetic; the gate reads the header).
  • A background writer slower than the 2 s settle window after repo.post_implement_command can still be blamed on the hook.
  • A branch cut down to exactly a shorter sibling's slug takes that sibling; without a bureau-branch marker Linear's generated branch name can resolve to a parent ticket's directory, and a markerless ticket whose directory is on main and named by feature.json is held as stale when speckit-specify records the same value again (post the marker and remove needs-human to release it).
  • The stages and the hold flush still write the literal needs-human label; a configured name is honoured by the picker, the in-flight count and the shepherd.
  • A pull request that no workflow runs for. The scaffolded ci.yml has paths-ignore: ['**.md', 'specs/**'], so a Markdown/spec-only PR gets no check run and an automatic merge is blocked after the 1800 s CI start grace; add a workflow that always reports a check, raise agents.merge_ci_start_grace_seconds or merge by hand, since doctor reads the checkout's on: blocks line by line and does not see paths-ignore.
  • A worktree left by an interrupted run before v3.1.0-rc.2 carries no record of its run; the first ticket that meets it gets needs-human and the halt comment, even if another ticket left it (see the earlier upgrade steps).
  • Carried over from v3.0.x: manual merging does not move Merge to Done, a manual repository without a Merge state refuses review with 24 and re-picks each tick, the review build check uses three steps rather than QA's further fallbacks, Claude co-authored commits count as bureau commits for rebase conflict resolution, and a linked virtualenv is the main checkout's own and is shared by all stage worktrees.
  • A run that halts with exit 21 on a clean worktree equal to origin still needs needs-human and a manual resume.
  • A BLOCK is not counted as a review cycle, so after a restart from build the review specialists are not told they see the code a second time.
  • The runtime's printed resume step 1 still names status as the liveness check; the documentation says to run release again until it no longer reports a live process group.
  • On git 2.54 only, a configuration-defined hook added between Bureau's discovery and its push, or one that appears only during a clone or pull, is not switched off (needs a second process of the same user).
  • Branch code runs as the same operating-system user: it can read the operator's files and can write .git/config to name a command Bureau's later push runs (see SECURITY.md); isolate with separate users or containers where that matters.
  • During a usage throttle, a held Merge ticket the bounded tick passed over waits for its hold (at most agents.merge_gate_recheck_seconds); a DIRTY held Merge ticket is never rebased by an --allow-merge tick (as in v3.1), and the queue loop still rebases it.
  • The early-exit pipe scan in tests/test_pipe_early_exit.sh does not cover shell inside templates/workflows YAML or readers behind timeout, xargs or a while-read loop.
  • A question the spec stage leaves open for the maintainer does not stop the stage; an answer posted later reaches spec review, not the plan.
  • The shell tests still use git's default automatic maintenance, so detached repacks can race their temporary-repository cleanups (#52).
