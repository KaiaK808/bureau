Bureau v3.1.0-rc.2 — a way back after an interrupted run

Release candidate · 2026-09-30 · source tag v3.1.0-rc.2. The GitHub Release is marked as a prerelease and records the exact tagged commit. The stable release remains v3.0.2 until v3.1.0 is published. The previous candidate is v3.1.0-rc.1, which describes the six pull requests of v3.1; earlier releases: v3.0.1, v3.0.0 and the previous major release v2.0.0.

rc.2 carries what the live acceptance of rc.1 found. The exit codes keep their meaning: a halt with 21 now also sets needs-human and comments on the ticket, bureau-worker.sh ends with 130 on SIGTERM or Ctrl-C, and shepherd.sh ends with 1 when --worktree names the main checkout.

The rc.1 acceptance

The maintainer's pilot installation was resynced to rc.1. One ticket went from Triage to Done with the shepherd in 54 minutes; the merge was pinned to the head the gate checked, and the review comment carried the merger's findings. Before that run, a first run was interrupted by SIGTERM and ended with 130, and its resume stopped with exit 21 ("refusing to reset unregistered worktree"). Those two runs showed the gaps below; nothing else from the acceptance needed a change.

What changed since rc.1

All in #41.

  • A way back after an interrupted run.
    • The wrapper that claimed the run prints the steps once, with the actual run ID, ticket, worktree and branch: release the run (python3 scripts/bureau-runtime.py release RUN_ID), then save what is wanted and drop the preserved worktree, or keep it and rerun with a new --worktree, then rerun. It used to say only "work preserved; inspect processes and explicitly release ownership", three times, and releasing alone ended the rerun in exit 21, because the interrupt removes the worktree's disposable-worker registration.
    • The branch steps keep unpushed work: a branch is deleted only when it was never pushed and has no commits of its own; commits on no remote or not on origin are pushed first, a never-pushed branch is then kept as <branch>-saved so the rerun can create it again, and a branch origin has is left to the rerun's git checkout -B. The main checkout, a missing worktree and a directory Git does not know as a worktree are never offered for removal.
    • bureau-worker.sh traps SIGTERM and Ctrl-C and ends with 130, keeping the worktree on the branch it was building. Untrapped, bash handed its cleanup $? = 0, which took the cancelled stage for a finished one and detached the worktree from that branch.
    • Nested stop graces: each runtime wrapper waits one step longer than the one inside it before it kills its child's process group (20, 15, 10, 5 s; BUREAU_STOP_GRACE_SECONDS sets the step, default 5). With one 5 s grace everywhere, the worker's runtime killed the stage's runtime before that one killed a stage that ignored the signal, and the stage ran on.
    • Troubleshooting describes the procedure.
  • A halt with exit 21 leaves a trace. A claim that an interrupted run or a run whose process is gone still holds, and the reset's refusal of an unregistered worktree, a registered worker that now holds another repository, a branch checked out in another worktree or a lost claim, now set needs-human (with the local hold when the label cannot be written) and post one comment that names the worktree and the way back; stderr carries the same steps. The ticket used to stay in its state with nothing on it, and a queue picked it again on every tick. When a worker loses its registration, <git common dir>/bureau/preserved/<key>.json records the run and ticket, so the halt goes to that ticket; a repeat sets the label again but posts no second comment (bureau/ownership-halts/). A live holder and a cancelled run write nothing. shepherd.sh --worktree . (or the main checkout's path) now ends with 1 before it claims anything.
  • The merge line names the pinned head: "Merging PR #N (squash) at …" is printed where gh pr merge --match-head-commit runs, after the just-in-time gate and the stop check; the review stage's inline merge prints the same line.
  • The review log says when it shows only the end of the build output: "Build output: last 20 of N lines" before the tail of a longer output, so trailing "running 0 tests" doc-test summaries no longer read as a run without tests.

See the changelog for the full entries and the exit codes for 21.

Upgrade an existing installation

From v3.1.0-rc.1: select tag v3.1.0-rc.2 in the source skill checkout and resync the scripts scope as one set (bureau-runtime.py, bureau-config.sh, bureau-worker.sh, shepherd.sh, merge-pipeline.sh and code-review-pipeline.sh changed). No configuration or interface change is required.

From v3.0.2, v3.0.1, v3.0.0 or v3.0.0-rc.2: select tag v3.1.0-rc.2 and resync the scripts scope and the interfaces scope as one set, then go through the checklist of the v3.1.0-rc.1 notes, also in Upgrade to v3.1: secrets no longer reach branch code, .env* entries in repo.worktree_links, the one-hour default timeout, false gate switches, the blocked gate for a repository without CI, the review stage's 2 and 25, shepherd holds, the moved alert throttle file, legacy markers in instruction files, the spec stage's 11, the post-implement hook's 14, and local variants.

In both cases, before dispatch resumes:

  • Leftover worktrees. List the worktrees an earlier interrupted or unfinished run left behind (git worktree list, python3 scripts/bureau-runtime.py status) and drop or adopt them. They carry no record of their run, so the first ticket whose stage meets one gets needs-human and the halt comment, even when another ticket's run left it. A run interrupted before the upgrade still holds its leases; release it with python3 scripts/bureau-runtime.py release RUN_ID.
  • Leftover branches. The old cleanup detached such a worktree from its branch, so the steps cannot name the stage's leftover local branch, and a spec rerun then stops with fatal: a branch named '…' already exists. After dropping the worktree, list the local branches origin does not have with git for-each-ref --format='%(refname:short)' refs/heads | while read -r b; do git rev-parse -q --verify "refs/remotes/origin/$b" >/dev/null || echo "$b"; done, check that the stage's branch carries nothing you need (git log --oneline BRANCH --not --remotes prints nothing) and delete it with git branch -D BRANCH, or keep it under another name (git branch -m BRANCH BRANCH-saved) so the rerun can create the branch again.
  • Wrappers: a wrapper that reads bureau-worker.sh's exit code sees 130 after SIGTERM or Ctrl-C. A stop can take longer: each nested runtime wrapper waits one step longer than the one inside it before it kills its child's process group (20, 15, 10 and 5 s from the outside in, with the default step of 5 s); BUREAU_STOP_GRACE_SECONDS sets the step.
  • A shepherd started with --worktree set to the main checkout ends with 1; give it a worktree of its own.

Compatibility and rollback

Dependencies and platforms are unchanged (Python 3.9+, Bash 3.2+, Git 2.26+, jq, curl; Node.js 18+ for the shared scheduler; Linux and macOS). Configuration schema versions 1 and 2 stay supported, and the manifest stays at version 1. To roll back to rc.1, select tag v3.1.0-rc.1 and resync the scripts scope, or restore the private backup (rollback); rc.1 does not read the new records under <git common dir>/bureau/preserved/ and bureau/ownership-halts/. Rollback to v3.0.2 follows the v3.1.0-rc.1 notes. Rollback cannot undo commits, pull requests, labels, comments or Linear transitions made in between.

Validation and known limitations

rc.2's changes are validated by the full Linux/macOS suite on the release commit, an independent verification pass with a fix round and a delta check of the fixes, and new tests on the real code paths with doubles only at the edges (Linear and Telegram, gh, the reviewers, a probe for the spec stage's provider work, entered through the real bureau_stage_enter so that a shepherd run nests three runtime wrappers as in the pilot). tests/test_interrupted_run_resume.sh and tests/test_ownership_halt_trace.sh run the printed steps as printed and resume the ticket to Done; tests/test_interrupt_grace.sh interrupts a stage that ignores SIGTERM ten times and finds nothing left running. All new test files fail against rc.1's code (5184cf8), and 40 of 40 mutations were killed after the fix round. The changes of rc.1 are validated as its notes describe, and by the acceptance above.

rc.2's own changes have not run in an installation yet.

Known limitations of rc.1 that still apply:

  • Process environments. On Linux /proc/<pid>/environ, and on macOS ps -E for executables that are not Apple platform binaries (a Homebrew python3 or gh, node), show the environment a process started with. The processes a stage starts after it exported .env (its gh and jq calls, its Python helpers) hold the keys while they run, and the GitHub token variables of the operator's shell stay in the runtime and the stage shells. The ancestors of branch code start without the .env keys unless the shell that started the driver exported them itself. A branch process left running in the background can read them. Closing this needs the stages to stop exporting the keys.
  • Git commands that talk to a remote, and gh, keep the GitHub token variables: a branch pre-push hook (on a push) or reference-transaction hook (on a fetch or a push) and a credential helper see them.
  • Same-user access. The main checkout's .env and .bureau.json, gh auth token and git credential helpers stay readable by the same Unix user. The default removes only the Bureau secrets and the GitHub token variables (an SSH agent, cloud credentials and registry tokens stay unless repo.untrusted_env is clean), the agent's own login reaches what it runs, and relative PATH entries are not checked. bureau-supervision.py in the review stage runs without python3 -I (safe unless the operator's PYTHONPATH has an empty entry), and doctor does not scan linked directories for a .env (the stages do). A secret of 6 or 7 characters can also remove an unrelated variable that contains it. Closing the rest needs isolation at the operating-system level (a separate user, a container or a virtual machine), which Bureau does not provide.
  • A gate that stays "not yet". The queue picks the same ticket on every poll and reruns the review build check each time while the gate stays undecided (a queued check on an offline runner, a required human review, a hold label, a head whose commit time lies in the future); the shepherd is bounded by its wait budget. The CI start grace covers only a head with no check run at all: a check that is queued but never picked up by a runner still counts as pending.
  • The comment cap can leave a code fence open when it cuts inside a code block (cosmetic; the gate reads the header).
  • A background writer slower than the 2 s settle window after repo.post_implement_command can still be blamed on the hook. On the /goal path a failed run's own commits stay in the worktree in both push modes, as in v3.0.2.
  • A branch cut down to exactly a shorter sibling's slug now takes that sibling (the trade-off of the tie order). Without a bureau-branch marker, Linear's generated branch name can resolve to a parent ticket's directory, as in v3.0.1. A ticket without a marker whose own directory is on main and named by feature.json is held as stale when speckit-specify records the same value again; post the marker comment for that directory and remove needs-human to release it.
  • The stages and the hold flush still write the literal needs-human label; a configured name is honoured by the picker, the in-flight count and the shepherd.
  • A pull request that no workflow runs for. The scaffolded ci.yml has paths-ignore: ['**.md', 'specs/**'], so a pull request that changes only Markdown files and specs/** gets no check run. In a repository that merges automatically, its gate is blocked once the 1800 s CI start grace has passed. Add a workflow that always reports a check, raise agents.merge_ci_start_grace_seconds, or merge such a pull request by hand. Doctor does not warn about this: its workflow check reads the on: block line by line, not as YAML, does not see paths-ignore, and reads only the workflows of the checkout it runs in.
  • Carried over from v3.0.x: with merge_mode: "manual", nothing moves a ticket from Merge to Done after the merge by hand; a manual repository without a Merge state refuses code review with 24 and re-picks the same ticket every tick; the review build check uses three steps and not the QA stage's further fallbacks; commits co-authored by Claude count as bureau commits when deciding whether the rebase stage can resolve a conflict; a linked virtualenv is the main checkout's own and is shared by all stage worktrees.

New in rc.2:

  • A worktree that an interrupted run left before the upgrade carries no record of its run: the first ticket whose stage meets it gets needs-human and the halt comment, even when another ticket's run left it (see the upgrade steps above).
