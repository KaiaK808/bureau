Bureau v3.1.0-rc.1 — branch code without Bureau secrets, and the gaps the installations found

Release candidate · 2026-09-30 · source tag v3.1.0-rc.1. The GitHub Release is marked as a prerelease and records the exact tagged commit. The stable release remains v3.0.2 until v3.1.0 is published; v3.1.0 follows once a pilot installation has been resynced with this candidate and has qualified one ticket end to end. Earlier releases: v3.0.1, v3.0.0 with its candidates v3.0.0-rc.2 and v3.0.0-rc.1, and the previous major release v2.0.0.

v3.1 is a minor release on v3.0.2. It collects six pull requests of fixes, guards and opt-in settings found in the installations and in cross-checks of their pipelines. The exit codes keep their meaning and no code is new; some stages use existing codes in new places: the review stage ends with 2 or 25 when its inline merge does not go through; the spec stage ends with 11 on a missing or malformed .specify/feature.json (was jq's 2 or 5) and on a stale one; implement, spec review and UX set needs-human with their 13 when no spec directory matches; the shepherd ends with 25 before it claims a ticket a human holds; the queue picker and the in-flight count end with 27 on a Linear answer that lacks a list they read; a post-implement hook that edits an already-uncommitted file ends implement with 14; an unusable repo.untrusted_env value refuses before any branch code runs (24; 14 for a post-implement hook, 18 in upstream-port.sh).

What changed

  • Code a branch controls runs without the Bureau secrets (#33).
    • Since v3 the queue and the shepherd exported .env to every stage, so the review build check, the QA test runs, repo.post_implement_command, the Codex completion test, the app test action, the build and test of upstream-port.sh and the agent processes inherited LINEAR_API_KEY, TELEGRAM_BOT_TOKEN, TELEGRAM_ALERT_CHAT_ID and any GH_TOKEN or GITHUB_TOKEN of the shell that started Bureau. They now start through one helper (bureau_untrusted_env in bureau-env.sh, untrusted_env in bureau-provider.py): without those variables and GH_ENTERPRISE_TOKEN / GITHUB_ENTERPRISE_TOKEN, without any other variable that carries one of their values (6 characters or more anywhere inside, a shorter one only as the whole value), and without BASH_ENV and ENV. Everything else stays, so toolchain variables keep working. The stage keeps the keys for its own Linear, GitHub and Telegram calls.
    • Branch code that gets in through Bureau's own work gets no keys either. Bureau's git commands, and the hooks and filters they run, go through a git function without those variables (commands that talk to a remote keep the GitHub token variables for the credential helper and lose the .env keys), gh through a gh function that removes the .env keys and keeps the GitHub token variables it logs in with, and the git and gh processes Bureau's Python starts through process_env. Inline Python runs with python3 -I, so a subprocess.py in the branch root cannot stand in for the standard library. The provider starts without the keys and the runtime wrapper without the .env keys, and the Linear and Telegram requests hand the key, the bot token, the chat id and the alert text to curl on stdin instead of its argument list.
    • QA and upstream-port.sh run their commands in a child bash --noprofile --norc -o pipefail -c, as the review build check does; QA used eval in the stage shell. A command no longer sees the stage's unexported variables and functions or its set -u.
    • The stages skip a repo.worktree_links entry with a .env* path component or whose fully resolved path in the main checkout passes through a .env* name (both reported as an error by doctor), and also a directory with a .env* name anywhere below it or whose search for one does not finish, which doctor does not check.
    • Opt-in repo.untrusted_env: "clean" runs the same commands in an allow-list environment of base variables; an agent also keeps its own login and network variables.
    • What stays readable for code that deliberately looks for the keys as the same Unix user is listed in SECURITY.md and under the known limitations below.
  • Review and merge outcomes (#38).
    • With the merge agent off and agents.merge_mode auto, the review stage's inline merge ended with 0 whether it merged or not, and the review reported Done. The review stage now follows the merge stage's codes: after a merge the ticket is Done; when the gate is not yet decided it records the APPROVE, comments once and ends with 2, and the next pick reuses the approval without a model call and merges once the gate passes; when the gate is blocked it sets needs-human, comments the gate lines and ends with 25, and after a human clears the blocker the next run reuses the approval. The shepherd waits on the review stage's "not yet" as it does at Merge.
    • agents.merge_require_green_ci: false and agents.merge_require_up_to_date: false switch their gates off; the gate read false as true. A quoted "false", which v3.0.2 read as off and so merged on red CI, keeps the gate on with a warning.
    • A PR head with no check run and no commit status is blocked once its commit is older than the new agents.merge_ci_start_grace_seconds (default 1800): a repository without CI no longer waits silently for ever.
    • agents.merge_min_required_checks and agents.merge_ci_start_grace_seconds follow one number rule in the gate and in doctor. v3.0.2 merged a head without any check when the minimum was -1 or a word such as "abc".
    • Every merge call passes --match-head-commit with the head the gate checked. A push between the gate and the merge makes the merge stage end with 2; the next run judges the new head.
    • The review merger returns a markdown comment and a findings list (bureau-review.schema.json), and the stage posts them with the verdict on the PR and in the Linear REQUEST_CHANGES and BLOCK comments, so the specialists' file:line findings reach the implementer and the human merger. The verdict is still decided from the object by the same ordered rules.
    • Linear and GitHub comments are fitted to 60,000 bytes (beginning and end kept, the verdict block kept whole), so one long model answer no longer halts a stage with 27.
  • Implement loop (#37).
    • The squash-range check for CI-skip markers also runs after every iteration, so a marker stops the loop after the iteration that wrote it instead of after the remaining paid iterations.
    • New agents.implement.push_each_iteration (default true, today's behaviour): with false, implement does not push after each iteration while a PR was already open when the run started, so a review round starts one CI run instead of one per iteration. A stage that ends before its end-of-run push pushes the deferred commits first, once and best effort (a provider that fails, times out or is interrupted, an unusable Linear, a crash, SIGTERM or SIGHUP); only a process killed outright leaves them in its worktree.
    • A repo.post_implement_command that changes an already-uncommitted file without committing it now halts with 14, like any other change it leaves behind.
  • Spec directory handling (#36).
    • Implement, spec review and UX set needs-human when no spec directory matches the branch; they routed the ticket back without a label, where it stayed.
    • The spec stage ends with 11 when .specify/feature.json is missing or malformed after speckit-specify (it ended with jq's 2, which the queue and the shepherd read as "queue empty", or 5), and it refuses a stale file (unchanged by the call, naming a directory that existed before and is not the ticket's own) with 11 and needs-human before plan and tasks.
    • Among several fitting spec directories, after the branch number, the one whose slug equals the branch slug wins; only two or more left are a tie. Every answer v3.0.2 gave stays; only former ties can become a pick.
    • The bureau-branch marker readers skip comments whose body is empty or null.
    • /linear-implement (the Claude command and the Codex skill) finds the spec directory with the shared matcher.
  • Operator guards (#35).
    • The shepherd refuses a ticket a human holds (needs-human, the configured linear.labels.needs_human.name, blocked, wip or a local hold) before it claims it: exit 25, nothing written. Without --from-stage, a hold left on a ticket that is already Done or cancelled does not stop a run or a chain.
    • Alert throttling is per repository (<git common dir>/bureau/alert-throttle.log, overridable with BUREAU_ALERT_THROTTLE_FILE), and every alert names its repository in a Repo: line.
    • A dry run writes no escalation record.
    • The queue picker and the in-flight count stop with 27 on a Linear answer that lacks a list they read; the count leaves out a ticket parked by the configured needs-human name.
  • Doctor, defaults and installer (#34).
    • The provider's default timeout per call is 3600 s instead of 900 s; doctor warns when an enabled spec, spec review, UX, QA or review stage gets less than 1800 s.
    • Doctor warns when automatic merging needs CI checks that no workflow provides, and when a merge gate switch or agents.implement.push_each_iteration is not a JSON boolean; it rejects .env* entries in repo.worktree_links and judges that list in the main checkout, also from a linked worktree.
    • The installer treats every form of the legacy bureau-init managed marker as a conflict that names the line, and it skips template files the source ignores (listed under skipped).
    • The managed block in CLAUDE.md and AGENTS.md describes the three merge routes of agents.merge_mode.

See the changelog for the full entries, configuration for the new keys, exit codes for the vocabulary and troubleshooting for the new refusals.

Upgrade an existing installation

From v3.0.2, v3.0.1, v3.0.0 or v3.0.0-rc.2: select tag v3.1.0-rc.1 in the source skill checkout and resync the scripts scope and the interfaces scope as one set (--resync-interfaces --resync-scripts). The scripts belong together (among them bureau-env.sh, bureau-config.sh, the stage scripts, shepherd.sh, bureau-worker.sh, codex-stage-runner.sh, bureau-provider.py, bureau-supervision.py, bureau-doctor.py, bureau-review.schema.json); the interfaces carry /linear-implement with the shared matcher and the managed block's corrected merge sentence. A locally edited copy stops the resync until it is merged by hand. From v3.0.1 or older, the upgrade notes of the releases in between apply as well (Upgrade to v3); from v3.0.0-rc.1, v2.0.0 or a legacy copy, follow that section first.

Check these before dispatch resumes:

  • Secrets no longer reach branch code. A test command, hook, repo.post_implement_command or agent step that needed LINEAR_API_KEY, TELEGRAM_BOT_TOKEN, TELEGRAM_ALERT_CHAT_ID, GH_TOKEN, GITHUB_TOKEN (or an enterprise variant) or BASH_ENV in its environment must get it another way; gh in a test still finds its stored login. QA's test command runs in a child bash: no stage-shell variables or functions, no set -u. A Git LFS checkout that authenticates only through GH_TOKEN in the environment no longer gets it during checkout and reset; use gh's stored login or a credential helper. Scripts of an installation that source bureau-env.sh or bureau-config.sh get the git function too.
  • repo.worktree_links: remove .env* entries and directories that hold a .env. The stages skip both; doctor reports a .env* entry as an error and does not look inside linked directories.
  • Stage timeout: stage calls that 900 s used to cut off now run for up to an hour. Set agents.<stage>.timeout_seconds or agents.providers.<provider>.timeout_seconds explicitly where the shorter limit was wanted.
  • Merge gate switches: agents.merge_require_green_ci: false and agents.merge_require_up_to_date: false now switch their gates off; check that each false in .bureau.json is meant. A quoted "false" keeps the gate on.
  • Repositories without CI: an installation that merges automatically and gets no check run on the PR head now sees a blocked gate 1800 s after the head commit instead of a silent wait: the queue loop alerts (hourly per ticket), and the shepherd and the review stage's inline merge halt with 25 and needs-human. Set agents.merge_require_green_ci to false there, or raise agents.merge_ci_start_grace_seconds for a slow runner.
  • Gate numbers: a merge_min_required_checks or merge_ci_start_grace_seconds written as a string of digits now counts as that number, a negative one or a word as the default; doctor names the number the gate uses.
  • Review stage exit codes: wrappers that run the review stage must accept 2 (approved, merge gate not yet decided; run it again later) and 25, as they already do from the merge stage; bureau-tick.sh reports them as waiting and blocked. A local review prompt or schema that removes comment or findings makes the merger's answer fail with 22.
  • Shepherd holds: a shepherd run or an orchestrated chain that used to drive a held ticket now stops with 25 before its claim; release the hold and re-shepherd. Each run makes one more Linear read before its claim.
  • Alert throttle file: the log moves from /tmp/bureau-alerts.log to <git common dir>/bureau/alert-throttle.log. Expect at most one repeated alert per key right after the upgrade; delete the old file once every installation on the host runs v3.1.
  • Instruction files: a CLAUDE.md or AGENTS.md that still holds a legacy bureau-init managed marker stops the resync until its old section is delimited with bureau-init:begin/end or removed (see troubleshooting).
  • Spec stage: a wrapper that read the spec stage's 2 or 5 after a failed specify sees 11. In installations that track .specify/feature.json on main, check that speckit-specify records each new feature; a stale file now stops the spec stage with needs-human. Tickets that earlier no-match stops parked in Spec without the label keep their state; nothing picks a ticket in Spec, so look for them and route them by hand.
  • Post-implement hook: a hook that edits an already-uncommitted file without committing it now halts implement with 14; make it commit what it changes.
  • Also changed: a CI-skip marker in a commit now stops implement after the iteration that wrote it; the installer skips template files the source ignores and names them under skipped; alerts carry a Repo: line; escalation records that earlier dry runs wrote are not removed.
  • Local variants: an installation that carries its own copy of the deferred push or of the secret hardening drops it with the resync, together with any strict xfail tests that waited for the deferred push (they now pass, and a strict XPASS fails the suite).

Optional: to defer implement's pushes while a PR is open, make agents.implement an object, "implement": {"enabled": true, "push_each_iteration": false}. To run branch code in an allow-list environment, set "untrusted_env": "clean" under repo after checking that repo.test_command and repo.post_implement_command run with only those variables; a test command then also loses an SSH agent, cloud credentials, registry tokens, the proxy variables and a private CA, and an agent that logs in through cloud credentials cannot start.

Run doctor after the resync (python3 scripts/bureau-doctor.py --mode background), then qualify one ticket end to end with the shepherd before dispatch resumes. See Upgrade to v3.1.

Compatibility and rollback

Dependencies and platforms are unchanged (Python 3.9+, Bash 3.2+, Git 2.26+, jq, curl; Node.js 18+ for the shared scheduler; Linux and macOS). Configuration schema versions 1 and 2 stay supported, the new keys are optional, and the manifest stays at version 1. To roll back to v3.0.2, point the source at tag v3.0.2 and resync the scripts and interfaces scopes, or restore the private backup (rollback). That brings back v3.0.2's behaviour with its gaps: branch code runs with the Bureau secrets in its environment, agents.merge_require_green_ci: false is read as true, the merge call is not pinned to the checked head, and the review stage reports Done after an inline merge that did not go through. Rollback cannot undo commits, pull requests or Linear transitions made in between; the caveats of v3.0.2 still apply.

Validation and known limitations

v3.1.0-rc.1 is validated by the full Linux/macOS suite on the release commit and the installer fixtures. Each of the six pull requests went through an independent verification pass, a fix round for its findings and a delta check of the fixes; #33 also went through three Codex cross-check rounds. The new tests run the real scripts with doubles only at the edges (Linear, GitHub, the models); each carries negative controls that fail against v3.0.2, and the new guards were mutation-checked:

  • #33: against v3.0.2 the new test files fail 276, 61 and 40 checks and the provider test 14 failures and 3 errors; the last mutation round killed 99 of 100, and the survivor is equivalent (the git commands of squash-marker-check.sh run no hook, filter or fsmonitor).
  • #38: 58 of 59 mutations killed in the first round (the survivor is equivalent), 24 of 24 and 16 of 16 in the fix rounds.
  • #37: 37 of 42 mutations killed; the five survivors change no outcome (a duplicated record, a batch replaced by per-path calls, a redundant pattern, a fallback for a configuration that already fails on load, symlinks passed to the batch).
  • #36: 41 of 41 mutations killed. The replay of 1,889 real branch/listing pairs from eight installations used for v3.0.2 gives the same answer as v3.0.2 in every pair (1,858 right, none wrong, no tie in either). Among 1,729 synthetic branch names built from the same directory names, 7 of the 56 ties became picks: 6 the intended directory, 1 the trade-off named below.
  • #35: 43 of 43 mutations killed.
  • #34: 60 of 60 mutations killed, plus 18 of 18 for its fix rounds.

No live ticket has run on v3.1.0-rc.1 yet. The pilot installation does not set push_each_iteration: false, so the deferred-push path rests on the harness tests.

Known limitations:

  • Process environments. On Linux /proc/<pid>/environ, and on macOS ps -E for executables that are not Apple platform binaries (a Homebrew python3 or gh, node), show the environment a process started with. The processes a stage starts after it exported .env (its gh and jq calls, its Python helpers) hold the keys while they run, and the GitHub token variables of the operator's shell stay in the runtime and the stage shells. The ancestors of branch code start without the .env keys unless the shell that started the driver exported them itself. A branch process left running in the background can read them. Closing this needs the stages to stop exporting the keys.
  • Git commands that talk to a remote, and gh, keep the GitHub token variables: a branch pre-push hook (on a push) or reference-transaction hook (on a fetch or a push) and a credential helper see them.
  • Same-user access. The main checkout's .env and .bureau.json, gh auth token and git credential helpers stay readable by the same Unix user. The default removes only the Bureau secrets and the GitHub token variables (an SSH agent, cloud credentials and registry tokens stay unless repo.untrusted_env is clean), the agent's own login reaches what it runs, and relative PATH entries are not checked. bureau-supervision.py in the review stage runs without python3 -I (safe unless the operator's PYTHONPATH has an empty entry), and doctor does not scan linked directories for a .env (the stages do). A secret of 6 or 7 characters can also remove an unrelated variable that contains it. Closing the rest needs isolation at the operating-system level (a separate user, a container or a virtual machine), which Bureau does not provide.
  • A gate that stays "not yet". The queue picks the same ticket on every poll and reruns the review build check each time while the gate stays undecided (a queued check on an offline runner, a required human review, a hold label, a head whose commit time lies in the future); the shepherd is bounded by its wait budget. The CI start grace covers only a head with no check run at all: a check that is queued but never picked up by a runner still counts as pending.
  • The comment cap can leave a code fence open when it cuts inside a code block (cosmetic; the gate reads the header).
  • A background writer slower than the 2 s settle window after repo.post_implement_command can still be blamed on the hook. On the /goal path a failed run's own commits stay in the worktree in both push modes, as in v3.0.2.
  • A branch cut down to exactly a shorter sibling's slug now takes that sibling (the trade-off of the tie order). Without a bureau-branch marker, Linear's generated branch name can resolve to a parent ticket's directory, as in v3.0.1. A ticket without a marker whose own directory is on main and named by feature.json is held as stale when speckit-specify records the same value again; post the marker comment for that directory and remove needs-human to release it.
  • The stages and the hold flush still write the literal needs-human label; a configured name is honoured by the picker, the in-flight count and the shepherd.
  • A pull request that no workflow runs for. The scaffolded ci.yml has paths-ignore: ['**.md', 'specs/**'], so a pull request that changes only Markdown files and specs/** gets no check run. In a repository that merges automatically, its gate is blocked once the 1800 s CI start grace has passed. Add a workflow that always reports a check, raise agents.merge_ci_start_grace_seconds, or merge such a pull request by hand. Doctor does not warn about this: its workflow check reads the on: block line by line, not as YAML, does not see paths-ignore, and reads only the workflows of the checkout it runs in.
  • Carried over from v3.0.x: with merge_mode: "manual", nothing moves a ticket from Merge to Done after the merge by hand; a manual repository without a Merge state refuses code review with 24 and re-picks the same ticket every tick; the review build check uses three steps and not the QA stage's further fallbacks; commits co-authored by Claude count as bureau commits when deciding whether the rebase stage can resolve a conflict; a linked virtualenv is the main checkout's own and is shared by all stage worktrees.
