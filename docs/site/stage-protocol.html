Shared stage execution and ownership

Bureau supports two workspace modes. App work uses the current checkout through python3 scripts/bureau-runtime.py; background scripts run through bureau-worker.sh in explicitly registered disposable worktrees. Direct background stage execution in a user checkout is refused. These controls do not bypass Codex permissions for the checkout or shared Git directory.

The shared Git directory stores bureau/leases.json, run records and disposable-worker registration. Claims cover both issue ID and canonical checkout path, using an OS file lock around updates. An app and a worker cannot own the same local issue or checkout concurrently. A worker releases its own branch after a stage. Held branches in other worktrees cause exit 21 rather than detaching the owner. Existing .worktrees/ directories are not implicitly disposable; inspect and retire or hand off an old worker before starting a new registered one.

App stages

python3 scripts/bureau-runtime.py status
python3 scripts/bureau-runtime.py prepare TEAM-123 implement --owner app-task
# Follow scripts/bureau-stage.md in the current task and write result.json.
python3 scripts/bureau-runtime.py finish RUN_ID --result result.json

The prepare response records issue/state identity, configuration hash, current HEAD, branch, canonical marker and project context. Attach an existing canonical branch before preparing. Finish requires a matching run/stage, live ownership, current result HEAD, unchanged configuration and unchanged issue state. The branch and canonical marker must still agree; review additionally requires the prepared HEAD. Complete spec work needs spec/plan/tasks artifacts in the prepared issue’s canonical feature folder under specs_dir; spec-review must validate that same feature’s spec.md. Prepare binds an existing canonical branch/directory; a newly created app feature must match its issue key and any number reservation. A valid spec from another ticket cannot complete the run; implementation/QA need successful test evidence. Partial/blocked results retain the current Linear state and save their explanation. Blocked outcomes and BLOCK reviews also apply the configured needs-human label before releasing ownership; every background queue excludes that label. A label failure keeps the run pending for retry. Resolve the blocker and explicitly remove its label before resuming background processing. Completion posts the canonical branch marker and a run marker, then moves to the configured state UUID. Repeating the identical result is idempotent, including recovery after a successful state move interrupted before local completion. Once finish records its pending result, retries must use that exact result and target state. Spec-review routing reads current configured labels at finish, including labels added during review. App REQUEST_CHANGES comments are consumed by the background implementation loop.

For resume, inspect status --run RUN_ID, the actual branch/diff and current Linear state. Continue unfinished work using its run ID. If the state/configuration/head makes the result stale, preserve the work, release the old run, and prepare a fresh stage after reconciling the change. release RUN_ID refuses a live background PID or a recorded live process group. An interrupted background run retains its issue/workspace claims and loses disposable-worker registration, even if its immediate shell already exited. Inspect the saved work and the process-group record at <shared-git-dir>/bureau/processes/RUN_ID.json, verify current process identities, stop any remaining writers, then release the run explicitly. The preserved checkout remains unregistered: adopt it for app recovery or explicitly retire it before creating another disposable worker. The interrupt message prints these steps with the run ID, the worktree and its unpushed local branch; a background rerun that meets the held claim or the unregistered worktree stops with 21 (except a checkout with an explicit former-worker failure note that a non-spec stage can reset without loss: clean, and HEAD on the fetched origin/<branch>, which the reset registers again) and leaves needs-human and one comment with the same steps on the ticket. Process inspection failures and reused live group IDs fail closed; do not kill a process solely because an old record mentions its ID. After a machine crash, inspect the old run before releasing it; app leases have no implicit expiry. This is local coordination, not a distributed lock or an atomic Linear compare-and-swap across hosts.

Spec phase resume and governance

Specify and plan must run no measurements, probes, benchmarks or full test-gate runs. Use existing evidence and leave unknowns for implementation/QA. Bureau supplies this rule and the governance requirement through prompts, managed instructions and commands; it preserves customized .specify/templates, the constitution and Spec Kit 1.2.2 helpers.

Every spec requires a section headed Governance and security, containing an explicit decision and rationale explaining applicability. Bureau prompts use Decision: and Rationale: fields; an existing explicit sentence such as "Not required because this changes only static documentation" also qualifies. For example:

## Governance and security
Decision: not required
Rationale: This documentation change processes no credentials or personal data.

In spec.md, place ## Governance and security with Decision: and Rationale: lines at column 0, before any code block, HTML block or front matter, in plain text.

The governance check catches common authoring mistakes using the following rules. It splits only LF and CRLF lines; other C0 controls (U+0000–U+001F except tab) and C1 controls (U+007F–U+009F) in the governance heading, decision or rationale are invalid. Content checks decode HTML entities, normalize Unicode NFKC and remove format characters (category Cf, including zero-width characters). Markdown heading syntax still requires a column-0 ATX heading with one to six ASCII # characters followed by an ASCII space; normalization does not turn a nonbreaking space after the hashes into valid syntax. A same-level or higher ATX heading ends the section, as does a setext underline (--- or ===, including longer runs) immediately after a text line; that preceding text cannot supply a field or rationale.

The first fence-like line is a permanent cutoff: after optional whitespace and any mix of list markers (-, *, +, or digits followed by . or )) and blockquote markers (>), three or more backticks or tildes end the scan, with no opener/closer matching or indentation bound. Marker whitespace is optional. The first line starting after optional spaces/tabs with < followed by an ASCII letter, ! or / is also a permanent cutoff, including a leading HTML comment. A leading YAML --- block is ignored through its closing ---; the validator can resume after that metadata, but an unclosed block contributes nothing. Other HTML comments are masked through --> or end of document, preserving physical lines and columns; their contents cannot supply fields or fence cutoffs. Governance after an earlier closed code or HTML block does not qualify.

Decision/rationale labels must start at column 0 without container prefixes. Values that start with a backtick code span, including values consisting entirely of a code span, are invalid. Rationale continuation lines may have zero to three spaces of indentation, but not four or more spaces or a leading tab (including spaces followed by a tab). A rationale must contain at least one letter or digit after normalization, and cannot be solely a placeholder, deferral or decision restatement. The same placeholder check applies to present Access/Logging/Retention fields. Examples rejected after normalization include TBD, TODO, N/A, a dash and an ellipsis, including fullwidth, entity-encoded or zero-width variants. Existing column-0 inline decision/explanation sentences and German or mixed Entscheidung:/Begründung: labels remain accepted. A justified not required or N/A is valid; there is no punctuation, verb or word-count requirement. Ordinary words such as “pending” or “wird definiert durch” inside a real explanation remain valid.

Known limits (governance check): the check targets honest mistakes by the spec agent; it is not a security boundary against deliberate obfuscation. Deliberate evasion, for example link reference titles, empty link labels or unusual Markdown or HTML constructs, is not guaranteed to be caught. Spec review remains responsible for judging whether the section is real and adequate, including applicability, circular or vague explanations and access/logging/retention risks.

Background spec review applies the shared check after permitted edits and forces REVIEW_STATUS=FAIL on a detected error; a model FAIL uses the same comment and route to Spec. Either failure invalidates from specify, so governance repair cannot resume at plan/tasks. App spec and spec_review completion require the prepared issue's spec.md and apply the same check before posting or moving; a detected error leaves the run prepared for repair. Passing this check does not replace substantive spec review. Existing specs may need this section added or moved before code blocks or HTML blocks.

Successful specify, plan and tasks phases each make one local commit of the reserved feature directory on its feature branch, named ISSUE: spec PHASE checkpoint with the Bureau-Generated: true trailer. Only completed phases receive checkpoints. The normal end-of-stage commit of remaining changes, single push, crosscheck, digest and routing still run; no per-phase pushes are added. Local commits and branch refs live in the shared Git directory and survive disposable-worker resets. Recovery on another clone/host still needs the commit to be available there; checkpoint metadata alone is insufficient.

Checkpoints share the evidence store, lock and atomic writer: <git common dir>/bureau/evidence/v1/spec-checkpoints/ISSUE.json. The evidence envelope stays schema_version: 1; spec records require checkpoint_version: 2 and record_type: spec_checkpoint. A record contains issue, repository-relative specs_dir and spec_directory, reserved branch and number, run_id, stage_attempt_id, input_sha256, updated_at and phases. Each phases.specify|plan|tasks contains commit (full Git object ID), completed_at, source run/attempt, input_sha256 and artifacts (feature-directory-relative path to SHA-256 map). Each artifact map covers the complete committed feature directory at that phase, so successful plan/tasks edits to earlier artifacts are included. Each phase requires its main artifact (spec.md, plan.md or tasks.md) to be nonempty. Fingerprints cover ticket title/description/project context, ordered review/human comment text and substantive research injected into specify. The latest published research stays input after its label is removed; publication, generated branch/digest, recovery and passed-review comments are bookkeeping.

The worker first obtains ordinary issue/workspace ownership and verifies disposable registration. It fetches origin, selects the last contiguous checkpoint reachable from the reserved local or origin branch, then checks out that branch at the recorded commit using the normal forced checkout, hard reset and clean -fdx. Uncommitted, staged, untracked and ignored leftovers are discarded. Hashes are recomputed from committed Git blobs, using the complete artifact snapshot recorded for each phase; file existence and a recorded commit ID alone cannot qualify a phase. A checkpoint never grants reset permission to an unregistered or user checkout. App preparation removes disposable registration and any former-worker failure note. Interrupted runs retain their existing explicit ownership recovery requirement. App stages use prepare/finish without disposable resets or automatic background phase checkpoints.

The spec stage revalidates the current input fingerprint and committed artifact maps before skipping a prefix. A plan timeout resumes at plan from the specify commit; a tasks timeout resumes at tasks from the plan commit. Changed inputs or failed spec review invalidate from specify. A missing, unreachable or tampered checkpoint truncates the valid prefix; no valid prefix means a fresh pass through all phases on the reserved branch. Published branch history is never rewound; a remote tip beyond the last phase checkpoint requires a fresh pass. Before specify/plan/tasks, the stage fast-forwards a stale local feature branch to the fetched origin tip, or creates a missing local branch at that tip. A local branch already ahead retains its commits. True divergence exits 25 before specify/plan/tasks, publishes a needs-human reason and requires a maintainer to reconcile both histories; the recovery trap returns the ticket to Triage and the needs-human label/hold excludes automatic picks. Bureau never force-pushes. The final stage commit is omitted when phase commits already include all changes. Changed reservations start fresh on their newly reserved branch. Incomplete phase edits never survive a retry. Checkpoints expire after 30 inactive days on evidence creation unless the issue has an active run; completed-run rotation is independent.

Checkpoint and observational evidence I/O failures warn and disable reuse for a fresh run under ordinary ownership/reset rules. Optional checkpoint reads and retention pruning are isolated per ticket, including during the real provider adapter's evidence initialization with reuse disabled. An unreadable or unprunable ticket record warns and marks only that ticket for fresh checkpoints; unrelated tickets and the provider's valid exit are unaffected. Directory enumeration and opt-out write failures also warn without aborting the provider. A separate durable opt-out at <git common dir>/bureau/spec-checkpoints-disabled/ISSUE.json prevents an old checkpoint from qualifying after a failed write or prune/read failure when the opt-out can be persisted; a successful fresh checkpoint initialization clears it. Commits still run when optional checkpoint storage is unavailable. Failed-review invalidation remains best-effort: FAIL publication and routing to Spec still run, and feedback changes the next fingerprint. Missing-tasks recovery still comments and moves to Spec with exit 13 even if invalidation fails. Provider completion receipts retain their separate persistence requirement before success is forwarded.

Adoption: resync scripts together, refresh interfaces for commands/instructions, reconcile local drift and restart drivers. No new configuration key, external exit code or Spec Kit change. Pre-v2 spec checkpoints are ignored with no inference/backfill from files; inspect old unregistered workers explicitly before reuse. Tests use fake providers/services and real local Git, including timeout/reset and mutation controls. Live provider and adopting-installation qualification remains outstanding.

Configuration and merge boundaries

BUREAU_CONFIG is an explicit path and is honored even from a linked worktree. Otherwise discovery checks the current root, primary checkout, and script installation root. setup copies ignored .bureau.json and .env from the discovered source into a new app worktree only when absent; existing files stay intact. Credentials remain local. Core operations use the direct API-key path for Linear state changes; available Linear tools can still serve interactive discovery.

BUREAU_NO_MERGE=1 applies to direct merge, review, queue and shepherd paths; queue/shepherd also accept --no-merge. Code review exits 20 after approval when the stop is requested. Otherwise inline merging delegates to the same gated merge pipeline used by the Merge worker, including when no Merge state is configured. The app prepare/finish protocol stops after review by default. Its --allow-merge option permits routing into a configured Merge queue; it never executes a merge itself.

New shell-generated commits carry Bureau-Generated: true. The ownership check still recognizes legacy Claude trailers/spec commits and merge commits. An unresolved Git reference fails the ownership check rather than counting as safe.

status is read-only. Shepherd's dry run describes a requested --from-stage without executing it and does not authenticate a model, claim an issue, or invoke a stage. Use these inspection paths before starting work.

Versioned background evidence

bureau-evidence.py owns a metadata-only evidence model (schema_version: 1) under <git common dir>/bureau/evidence/v1/, shared by linked worktrees. Background exec attempts to record a run and each nested worker/stage before preparation. Nested execution retains the outer run ID and gives every attempt a unique ID and parent ID. Parallel specialist calls have separate provider attempt IDs and phases (correctness, security, performance, verdict). App prepare/finish records retain their existing format and location.

Evidence is observational. Manifest/attempt, gate, PR pointer, wait and retention exceptions are caught at best-effort boundaries in startup and finalization; the tested failures preserve stage authorization, routing and ordinary exits. Python's optional warnings use unbuffered fd 2 writes and swallow write errors, leaving nothing to flush again at shutdown. Bash evidence and review-cleanup diagnostics run in protected subshells: a closed stderr reader can terminate that write with SIGPIPE without terminating the stage. Merge capture also protects the redirection itself, including diagnostics Bash emits when the destination cannot be opened. Closed-reader shell/routing and Python finalization fixtures cover exits 0, 14, 25 and 124, including unopenable merge capture in the production || true context. Invalid records from any ticket are isolated individually: when removal succeeds, quarantine retains only size, SHA-256 and observation time, with no copy of the bad bytes. Unreadable records are skipped. Python and the common Bash evidence wrapper cap warnings at once per process; merge capture and review cleanup have their own protected diagnostics. ENOSPC, permission errors and lock contention leave work running. Evidence locks wait at most 250 ms. waits itself is read-only and skips invalid records without quarantining them.

The sole mandatory evidence write is a receipt before forwarding a successful provider result. If that persistence fails, including when the protected store has no capacity for it, the adapter follows its existing error path and forwards no success. A receipt does not require a manifest or manifest link to succeed. Error/timeout/cancellation receipts, manifest links, pruning and provider diagnostic metadata are best effort; their failure preserves the original outcome.

Updates use an OS file lock and atomic replacement; JSON writes fsync the file and containing directory. New directories use 0700 and files 0600. This is local coordination, not a cross-host lock or tamper-proof audit trail.

Known limits: The tested failures do not cover every way storage or a process can fail. Abrupt termination, power loss, a filesystem that does not honor syncs, or unusual I/O errors while the interpreter shuts down may still lose evidence or change an exit. External edits and separate hosts are outside the store's lock. Sweep bounds require the documented clock, readable tickets and dispatcher cadence; stalled dispatchers, changing ticket sets and other restart patterns have no such bound. When selection switches between persisted order and fallback rotation, the rotation can start out of phase, so covering every ticket can take one sweep more than N (seen with six tickets at the default 30-minute cadence: seven sweeps).

Privacy contract

The shared store retains allowlisted identity/measurement fields and digests only. It contains no raw logs, excerpts, command text, ticket descriptions, specialist prose, review comments or structured-result free text. There is no excerpt option. Shell helpers still run through bureau_without_secrets, with Bureau-owned secrets and their carriers removed; because no source text is retained, privacy does not depend on finding every token pattern. Arbitrary phase/cause/actor/PR URL text cannot become a diagnostic text channel: phases and causes outside the vocabulary are digested, reasons are digested, actors use the supported vocabulary, and PR metadata keeps only the number.

Record Fields (version 1)
Receipt: runs/RUN_ID/receipts/PROVIDER_ATTEMPT_ID.json schema_version, record_type, run/provider/stage attempt IDs, issue, stage, phase, provider, schema SHA-256, normalized/provider exits, outcome, start/end HEAD, start/end times, original provider_logs and transcript pointers. structured_result is always null; result_sha256 is the SHA-256 of canonical structured JSON, or null when absent.
Manifest: runs/RUN_ID/manifest.json Run/issue identity, workspace pointer, start/end times, start/final HEAD, normalized exit, PR number, attempts.
Attempt in manifest Attempt/parent IDs, stage/phase, workspace pointer, start/end times and HEADs, normalized exit, relative receipt paths, gate metadata and PR number. Worker HEAD can be null before creation. The run's final HEAD follows its last completed worker/stage.
Gate/artifact metadata in attempt kind, checked head, end_head, command_id, command SHA-256, normalized exit, recorded time, full-stream byte count and SHA-256. IDs name the configured role (repo.test_command, review.build, qa.test, review.artifact, qa.summary, or configured-command); command text and filenames are not copied. Artifacts have null HEAD/exit and imply no gate pass.
Wait: waits/WAIT_ID.json Wait/issue/run IDs, cause key, kind, reason SHA-256, responsible actor, stage, exit, PR number and boundary generation when known, state, first reached/last observed/last checked times, resolved time, resolution observation time/basis and reached/resolved events.
Ticket: tickets/ISSUE.json Issue identity, first/last observation and terminal observation time.
Quarantine digest Record type, observation time, original size and SHA-256 only.

Timestamps are UTC Unix seconds. Missing HEADs and unknown event times are null, never inferred from commits. Gate streams and review artifacts are hashed before temporary directories/worktrees are cleaned, without retaining any source bytes. Provider prompt/output/transcript files remain in their existing locations, outside this store and its retention policy; the store only points at them. Those original files may contain private content and may disappear independently.

Receipt reconciliation requires the exact run, provider attempt, stage attempt, ticket, stage, phase, schema and current HEAD, and both exits must be zero. It reads the original provider result through its pointer, checks the full result digest and validates the schema again. A missing or changed original fails recovery; no free-text result is reconstructed from metadata, a prior receipt or Git history.

python3 scripts/bureau-runtime.py status --run RUN_ID
python3 scripts/bureau-runtime.py waits
python3 scripts/bureau-runtime.py waits --issue TEAM-123

status --run reads an app record when present, otherwise the background manifest. waits makes no service calls. Waiting seconds/share count overlapping intervals once over the retained local observation period, clipped to 30 days. Unknown ends use the first observation that the wait cleared: these are observed upper bounds, not exact historical lead-time metrics.

Waiting lifecycle and observation

Wait keys identify a cause independently of the run. mark_needs_human opens a typed wait before attempting publication, including failed publication/local holds. Exit 20 opens an approval decision; 21 opens an ownership/resource wait. Manual Merge records the approved PR and generation; automatic Merge opens a dependency wait for its worker. Gate waits belong to CI/gate owners or the repository maintainer. Supported kinds are decision, dependency, compliance, resource and technical; an exit code alone does not identify every cause.

Repeated refusals retain the wait ID, first reached time and reached event. Acquiring a lease does not resolve a preparation refusal: ownership closes only after successful stage/worker execution. Approval PR observations close only their matching boundary generation, after resume(expected=record) actually removes that boundary. Replacing a generation resolves its predecessor as an observed supersession; a stale PR cannot close the replacement or unrelated waits. An authoritative timestamp before the wait (or in the future) is rejected, leaving the wait open.

Each bounded tick and continuous queue iteration attempts up to four distinct tickets with open waits, even with manual merge and disabled merge/rebase agents. Only an attempted read advances its persisted cursor, including failures/timeouts; selection leaves unvisited cursors unchanged. Each attempted ticket updates its matching waits independently: a refused larger record does not stop a smaller writable cursor from advancing. Selection reserves room for the next timestamp's full encoding, then writes and reads back the oldest cursor unchanged to check persistence. When that succeeds, oldest persisted cursors take priority across fresh processes; rotation never overrides them. If the cursor cannot round-trip, a retained Python store uses in-memory attempt order and shell dispatchers pass their in-memory sweep count into each fresh Python invocation. Fresh shell ticks seed that fallback from the current time divided by the configured agents.poll_interval_minutes in seconds, so polls at that cadence advance one turn, including ordinary 30-minute polls. For a stable set of N readable open-wait tickets, an advancing clock and at least one read started per sweep, persisted cursors cover every ticket within N sweeps while selection stays on persisted order (see Known limits for the switch to fallback rotation); refused writes retain the same bound in a continuous dispatcher or fresh ticks at the configured cadence. Arbitrary restarts or other external polling cadences have no cross-process fallback bound. The pass has a shared 10-second network budget and performs no state, label or PR mutation and no provider work. A terminal Linear snapshot resolves only waits captured for that observation. For a PR-linked approval, a matching merged PR can close that approval even while the ticket remains at Merge. Concurrent boundary replacement is checked again after the remote read.

Without authoritative history, resolved_at and the resolved event's at remain null; only observation times are recorded. Linear completedAt/canceledAt, when supplied by its terminal snapshot, or GitHub mergedAt can supply an exact end. An unrelated old PR merge never establishes that a newer ticket wait ended. Clearing a hold after publishing its label does not itself resolve the human wait.

Retention and global limits

On writes, evictable completed runs expire after 30 days or 128 completed runs. Resolved waits and inactive ticket observations expire after 30 days. Global storage additionally has a 16 MiB total byte cap and 4,096 file cap, covering manifests, receipts, waits, ticket records, spec checkpoints, quarantine digests and atomic staging leftovers (the empty lock file is excluded). A manifest includes its attempt/gate entries in this byte budget. Before allocation, a write reserves its full temporary size and one additional file slot, including unchanged/shrinking replacements. Failed cleanup attempts to discard the temporary payload; an undeletable .tmp remains an uncommitted file within that reservation and is never read as a record. Pruning retries its removal and also recognizes legacy staging names. Under capacity pressure, the oldest completed data is removed first; deleting a run removes its manifest and receipts together. Resolved waits, inactive observations and quarantine digests are also eligible by age.

Active/interrupted runs, open waits, and runs referenced by open waits are never evicted. When protected data leaves no staging capacity, optional writes (even unchanged replacements) skip with a warning; a success receipt that cannot fit fails persistence and prevents success forwarding. Any housekeeping exception, including an undeletable staging leftover, also leaves capacity unconfirmed: optional writes skip and a mandatory success receipt fails closed. These reservations prevent writes from taking an in-budget store over its cap; an already oversized store containing protected or undeletable files still requires operator inspection. Provider originals are outside this cap; this is not a disk quota on provider transcripts. Waiting shares describe the retained observation window, not discarded history.
