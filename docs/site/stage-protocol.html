Shared stage execution and ownership

Bureau supports two workspace modes. App work uses the current checkout through python3 scripts/bureau-runtime.py; background scripts run through bureau-worker.sh in explicitly registered disposable worktrees. Direct background stage execution in a user checkout is refused. These controls do not bypass Codex permissions for the checkout or shared Git directory.

The shared Git directory stores bureau/leases.json, run records and disposable-worker registration. Claims cover both issue ID and canonical checkout path, using an OS file lock around updates. An app and a worker cannot own the same local issue or checkout concurrently. A worker releases its own branch after a stage. Held branches in other worktrees cause exit 21 rather than detaching the owner. Existing .worktrees/ directories are not implicitly disposable; inspect and retire or hand off an old worker before starting a new registered one.

Continuous ticket dispatch

Dispatch requires the literal JSON boolean agents.file_overlap_gate: true; absent, false and invalid values refuse startup with 24 before selection or work. This requirement applies to one lane and dry-run as well. Enable the gate only after comparing installed-script drift and resyncing every writer together.

python3 -I scripts/bureau-dispatch.py run refills agents.parallel_lanes owned ticket lanes (default 2), draining downstream work before Triage through pipeline_pick_next/pick_issue. Both tmux launchers start one queue-loop-supervised.sh dispatch pool, replacing their stage pollers. bureau/dispatch.lock in the common Git directory excludes competing dispatchers and legacy queue-loop.sh pollers. Lane runtime wrappers retain the lock descriptor until they finish, including after loss of their dispatcher parent. Stop existing pollers before starting the new launcher. Standalone shepherd and explicit batch execution remain separate operations. Each lane runs shepherd.sh --no-tmux --respect-config --worktree … through the trusted runtime with a fresh run identity and unique attempt worktree. Shepherd enforces stage toggles at every dispatch boundary; disabled stages hand off with 20.

Pause, strict ticket eligibility, human holds, ownership and one-shot usage are rechecked before launch; runtime overlap admission precedes ownership/reset. A launch-specific bureau/dispatch-ready/ marker settles first-stage admission before the next startup snapshot; a marker write failure retains ownership and serialized startup. Complete admission snapshots that move while being checked retry through the same gate up to three times in dispatcher mode; transport, shape and ownership failures retain their codes, and withdrawal wins on every attempt. Capacity (28), overlap (29), quota (23), transient Linear/authentication waits and merge-gate 2 yield lanes. Completion refills immediately; idle arrivals use agents.poll_interval_minutes (--poll-seconds overrides the interval for a direct invocation). run --dry-run (also via queue/supervisor --dry-run) prints one candidate and exits without a lane or skip-store mutation; --no-merge remains a caller boundary. Waiting adds no paid round. bureau/dispatch-skips.json persists retry deadlines and permanent holds. A 25, including unlabeled silence escalation, cannot be immediately repicked; intentional handoffs, terminal tickets and unknown failures also stay skipped across restart. To resume after reconciliation, stop the dispatcher and remove that ticket's JSON entry, clearing any human hold as well. A 25 explicitly identified by the preflight pause acknowledgment or a lane-specific .paused marker defers until unpause instead; a concurrent human 25 remains held.

bureau/spec-admissions.guard serializes Spec count/reservation/move. bureau/spec-admissions.json counts pending moves absent from lagging Linear counts; observed in-flight tickets count once. Interrupted ownership retains reservations until reconciliation. agents.max_concurrent_issues and its manual-Merge counting policy remain separate from process lanes. Coordination data stays outside prunable evidence and is shared only by worktrees of the same Git repository.

Each launch first persists bureau/dispatch-lanes/ATTEMPT.json with its issue, stage and unique workspace. The outer runtime records its run identity and terminal exit there after nested cleanup, independently of the dispatcher. On restart, dispatch reconciles these records into dispatch-skips.json before selecting work; acknowledgment follows the skip write and uses the attempt identity to avoid duplicate backoff or alerts. An unfinished launch without a terminal outcome becomes a permanent interruption hold (130), requiring reconciliation. Lane-specific pause outcomes retain their retry behavior. Dry-run excludes unreconciled launches without acknowledging or changing their records. Reconciled launch records and readiness markers are removed; journal data carries no signalling authority.

Within a dispatcher-owned Merge worker, stale/DIRTY work may merge forward the fetched, pinned PR target through merge_origin_main_or_abort and the existing conflict transaction. Strict withdrawal checkpoints guard the normal push and return to Build Review. Gate-report refreshed/base_refresh metadata plus exit 20 makes shepherd continue to fresh review, including inline merge; a refresh grants neither merge success nor approval/gate reuse for the changed head. At most two refreshes run per lane; total review-round limits survive resumptions. Security/review/hold/thread blockers take precedence. Strict CI/base/JIT merge gates remain unchanged.

SIGTERM/SIGINT/SIGHUP stop admission, signal only live runtime handles launched by this dispatcher and join nested cleanup before releasing the lock (130). Stored PIDs and process-name scans are never signal targets. Interrupted leases and unfinished work survive; only clean, detached, identity-matching registered workers can be removed. The supervisor waits for dispatcher cleanup. Resync the complete scripts scope and restart launchers together; mixed older writers, separate clones/hosts and live provider CLI qualification remain outside local fake-service validation.

Cancellation received while constructing the dispatcher is carried into its run handlers before selection. After dispatcher loss, supervisor exit 21 enters bureau-dispatch.py wait: it waits cancellably for the actual lock holder, consumes no crash retries and resumes dispatch when the lock becomes available. Cancelling this wait stops only the supervisor's waiter, leaving inherited lanes to finish; the supervisor never adopts or signals a previous dispatcher's lanes.

Ticket budget and progress stops

bureau-ticket.py keeps authoritative per-ticket accounting in <common-git-dir>/bureau/tickets/ISSUE.json, with a per-ticket file lock, fsynced atomic replacement and private permissions. Every provider invocation reserves its provider_attempt_id with run/stage-attempt/stage/phase identity before starting, then records usage and elapsed time even on failure. Checker/verifier invocations use the same path. Nested wrappers never double-count a call. The ledger survives worktree cleanup, reruns and optional evidence pruning, without historical backfill. See configuration and the progress contract.

An active ticket checks its cumulative budget and progress policy at each existing bureau_ticket_checkpoint. Confirmed withdrawal retains its existing exit before budget evaluation. Budget/stall exhaustion uses the same cooperative stop latch, ticket-control/RUN_ID/stop-25, and worker cleanup as withdrawal: no signals or state rollback, no new provider call or ordinary publication after the checkpoint, preserved dirty/ahead work with disposable registration removed, and ownership released after current writers finish. Parallel providers finish/join before their parent releases ownership. Existing best-effort preservation pushes remain allowed. Dispatcher persists a permanent 25 hold; standalone shepherd consumes the same latch at its existing boundaries.

Tokens/time may overshoot by calls already admitted at the safe point; call slots are serialized under the ticket lock. Missing usage stays null. With a token limit it stops as budget with usage_unknown: true, unless allow_unknown_usage is explicitly true; the known lower bound still applies. Unavailable/invalid mandatory accounting uses existing exit 24 and cannot authorize more paid work.

The stop vocabulary is closed. Details can explain a stop but cannot supply another terminal_reason:

terminal_reason Existing exit Origin
budget 25 Token, provider-call or cumulative provider-wall limit; disallowed unknown usage
timeout 124 Provider wall-clock timeout
watchdog 25 Provider silence watchdog
review_capped 25 Trusted review cycle/round cap
human_hold 25 Human hold/pause or other human-attention stop
ticket_withdrawn 0 / 26 / 25 Configured Done / cancellation-or-duplicate / other inactive state
stalled 25 Opt-in trusted progress policy exhausted

Successful completion, intentional handoff 20, quiet waits, infrastructure failures and cancellation 130 retain their exits without an invented reason. The ticket ledger stores the originating reason; dispatch lane records and dispatch-skips.json carry the matching reason. A later generic hold cannot overwrite that run's cap/watchdog/budget reason. This vocabulary does not replace observational learning cause classes.

A progress turn ends once per completed background stage attempt. Contract IDs describe fulfilled requirements, qualified gates or confirmed findings, bound to exact configured outer gate commands. Only green checks at unchanged HEAD with readable output from bureau_record_gate or the outside-gate executor qualify. Provider results, declared fixes, commits, completed checkboxes and activity never do. Each contract-bound fact resets the counter once; repeated green checks at new HEADs earn no reset. After max_non_improving_turns (default 2), stage completion consumes the shared latch before the waiting worker cleans up, returning 25 with terminal_reason: stalled. Interrupted/withdrawn/already-held stages and wrapper attempts do not advance it. Budgets and progress are both off by default; stage/review limits remain independent.

Cooperative ticket withdrawal

bureau_ticket_checkpoint is the trusted shell boundary for background work. It checks after selection/claim before dispatch, before and after each provider pass, before ordinary push/PR/comment/acceptance publication, immediately before the merge and on queue/shepherd iterations. Preservation pushes of commits already made remain allowed on exit, as described below. agents.ticket_active_states resolves state keys to configured IDs; display names do not decide whether work continues. Done exits 0, configured cancellation/duplication exits 26, other inactive IDs exit 25. Active-to-active moves retain the optimistic mutation conflict (21). Normal stage transitions, including manual Merge approval publication, continue as before.

A confirmed withdrawal latches under <git common dir>/bureau/ticket-control/RUN_ID/stop-CODE. Captured and parallel calls share that latch; it prevents a later refresh failure or reactivation from resuming this withdrawn run. Mandatory stage guards and shepherd state reads classify their successful snapshot with the same ID-based checkpoint and latch withdrawal before routing. Parents consume the latch after captured calls, including Done's exit 0 and before shepherd's read-error handling; a snapshot of another inactive state ends shepherd with 25 without adding needs-human, even if subsequent additional refreshes fail. A failed additional refresh warns once per run and permits the already authorized unit; a failed mandatory read retains its existing strict error handling. Invalid active-state configuration exits 24. This adds no polling daemon or interval.

Withdrawal sends no signal. A provider already in flight finishes before its post-call checkpoint; provider-internal actions can therefore finish within that unit. Parallel review joins every specialist before the parent exits. Spec recovery skips rollback. Implementation preserves already made commits with its existing best-effort failure/EXIT push, without another checkpoint or any PR create/ready, comment or merge; failed preservation pushes leave the commits locally. The worker removes disposable registration for dirty/ahead work even when Done returned 0. Files, local commits and the branch remain available for inspection; they are not automatically reset on the next pick. Issue/workspace leases release after the stage and worker finish. Signals retain 130 and the existing interrupted-lease recovery requirements; a worker interrupted independently of shepherd retains its cancelled-run log and halt alert. Additional refreshes run only within a claimed background run, use one attempt without changing the caller's retry/fault state, and leave standalone Linear helpers on their existing strict reads. App prepare/finish retains its separate stale-result checks.

PR 6 outside-sandbox recovery checks before starting the rerun and after it returns; a withdrawn ticket starts no new rerun. PR 7 checks each acceptance destination before publication and consumes any stop in the parent; an externally parked ticket gets no new approval brief. Fresh ticket posts require an explicit publication-completed acknowledgment after post_comment returns successfully: a checkpoint that exits 0 without posting leaves delivery pending, so a new run after reactivation can publish at the same HEAD. An existing remote marker still reconciles delivery. The ordinary manual Merge boundary still publishes its approval brief.

Implement retries with clean base merges

The existing re-acceptance rule still requires an explicit former-worker failure note and permits a clean linked non-spec worker whose HEAD equals or is behind the freshly fetched origin/<branch>, independently of base resolution; the remote need not have main. Implement also re-accepts a preserved worker ahead only by verified clean merges of the resolved base. It retains HEAD through worker preparation and implement startup, bypassing both resetting checkouts and clean. It never rolls back a merge. The same worktree path must be reused; a different path does not free a branch held by the preserved checkout.

The merge-only rule requires the same repository's linked worktree (never the primary checkout), the requested local issue branch, no tracked or untracked changes, no in-progress merge, and readable fetched refs. Ignored files do not count as dirt and remain in this retained path. After fetching, choose origin/<repo.base_branch> when the configured value is a nonempty syntactically valid branch name, otherwise the symbolic target of refs/remotes/origin/HEAD, otherwise origin/main. Pin that selected base ref and its commit consistently through classification and rechecks. A selected ref that does not resolve to a commit disables merge-only acceptance; do not silently substitute another base. This resolution applies to the merge-only rule; other stages' reset/merge policies keep their existing behavior.

Pin HEAD and origin's issue tip alongside the base; require origin's issue tip to be an ancestor of HEAD. Inspect exactly git rev-list <issue-tip>..<HEAD> --not <base-tip>. The nonempty result must contain only two-parent merges. Every first parent is the issue tip or another merge in this result, so the first-parent chain anchors at the issue tip; every second parent is an ancestor of the pinned base. For each merge, git merge-tree --write-tree <first-parent> <second-parent> must succeed and return exactly the committed result tree. Ordinary base commits are excluded; ordinary own commits, unrelated/reversed/octopus merges, conflict resolutions and extra changes fail. Missing merge-tree support (Git before 2.38), fetch/ref errors and changed HEAD/refs/status fail closed. Revalidation never resets a newly arrived writer commit.

Automatic merge-only re-acceptance is limited to implement workers whose preservation record names this issue, branch and workspace with reason: unfinished and exit_code: 22 or 23. Worker cleanup adds the exit code to the existing <git common dir>/bureau/preserved/<workspace-key>.json record. Retained preparation keeps that record and revalidates even after registration was restored: a preparation failure cannot turn registration into permission to reset retained work. Existing registration identity checks still run before re-acceptance. Spec workers retain disposable registration after ordinary failures and reset/clean to verified committed phase checkpoints or the configured origin base; they never retain unfinished phase edits through this rule. Other stages and legacy/unknown failure records do not gain merge-only permission. Ordinary failures release leases; an interruption (130) still removes registration and keeps the leases regardless of cleanliness. Timeout (124), signals and interrupted records do not enter this new resume path and require the existing recovery procedure.

A failing implement stage still pushes a merge-only state (one CI run), as before. Provider failures, timeouts, /goal, EXIT-trap and signal pushes retain their existing behavior. When the ordinary failure push is refused, cleanup preserves the local merge and the next tick can re-accept it under the rule above.

Adoption: resync the scripts scope as one set (including config, worker and implement), reconcile local drift and restart drivers. No schema migration or exit-code change. Existing merge-only records without an exit code need explicit recovery; do not infer a previous failure from the tree. Resolve a pre-existing needs-human hold deliberately before retrying. Qualification uses fake providers/services and real local Git, two worker ticks and negative controls; no live installation or CI execution is claimed.

File-overlap admission

Enable agents.file_overlap_gate: true only after comparing installation drift and resyncing all scripts together, including bureau-paths.py and bureau-admission.py. Restart every writer/driver; mixed old/new writers and separate clones or hosts do not share this gate. The default remains disabled for standalone operations; continuous dispatch requires it, including one lane. Admission uses PR 9's strict configured-ID checkpoint and the worker's shared run latch before granting or returning a wait, including preflight before execution ownership. Done returns 0, cancellation/duplicate 26 and other configured inactive or unknown states 25. These withdrawals take precedence over exit 29. The calling shell consumes the stop before any Build mutation, including Done's exit 0. An older writer without these checkpoints cannot certify safe withdrawal.

After successful tasks generation or checkpoint resume, the spec stage records the ticket, canonical branch, committed tasks identity, SHA-256 and normalized paths in <git common dir>/bureau/admission/v1.json. App spec completion does the same. The extractor supports root and extensionless files, including bare dotfiles and standalone root references in mixed-path tasks, arbitrary language layouts and directory scopes. The root scope . overlaps every path; unresolved root spellings become unknown. Globs expand against the committed Git tree; unresolved globs, missing/ambiguous inventories, traversal and ambiguous extensionless references become unknown. Unknown scope overlaps the entire repository and can be admitted exclusively. The literal repo.path_prefix_strip applies once. Generated documentation and CHANGELOG paths remain ordinary conflicts even when another resolver can regenerate them. The advisory spec crosscheck uses this extractor and exact/directory matching only while the gate is enabled; absent/false retains the legacy extractor, literal prefix stripping and substring matching.

One repository-shared file lock covers complete paginated Linear snapshots (including canonical-branch comments), open PR snapshots, reconciliation and atomic scope reservation. Build, Build Review, Merge and configured QA/Copy work hold their scopes. State holders follow existing linear.projects (empty means the whole team); reservations, active ownership and open Bureau PRs retain their footprints across project changes. Open Bureau PRs remain holders when their tickets are parked, human-held or terminal; canonical/recorded branches, numbered spec branches, explicit Bureau bodies and the legacy Claude-generated tasks-spec/draft body identify them. PR diffs use immutable base/head commits, both sides of renames and a pinned identity recheck. An unreadable service snapshot or diff is an error (27/18), never an empty holder set. The candidate's own ticket and same-repository branch PR are excluded; a fork PR with the same branch name still holds its diff. Live services are not a cross-service transaction: changes by humans or old writers after the checked snapshot remain outside local serialization.

Admission persists a reservation before the Build transition. Every Build route, including QA/review rework and shepherd --from-stage, passes the shared guard. Background implementation/Copy/QA preflight runs before ownership/reset, then implementation rechecks its merged tasks before writing. Review checks before reserving a paid round, after respecting a requested approval stop. App prepare for writing stages gates the current checkout without resets; app finish gates Build/Copy/QA transitions and retains a prepared result on a wait so it can be submitted again. Background Spec Review/UX/Copy store a successful readiness result bound to branch HEAD, task digest, ticket snapshot, stage and configuration. Spec Review/UX additionally bind readiness to their validated passing status and installed schema digest; see result contracts and upgrades. Repeated waits retry admission without another creative pass. Changed tasks, branch, ticket or configuration invalidate readiness. Review admission polling consumes no PR 8 round, approval or gate receipt.

Migration runs under the admission lock. Existing Build/Copy tickets become queued only after proving a readable spec-only branch, no execution lease/preserved work and no dirty attached checkout. State alone never elects them. The first queued contender to reserve wins; other queued tickets are not holders against it, avoiding mutual waiting. Existing source changes, downstream work and unknown writer ownership remain holders. Reservations have no TTL and are outside prunable evidence. A rework route with an existing admitted footprint retains that reservation; the next worker still checks every holder/PR before any paid pass or write. This continuation prevents admission polling from buying another review round. Task changes refresh inventories, separately from the granted scopes in reservations. Other tickets compare against granted scopes only. A requested expansion checks the union of the grant and current inventory; only successful admission replaces the grant, so a wait never expands or shrinks the holder's reservation. All states PR 9 classifies as withdrawn release their reservations only after cooperative cleanup has finished and execution ownership is absent, including configured inactive states whose service type is nonterminal. Holding state IDs excluded by agents.ticket_active_states are not re-elected after release. An open PR still holds its diff. Reservations already expanded by an older runtime are preserved; reconcile such a reservation explicitly after checking unfinished work. Do not delete the store to clear a wait while work may still exist. Reconcile stale leases/preserved work through the ownership protocol first.

Conflicts return 29 (file-overlap-wait) with holder identifiers and intersecting paths or the unknown reason. Evidence mirrors a stable file-overlap resource wait; losing/pruning evidence cannot grant admission. Within each queue poll, a stage skips candidates that just returned 29 and tries the next candidate, allowing disjoint work through. The skip list clears for the next poll, restoring each waiter's priority; exhausting only waiting candidates returns 29. Tick reports waiting, and the shepherd's stage loop waits cancellably without stuck counts. A guarded move_issue call, including shepherd --from-stage build, returns 29 to its caller without a failure comment, human label or alert. Failure summaries exclude this class. No alert, human label or model call is added for admission polling. Other ownership/service errors retain their existing codes. Qualification uses real local Git and fake providers/services; no live installation or full Codex background qualification is implied.

Spec phase resume and governance

Specify and plan must run no measurements, probes, benchmarks or full test-gate runs. Use existing evidence and leave unknowns for implementation/QA. Bureau supplies this rule and the governance requirement through prompts, managed instructions and commands; it preserves customized .specify/templates, the constitution and Spec Kit 1.2.2 helpers.

Every spec requires a section headed Governance and security, containing an explicit decision and rationale explaining applicability. Bureau prompts use Decision: and Rationale: fields; an existing explicit sentence such as "Not required because this changes only static documentation" also qualifies. For example:

## Governance and security
Decision: not required
Rationale: This documentation change processes no credentials or personal data.

In spec.md, place ## Governance and security with Decision: and Rationale: lines at column 0, in plain text, before any code block or HTML block; a leading YAML front matter block is allowed.

The governance check catches common authoring mistakes using the following rules. It splits only LF and CRLF lines; other C0 controls (U+0000–U+001F except tab) and C1 controls (U+007F–U+009F) in the governance heading, decision or rationale are invalid. Content checks decode HTML entities, normalize Unicode NFKC and remove format characters (category Cf, including zero-width characters). Markdown heading syntax still requires a column-0 ATX heading with one to six ASCII # characters followed by an ASCII space; normalization does not turn a nonbreaking space after the hashes into valid syntax. A same-level or higher ATX heading ends the section, as does a setext underline (--- or ===, including longer runs) immediately after a text line; that preceding text cannot supply a field or rationale.

The first fence-like line is a permanent cutoff: after optional whitespace and any mix of list markers (-, *, +, or digits followed by . or )) and blockquote markers (>), three or more backticks or tildes end the scan, with no opener/closer matching or indentation bound. Marker whitespace is optional. Every nonblank line indented by four or more spaces or a tab (including spaces followed by a tab) is also a cutoff; this conservative rule includes list continuations. The first line starting after optional spaces/tabs with < followed by an ASCII letter, ! or / is also a permanent cutoff, including a leading HTML comment. A leading YAML --- block is ignored through its closing ---; the validator can resume after that metadata, but an unclosed block contributes nothing. Other HTML comments are masked through --> or end of document, preserving physical lines and columns; their contents cannot supply fields or fence cutoffs. Governance after an earlier closed code or HTML block does not qualify.

Decision/rationale labels must start at column 0 without container prefixes. Values that start with a backtick code span, including values consisting entirely of a code span, are invalid. Rationale continuation lines may have zero to three spaces of indentation, but not four or more spaces or a leading tab (including spaces followed by a tab). Blockquoted continuation lines do not supply rationale text. The placeholder check removes brackets, parentheses, quotes, blockquote and emphasis markers and surrounding punctuation. A rationale must contain at least one letter or digit after normalization, and cannot be solely a placeholder, deferral or decision restatement. The same placeholder check applies to present Access/Logging/Retention fields. Examples rejected after normalization include TBD, TODO, N/A, a dash and an ellipsis, including fullwidth, entity-encoded or zero-width variants. Existing column-0 inline decision/explanation sentences and German or mixed Entscheidung:/Begründung: labels remain accepted. A justified not required or N/A is valid; there is no punctuation, verb or word-count requirement. Ordinary words such as “pending” or “wird definiert durch” inside a real explanation remain valid.

Known limits (governance check): the check targets honest mistakes by the spec agent; it is not a security boundary against deliberate obfuscation. Deliberate evasion, for example link reference titles, empty link labels or unusual Markdown or HTML constructs, is not guaranteed to be caught. Spec review remains responsible for judging whether the section is real and adequate, including applicability, circular or vague explanations and access/logging/retention risks. Placeholder recognition covers common template wording; other placeholder phrasing and further Markdown container constructs are left to spec review.

Background spec review applies the shared check after permitted edits and forces REVIEW_STATUS=FAIL on a detected error; a model FAIL uses the same comment and route to Spec. Its full summary, including the governance error, passes through comment projection; the trusted validator reason survives even when an unreadable model summary or failed projector is omitted. Either failure invalidates from specify, so governance repair cannot resume at plan/tasks. App spec and spec_review completion require the prepared issue's spec.md and apply the same check before posting or moving; a detected error leaves the run prepared for repair. Passing this check does not replace substantive spec review. Existing specs may need this section added or moved before code blocks or HTML blocks.

Successful specify, plan and tasks phases each make one local commit of the reserved feature directory on its feature branch, named ISSUE: spec PHASE checkpoint with the Bureau-Generated: true trailer. Only completed phases receive checkpoints. The normal end-of-stage commit of remaining changes, single push, crosscheck, digest and routing still run; no per-phase pushes are added. Closed-reader shell/routing and Python finalization fixtures cover exits 0, 14, 25 and 124, including unopenable merge capture in the production || true context. Invalid records from any ticket are isolated individually: when removal succeeds, quarantine retains only size, SHA-256 and observation time, with no copy of the bad bytes. Unreadable records are skipped. Python and the common Bash evidence wrapper cap warnings at once per process; merge capture and review cleanup have their own protected diagnostics. ENOSPC, permission errors and lock contention leave work running. Evidence locks wait at most 250 ms. waits itself is read-only and skips invalid records without quarantining them.

The sole mandatory evidence write is a receipt before forwarding a successful provider result. If that persistence fails, including when the protected store has no capacity for it, the adapter follows its existing error path and forwards no success. A receipt does not require a manifest or manifest link to succeed. Error/timeout/cancellation receipts, manifest links, pruning and provider diagnostic metadata are best effort; their failure preserves the original outcome.

Updates use an OS file lock and atomic replacement; JSON writes fsync the file and containing directory. New directories use 0700 and files 0600. This is local coordination, not a cross-host lock or tamper-proof audit trail.

Known limits: The tested failures do not cover every way storage or a process can fail. Abrupt termination, power loss, a filesystem that does not honor syncs, or unusual I/O errors while the interpreter shuts down may still lose evidence or change an exit. External edits and separate hosts are outside the store's lock. Sweep bounds require the documented clock, readable tickets and dispatcher cadence; stalled dispatchers, changing ticket sets and other restart patterns have no such bound. When selection switches between persisted order and fallback rotation, the rotation can start out of phase, so covering every ticket can take one sweep more than N (seen with six tickets at the default 30-minute cadence: seven sweeps).

Privacy contract

Receipts, manifests and waits retain allowlisted identity/measurement fields, digests and local provider pointers. They contain no raw logs, excerpts, command text, ticket descriptions, specialist prose, review comments or structured-result free text. There is no excerpt option. The explicit free-text exception is the advisory observations in insights.jsonl, bounded and filtered as described above; that best-effort filter is not a guarantee of secret removal. The acceptance ledger retains only the projected brief body, with store-relative evidence identifiers in place of local pointers. Shell helpers still run through bureau_without_secrets, with Bureau-owned secrets and their carriers removed. Arbitrary phase/cause/actor/PR URL text cannot become a diagnostic text channel: phases and causes outside the vocabulary are digested, reasons are digested, actors use the supported vocabulary, and PR metadata keeps only the number.

Waiting lifecycle and observation

Wait keys identify a cause independently of the run. mark_needs_human opens a typed wait before attempting publication, including failed publication/local holds. Exit 20 opens an approval decision; 21 opens an ownership/resource wait. Manual Merge records the approved PR and generation; automatic Merge opens a dependency wait for its worker. Gate waits belong to CI/gate owners or the repository maintainer. Supported kinds are decision, dependency, compliance, resource and technical; an exit code alone does not identify every cause.

Repeated refusals retain the wait ID, first reached time and reached event. Acquiring a lease does not resolve a preparation refusal: ownership closes only after successful stage/worker execution. Approval PR observations close only their matching boundary generation, after resume(expected=record) actually removes that boundary. Replacing a generation resolves its predecessor as an observed supersession; a stale PR cannot close the replacement or unrelated waits. An authoritative timestamp before the wait (or in the future) is rejected, leaving the wait open.

Each bounded tick and continuous queue iteration attempts up to four distinct tickets with open waits, even with manual merge and disabled merge/rebase agents. Only an attempted read advances its persisted cursor, including failures/timeouts; selection leaves unvisited cursors unchanged. Each attempted ticket updates its matching waits independently: a refused larger record does not stop a smaller writable cursor from advancing. Selection reserves room for the next timestamp's full encoding, then writes and reads back the oldest cursor unchanged to check persistence. When that succeeds, oldest persisted cursors take priority across fresh processes; rotation never overrides them. If the cursor cannot round-trip, a retained Python store uses in-memory attempt order and shell dispatchers pass their in-memory sweep count into each fresh Python invocation. Fresh shell ticks seed that fallback from the current time divided by the configured agents.poll_interval_minutes in seconds, so polls at that cadence advance one turn, including ordinary 30-minute polls. For a stable set of N readable open-wait tickets, an advancing clock and at least one read started per sweep, persisted cursors cover every ticket within N sweeps while selection stays on persisted order (see Known limits for the switch to fallback rotation); refused writes retain the same bound in a continuous dispatcher or fresh ticks at the configured cadence. Arbitrary restarts or other external polling cadences have no cross-process fallback bound. The pass has a shared 10-second network budget and performs no state, label or PR mutation and no provider work. A terminal Linear snapshot resolves only waits captured for that observation. For a PR-linked approval, a matching merged PR can close that approval even while the ticket remains at Merge. Concurrent boundary replacement is checked again after the remote read.

Without authoritative history, resolved_at and the resolved event's at remain null; only observation times are recorded. Linear completedAt/canceledAt, when supplied by its terminal snapshot, or GitHub mergedAt can supply an exact end. An unrelated old PR merge never establishes that a newer ticket wait ended. Clearing a hold after publishing its label does not itself resolve the human wait.

Retention and global limits

On writes, evictable completed runs expire after 30 days or 128 completed runs. Resolved waits and inactive ticket observations expire after 30 days. Global storage additionally has a 16 MiB total byte cap and 4,096 file cap, covering manifests, receipts, waits, ticket records, spec checkpoints, quarantine digests and atomic staging leftovers (the empty lock file is excluded). A manifest includes its attempt/gate entries in this byte budget. Before allocation, a write reserves its full temporary size and one additional file slot, including unchanged/shrinking replacements. Failed cleanup attempts to discard the temporary payload; an undeletable .tmp remains an uncommitted file within that reservation and is never read as a record. Pruning retries its removal and also recognizes legacy staging names. Under capacity pressure, the oldest completed data is removed first; deleting a run removes its manifest and receipts together. Resolved waits, inactive observations and quarantine digests are also eligible by age.

Active/interrupted runs, open waits, and runs referenced by open waits are never evicted. When protected data leaves no staging capacity, optional writes (even unchanged replacements) skip with a warning; a success receipt that cannot fit fails persistence and prevents success forwarding. Any housekeeping exception, including an undeletable staging leftover, also leaves capacity unconfirmed: optional writes skip and a mandatory success receipt fails closed. These reservations prevent writes from taking an in-budget store over its cap; an already oversized store containing protected or undeletable files still requires operator inspection. Provider originals are outside this cap; this is not a disk quota on provider transcripts. Waiting shares describe the retained observation window, not discarded history.
