Configuration reference

Every knob bureau-init exposes — what it controls, where it lives, and what the default is. Two surfaces:

  • .bureau.json — written by /bureau-init to the target repo's root. Gitignored. UUIDs + agent toggles.
  • Environment variables — runtime-only overrides read by the pipeline scripts. Not persisted; usually set inline (BUREAU_DRY_RUN=1 ./scripts/queue-loop.sh ...) or in .env.

Setup captures the project-specific settings. Verify credentials, installed tools and real tests before running work. Current app tasks use the app-selected model; provider settings below select background CLIs.

.bureau.json

Version and validation

Version 1 remains compatible; version 2 makes the legacy agents.runner: "claude" default explicit. Migration preserves existing fields, adds agents.model_compatibility: "v1" to retain legacy provider model selection, and saves a private exact backup. bureau-doctor.py validates shape/version and reports effective settings without contacting providers. See migration and rollback.

agents

Which pipelines run, how often they poll, how aggressive they are.

Default semantics. An absent stage is disabled. A boolean controls the stage directly; an object such as {"enabled":true,"runner":"codex"} is enabled unless enabled is explicitly false. The setup defaults below describe the initial configuration, not a fallback that enables missing stages. Preserve existing choices during updates.

agents.merge_min_required_checks number 1 Minimum completed check-runs required on the PR head SHA before merge_require_green_ci will pass. Prevents a PR with zero registered workflows from passing vacuously. Set to 0 for repos with no CI at all (rare — prefer flipping merge_require_green_ci to false instead). A value that is not a plain whole number is read by the gate's number rule: a string that reads as a number is that number (ASCII blanks around it and one leading + are dropped, then digits with an optional fraction and exponent: " 2", "+2", "2.0", "1e3"), a fraction is rounded up (never fewer than written), a number above 9999999 is 9999999, and a negative number or any other value is the default, each with a warning from the merge stage and the doctor (one rule: _merge_gate_number in bureau-config.sh, gate_number in bureau-doctor.py). Before v3.1 a negative number or a word let the check pass with no check at all
agents.merge_ci_start_grace_seconds number 1800 How long after the PR head's commit (its committer time on GitHub) the merge gate waits for CI to appear. A head with no check run (not even a queued one) and no commit status is "not yet" within this time and blocked after it (25, alert; the shepherd halts), so a repository whose workflow never runs for the PR stops waiting silently. 0 blocks at once. A value that is not a plain whole number is read by the same rule as merge_min_required_checks (default 1800). A time that cannot be read keeps the gate at "not yet"; does not apply when merge_min_required_checks is 0. A check run that exists but is still queued is covered by merge_ci_queued_grace_seconds
agents.merge_ci_queued_grace_seconds number 3600 How long a check run on the PR head may stay queued — created, but taken by no runner — before the merge gate gives up on it (v3.2). Past it the gate reports ci: check <name> queued for N s on <head>, past the CI queue grace (agents.merge_ci_queued_grace_seconds: N) — runner offline? and is blocked (25; the queue loop alerts, at most once an hour per ticket; the review stage sets needs-human; the shepherd halts); before v3.2 such a check counted as pending for ever. The time is the check run's started_at, which GitHub sets when it queues the run; a run without a readable time stays pending. Only the status queued counts: a running check, a deployment approval (waiting), a concurrency wait (pending) and a pending commit status stay "not yet". The default leaves room for a single self-hosted runner that works through a few jobs ahead of this one; measure how long jobs wait to start there before keeping it (a runner outage longer than the grace blocks every approved PR waiting on it, with needs-human after an inline merge), lower it where runners pick up jobs within minutes, raise it where jobs regularly wait longer. 0 blocks a queued check at once; to keep v3.1's behaviour set 9999999. Read by the same rule as merge_min_required_checks (default 3600)
agents.merge_gate_recheck_seconds number 3600 The longest hold on a ticket whose merge gate was not yet decided, or blocked at the merge stage (v3.2). The review stage records such an APPROVE and ends with 2; the merge stage ends with 2 or 25 and marks the ticket. The picker of that stage (review or merge; never rebase) then puts the ticket after every other candidate while its branch on origin is still at the judged head, and still takes it when nothing else can be picked, so a hold never delays a merge while nothing else waits (the bounded tick with --allow-merge runs another stage that has work first, see troubleshooting). The hold is two poll intervals after the first answer (at least 300 s; the queue loop's own interval, else agents.poll_interval_minutes) and doubles with each further one, never above this value: with the default 30-minute poll and other tickets waiting, such a ticket is checked about every other poll; with a 5-minute poll after about 2, 4, 8 and then every 12 polls. With a poll of an hour or longer set this to at least two intervals, or nothing is held. A push, a branch gone from origin and a record time in the future end the hold. At Build Review the next run reuses the approval without a model call and without the build check that passed for the same head, base, command, repo.untrusted_env and repo.worktree_links. The shepherd is not affected. 0 switches the holds off (the ticket is picked on every poll, as before v3.2). Read by the same rule as merge_min_required_checks (default 3600)

repo.remote_git_runs_hooks bool or "operator" false Whether Bureau's own git commands that talk to a remote — push, fetch, pull, ls-remote, clone, remote, submodule, all of which keep the GitHub token variables for the credential helper — run the repository's hooks. Since v3.2 they run with -c core.hooksPath=/dev/null and, for the hooks the configuration defines (git 2.54 and later), hook.<event>.enabled=false for every hook event and hook.<name>.enabled=false for every configured hook name (the git function in scripts/bureau-env.sh): a hook from the branch would see the GitHub tokens, pre-push on a push and reference-transaction on every ref update a fetch or a push makes. A pre-push hook (lint, tests) therefore no longer runs when Bureau pushes; CI runs those checks on the pull request. A repository that uses Git LFS needs true or "operator": git lfs install uploads the LFS objects in a pre-push hook, and without it Bureau's push leaves them off the remote; doctor warns when the main checkout uses filter=lfs (in its .gitattributes, a .gitattributes further down that git lists, or .git/info/attributes) and the key is not true. true (the JSON value) runs the hooks again, as v3.1 did, including hooks the branch supplies through a core.hooksPath that points into the working tree (husky's .husky, a tracked .githooks). "operator" (the string) runs only the main checkout's own hooks directory, hooks/ in the git common dir (.git/hooks of the main checkout, also for a stage in a linked worktree), which no commit can write: Bureau forces core.hooksPath to that directory's absolute path for its remote commands, whatever core.hooksPath the configuration names, and keeps the hooks the configuration defines (hook.<name>.command) switched off by name; those operator hooks see the GitHub tokens. Put the hooks Bureau's push needs (the pre-push of git lfs install, a secret scanner) there; for clone and outside a repository "operator" keeps every hook off. With "operator" and with the hooks off (every value but true) Bureau's own push, fetch and pull do not recurse into submodules: push.recurseSubmodules=no, fetch.recurseSubmodules=no and submodule.recurse=false go on the command line after the caller's own options of git, so neither configuration nor a caller's -c, --config-env or included file turns recursion back on, and a Bureau git call that asks for recursion in its arguments (git submodule; --recurse-submodules, --recurse-submodules-default or --recursive under any prefix git accepts, except a value of no), any git clone, and a call with a git option before the subcommand that git itself does not define are refused with exit 128, because a child git in a submodule would run hooks that submodule's configuration defines; Bureau's push then neither pushes nor checks submodule commits (SECURITY.md has the exact rule). Absent, null, false, any other value and a .bureau.json that cannot be read keep them off; doctor reports the mode as remote_git_hooks (on, operator or off) and warns on a value that is neither a JSON boolean nor "operator", and, with Git LFS and "operator", when that hooks directory has no executable pre-push. Local commands (commit, checkout, merge, reset) run their hooks either way, without the Bureau secrets. Hooks only: a credential helper, a filter or an fsmonitor named in the git configuration still runs, and gh's own git calls keep their hooks; see SECURITY.md
repo.post_implement_command string unset Optional hook for a repository that derives files from an implementation, for example regenerating generated docs or command contracts. The implement stage runs it wherever it releases the work for review: when the run ends COMPLETE (hand-off to QA or Build Review), whether or not this run made commits of its own, and when it ends PARTIAL with commits (the PR is marked ready so CI runs); never in a dry run. It runs after the loop and before the squash-range check and the final push, in the implement worktree via bash -o pipefail -c, with no stdin, with BUREAU_ISSUE and BUREAU_BRANCH set, and within BUREAU_POST_IMPLEMENT_TIMEOUT seconds (default 900, never above BUREAU_IMPL_TOTAL_TIMEOUT; on timeout its process group gets SIGTERM, then SIGKILL after 5 s). It commits its own output; those commits are checked and pushed with the run's. It must be idempotent and exit 0 when there is nothing to commit, because it also runs when a later run has nothing new: a bare git commit exits 1 then, so write `git add generated/ && { git diff --cached --quiet
repo.worktree_links list of paths [] Paths symlinked from the main checkout into every stage worktree after each reset, for what the reset's git clean -fdx removes and nothing reinstalls, typically a Python virtualenv: [".venv"]. Each entry must be a plain relative path (no leading /, no ., .., .git in any case, or empty component); a name may start with -. A path is skipped with one warning line, and the stage runs on without it, when the branch tracks it, when its parent is missing in the worktree, leads outside it or runs through a symlink in it, when it does not exist in the main checkout, when the worktree's gitignore does not ignore it as a symlink, or when a real file or directory sits at that path; an older link is replaced. A directory-only pattern such as .venv/ does not match a symlink, and an untracked link would leave the worktree dirty (the worker then preserves it and the next reset stops with 21), so list .venv in .gitignore without the slash. The next reset removes the link, never its target. The link is the main checkout's own copy, not a copy of it: every stage and every parallel worker shares it, and commands in a stage worktree act on it — python3 -m venv --clear .venv empties the main checkout's virtualenv, rm -rf .venv/ (with the slash) deletes it, pip install changes it, and code from a pull request that QA or the review build check runs before anyone has approved it can change the environment every later stage and you use. The stage protocol (scripts/bureau-stage.md) tells the agents never to delete, recreate or clear a linked path and not to install into it unless the ticket asks for that; it cannot enforce it. Never applied in the main checkout itself, nor in a worktree of a bare repository (there is no main checkout). Never list a .env* file (.env, .env.local, .envrc, a path through such a name, or a link to one): the link would put the main checkout's secrets into every stage worktree, where pull-request code runs, while the reset keeps them out otherwise; the stages find .env through the main checkout without it. The stages skip such an entry with one warning line, and also a directory with a .env* name anywhere below it (links followed) or one that cannot be searched completely; both sides also check every component of the entry's fully resolved path. bureau-doctor.py lists each entry with its status (ok, missing in the main checkout, tracked in the main checkout, not ignored as a symlink, invalid, env file, holds an env file, not searched completely, no main checkout), warns or errors the way the stages would skip, and reports a .env* entry, a directory that holds one (naming the first it finds) and a directory it cannot search completely as errors; it runs the stages' own search (find -L DIR -mindepth 1 -iname '.env*', no depth limit). That search matches names and follows links into directories: a link under another name that points at a .env file (creds -> ../.env inside a linked directory) is not detected, by the stages or by doctor. It fails on an unreadable subdirectory, and with GNU find on a link loop, which the BSD find of macOS skips; false counts as no links, like an absent key. It judges existence and tracking in the main checkout the stages link from, which it reports as main_checkout, also when it runs in a linked worktree; for a bare repository or a git directory outside the main checkout it reports none and warns that the stages make no links. Python repositories

The stage worktrees are reset with git clean -fdx, which removes an ignored .venv. First commit the resynced scripts to main, so that the stage protocol the agents read in their worktree (scripts/bureau-stage.md) carries the rule for linked paths; then set "repo": {"worktree_links": [".venv"]} so every stage worktree gets a link to the main checkout's virtualenv, and make sure .gitignore lists .venv (not only .venv/); bureau-doctor.py shows whether it does. With an editable install (pip install -e .), the linked virtualenv's .pth file points at the main checkout's src/, not at the worktree's, so Python in a worktree imports the main checkout's code unless the worktree comes first on the path: run tests as PYTHONPATH=src .venv/bin/python -m pytest (or set it in repo.test_command or scripts/bureau-test.sh), and say so in the project instructions the agents read. The linked virtualenv is the main checkout's own: what an agent installs, recreates or deletes there happens to yours, and pull-request code that QA or the review build check runs uses it too. If that is not acceptable for a repository, leave the virtualenv out of worktree_links and let repo.test_command or scripts/bureau-test.sh create what the tests need.

Implement-pipeline retry loop

Env-only knobs (no .bureau.json equivalent). implement-pipeline.sh invokes the selected provider inside a bounded retry loop and parks the issue with needs-human if it doesn't reach status: COMPLETE within the budget.

Var Default Notes
BUREAU_IMPL_MAX_ITER 3 Max provider passes per tick. Each iter parses the JSON status block, runs the squash-range check, pushes commits (see agents.implement.push_each_iteration), and decides continue/stop. Since v3.2 a pass that times out counts as one of them (status TIMEOUT in the iteration log) and the loop goes on; the stage ends with 124 only when the last allowed pass times out
BUREAU_IMPL_ITER_TIMEOUT 1800 Per-iteration provider wall-time cap in seconds, limited by the remaining total budget and enforced by the Python adapter for both providers
BUREAU_IMPL_TOTAL_TIMEOUT 5400 Budget in seconds for the implementation provider loop. Independent executor tests and publication can add time after it; this is not a monetary cap. Since v3.2 it, not one timed-out pass, bounds a stage whose passes time out; a timed-out pass that leaves 60 s or less of it ends the stage with 124. Setting it to BUREAU_IMPL_ITER_TIMEOUT brings back the pre-v3.2 ceiling of one timed-out pass, but also caps a productive multi-pass run at that one pass's time; BUREAU_IMPL_MAX_ITER=1 is the other trade-off (one pass of any kind)
BUREAU_POST_IMPLEMENT_TIMEOUT 900 Limit in seconds for repo.post_implement_command, never above BUREAU_IMPL_TOTAL_TIMEOUT. On timeout the hook's process group is ended and the stage halts with 14

The default provider-loop budget is 90 minutes, and since v3.2 a stage whose passes time out can use all of it: a timed-out pass no longer ends the stage while another pass fits (see Exit 124). An unproductive first PARTIAL iteration can become STUCK; a timed-out pass never does; prior productive iterations and legitimate COMPLETE results have separate handling. The executor checks Git evidence and, for Codex completion, the configured project tests. A provider's success text alone cannot complete the stage.

Terminal states map to PR state + Linear:

Status PR needs-human label State move logs/escalations.log
COMPLETE flipped to ready (gh pr ready) no → QA / Build Review no
NEEDS_HUMAN / STUCK / CAP_TIME / PARTIAL draft yes stays in Build yes
CI_MARKER draft, report posted on the PR yes stays in Build yes

CI_MARKER overrides every other status, COMPLETE included: a commit message in origin/main..HEAD carries an entry of scripts/ci-skip-markers.txt ([skip ci] and the other forms GitHub honours), or the range could not be read. Reword the named messages, then remove needs-human. The check also runs after every iteration of the loop, so a marker stops the run after the iteration that wrote it instead of after all of them, and that check's report goes into the iteration log of the summary; the /goal path, which has no iterations, checks once after its run, and the check before the hand-off always runs. The QA stage runs the same check and flags needs-human instead of routing on.

Resolution and provider usage

The actual creative invocation uses bureau-provider.py. Runner precedence is per-stage BUREAU_RUNNER_STAGE, stage JSON, default JSON, then Claude. Model precedence is provider-specific stage environment, generic stage environment, stage JSON, provider JSON, generic default JSON only for its owning default runner, provider environment default, and the legacy Claude environment default. See provider runtime.

BUREAU_REASONING_STAGE, BUREAU_SANDBOX_STAGE, BUREAU_STAGE_TIMEOUT and BUREAU_CLAUDE_CONFIG_DIR override the corresponding provider settings; like the other overrides on this line they are read from the process environment, not from .env. BUREAU_CONFIG selects the explicit configuration file; otherwise the current checkout and primary worktree are checked. BUREAU_NO_MERGE=1 preserves the review boundary in background code review/merge entry points.

BUREAU_CODEX_USAGE_FILE supplies an operator-provided Codex signal (pct, reset_epoch, updated_epoch). A shared BUREAU_USAGE_FILE is usable by Codex only when tagged "provider":"codex". Claude retains its legacy/ClaudeWatch sources. No signal means unknown usage and dispatch proceeds; provider quota failures are classified separately. Bureau does not scrape private Codex account files. The app's account-usage tool is independent of CLI token evidence.

Cost logs keep available CLI estimates separate from actual billed dollars (null). Missing Codex costs are never reported as zero. bureau-status.sh --cost displays unavailable when a total includes unknown values.
