The four known fixes

1. CI-skip-marker guard — CORRECTED: two different fixes, in two different trees, neither complete

The brief treats sanitize_ci_markers and squash-marker-check.sh as one fix. They are two independent answers to the same incident class, and they live in different installations.

  • installation A — detect and halt. scripts/squash-marker-check.sh (125 lines) reads every commit message in <base>..HEAD and reports any line matching scripts/ci-skip-markers.txt (7 markers). check_squash_range() in bureau-config.sh wraps it and distinguishes three outcomes — clean, found (exit 3), and unchecked (any other exit, which also halts: "halting rather than passing it on unchecked"). implement-pipeline.sh:186 raises a CI_MARKER halt state before hand-off; comment_on_branch_pr() posts the finding on the PR. Installation A also removed the marker injection entirely — implement-pipeline.sh there contains no [skip ci] amend at all. Origin: EXP-1462 / EXP-1465, explicitly dated and narrated.
  • installation B — neutralise at the merge. scripts/merge-body.sh defines sanitize_ci_markers() (defangs all 7 GitHub-honoured forms case-insensitively, idempotently, byte-identical when no marker is present) and build_merge_body() (never returns empty → the caller never falls back to GitHub's commit-list default). Sourced by merge-pipeline.sh:8 and code-review-pipeline.sh; used at merge-pipeline.sh:404 and code-review-pipeline.sh:479. Origin: EXP-1318 / B38, with the evidence cited inline ("Beleg 6/6, 29.07.").
  • Template — neither, and it manufactures the hazard. implement-pipeline.sh:513-514 amends [skip ci] onto every iteration commit; merge-pipeline.sh:366 runs gh pr merge "$PR_NUMBER" "--$BUREAU_MERGE_STRATEGY" with no --subject/--body. GitHub then composes the squash message from the branch commit list, finds the marker, and creates no CI run for the push to main.

Cost of the gap: the template as shipped can land unverified code on main silently. Installation A is safe because it neither injects nor tolerates the marker; installation B is safe at the merge but still injects at implement-pipeline.sh:527-528, so its protection depends entirely on merge-body.sh being sourced — and its rebase branch (merge-pipeline.sh:408) is explicitly outside the guarantee.

  • installation B — client-side strict priority. _resolve_label_id() at bureau-config.sh:594 fetches first: 20 with team { key } and selects in order: the issue team's own label, else a workspace-level (team == null) label, else nothing. bureau_load_env parses rather than executes, and carries three hardenings beyond the obvious one, each traceable: it disables a running set -x before the first expansion and restores it on every return (no secret reaches a trace); it restricts assignment to an allowlist (bureau_env_key_allowed); and it accepts values for the six arithmetic-bound keys only as 0 or leading-zero-free digits (bureau_env_key_numeric), because bash re-evaluates variable content inside $(( )), so KEY=x[$(cmd)] would execute cmd in the reading script — the last remaining path from a .env value to a command. Leading zeros are rejected specifically because bash reads 08 as octal and aborts. Written for bash 3.2 (no local -, no declare -g). Origin: EXP-1469, extended by EXP-1478.

Cost of the gap: in template and installation B, a single KEY= value line in .env executes value as a command, and bash echoes it in the "command not found" message — into a log that reaches Linear or GitHub.

Structural gap: the newer runtime

The template is Bureau v2.0.0 (tag v2.0.0, commit d7fd2d6, 2026-09-07). It contains 14 files that exist in neither installation:

bureau-runtime.py (488) · bureau-worker.sh (51) · bureau-supervision.py (207) · bureau-provider.py (249) · bureau-doctor.py (167) · bureau-monitor.py (30) · bureau-tick.sh (104) · bureau-app.sh (22) · bureau-stage.md · bureau-schedule.mjs · bureau-schedule-cli.mjs · bureau-implement.schema.json · bureau-qa.schema.json · bureau-review.schema.json

The ownership model is real and implemented, not merely documented. bureau-runtime.py holds a Store class whose state is <git-common-dir>/bureau/leases.json, guarded by fcntl.flock(LOCK_EX) (line 79), with claim / release / assert_owner / finish_execution and a workers/ registration directory keyed by a SHA-256 of the resolved workspace path. App leases deliberately carry no TTL. bureau-worker.sh re-execs itself through bureau-runtime.py … exec before touching the worktree, so ownership is claimed before any reset, and its EXIT trap preserves unfinished work rather than resetting over it.

Neither installation runs this, and neither runs a substitute. There is no bureau/ directory in either repo, no leases.json, no flock, no O_EXCL, no lock directory. The only occurrences of the word "lease" in either installation are the English words "release"/"released" in unrelated comments. Both run the pre-v2 shape: shepherd.sh and queue-loop.sh call reset_worktree directly and then cd "$wt" + bash scripts/<pipeline>.sh — no claim, no registration, no assertion. Concurrency safety rests entirely on free_branch_from_other_worktrees and the max_concurrent_issues cap.

What adoption would mean. Both installations are on config schema v1 (.bureau.json version: 1); the v2 runtime reads v2 keys with v1 fallback (start-bureau-v2.sh uses .agents.workbench_runner // .agents.runner // "claude"), and the skill README states v1 configs remain supported with an optional migration. So adoption is a /bureau-init --resync-scripts plus an optional schema migration — not a rewrite. The real cost is that a resync would overwrite the 23 shared scripts and destroy every local hardening listed above unless those are carried upstream first. That ordering is the whole decision.

Neither installation ever attempted a resync. Each was scaffolded exactly once and never refreshed: installation B at fd5c7da "Foundation: Trichter-Basis + Bureau-Pipeline (EXP-1270)", 2026-07-20; installation A at a56bf7d/5dd6dbb "chore(bureau): pipeline scaffold for the core fork (bureau-init, speckit 0.7.5)", 2026-09-04. git log --all --grep='resync|bureau-init|v2.0.0|upstream' -i returns no other commit in either repo. So the old shape is inheritance, not rejection — installation A was scaffolded three days before the v2.0.0 tag existed and has stayed on the pre-v2 template while actively developing against it (last scripts/ commit 2026-09-21, EXP-1478). Installation B's last scripts/ commit is 2026-08-21; it is effectively frozen.
