# Bureau v3.0.2 — every stage reads the ticket's own spec, and a Python venv in every worktree

**Stable release · 2026-09-29 · source tag `v3.0.2`.** The [GitHub Release](https://github.com/KaiaK808/bureau/releases/tag/v3.0.2) records the exact tagged commit. v3.0.2 is a patch release on [v3.0.1](release-notes-v3.0.1.md), which patches [v3.0.0](release-notes-v3.0.0.md); it fixes how the stages find a ticket's spec and adds one opt-in setting. The candidates of v3.0.0 were [v3.0.0-rc.2](release-notes-v3.0.0-rc.2.md) and [v3.0.0-rc.1](release-notes-v3.0.0-rc.1.md); the previous major release is [v2.0.0](release-notes-v2.0.0.md).

The exit codes keep their meaning. A stage that finds no spec directory for its ticket ends as it already did: implement and spec review with `13` back to Spec, UX with `13` back to Spec Review; QA, review and copy continue without spec context. New: when two directories fit a branch equally, implement, spec review and UX say so, name both, and set `needs-human` as they route back.

## What changed

- **Every stage finds the ticket's own spec directory** ([#29](https://github.com/KaiaK808/bureau/pull/29)). Spec directories and branches share the form `NNN-<slug>`, but the number is not unique: some installations mint `001-<slug>` for every ticket, others repeat a number now and then, and hand-made branches reuse the number of an unrelated spec.
  - Implement matched the number first and took the first alphabetical `NNN-*/tasks.md`. In an installation whose spec directories all start with `001-`, every ticket was built from the same, wrong tasks: in a replay of that installation's history, v3.0.1 implement found the right directory for 5 of 41 bureau-generated pull requests (against the listing each one saw), the new function for all 41.
  - QA, review, copy, UX and spec review matched the directory's slug as a loose substring of the branch, so `001-refund` won over `001-refund-rate`; spec review and UX fell back to the newest directory when nothing matched, and the spec stage always used the newest directory for its crosscheck and digest. In a fresh worktree every directory has the same age.
  - All of them now call `bureau_spec_dir_for_branch` in `bureau-config.sh`. The branch first loses everything up to its last `/` (`codex/`, `exp/`, a user name) and a leading issue key such as `exp-1444-`. Then: a directory named exactly like the branch or its last segment; else the one directory whose slug fits the branch slug — equal, the branch slug as its start up to a `-` (a truncated branch name), or a run of whole `-`-separated words inside the branch slug (a branch with extra words); when several fit, the one of them that carries the branch's number. A number alone never selects a directory. Anything ambiguous yields no directory; slugs compare case-insensitively, as before.
  - When two directories fit equally, implement, spec review and UX comment with both names (`bureau_spec_dir_candidates`), set `needs-human` and route back: running Spec again cannot resolve that.
  - The spec stage uses the directory `.specify/feature.json` names for plan, tasks, crosscheck and digest, and tells the agent to work on that directory instead of "the most recent spec".
  - The implement part was first written in June 2026 on a branch that never reached `main`, from a hand-patch in one installation; this release carries it, extends it to every stage and to prefixed branch names, and drops its number-only fallback.
- **Stage worktrees get their virtualenv back** ([#30](https://github.com/KaiaK808/bureau/pull/30)). `reset_worktree` ends with `git clean -fdx`, which removes every ignored path from a stage worktree; only `node_modules` came back. In a Python installation the agents' own commands (`.venv/bin/python -m pytest` from a spec) failed and tickets were parked for a human.
  - New `repo.worktree_links`, a list of relative paths such as `[".venv"]`: after every reset, each is symlinked from the main checkout into the stage worktree (`bureau_link_worktree_paths`). Empty by default, which changes nothing.
  - A path is skipped with one warning line when the entry is not a plain relative path (absolute, `.`, `..`, `.git` in any case, or an empty component; a leading `-` is fine), when the branch tracks it, when its parent is missing in the worktree, leads outside it or runs through a symlink in it, when it does not exist in the main checkout, when the worktree's gitignore does not ignore it as a symlink, or when a real file or directory is at that path; an older link is replaced. The next reset removes the link, never its target. The main checkout itself, worktrees of a bare repository and repositories whose git directory is kept elsewhere (`--separate-git-dir`) are never linked.
  - A directory-only pattern such as `.venv/` does not match a symlink; an untracked link would leave the worktree dirty, the worker would preserve it and the next reset would stop with `21`. List `.venv` in `.gitignore` without the slash. `bureau-doctor.py` reports each entry with its status, checks it the way a stage worktree sees it, and flags what the stages would skip.
  - **The link is the main checkout's own virtualenv, not a copy.** Every stage and every parallel worker shares it, and commands in a stage worktree act on it: `python3 -m venv --clear .venv` empties it, `rm -rf .venv/` (with the slash) deletes it, `pip install` changes it, and pull-request code that QA or the review build check runs before approval can change the environment every later stage and the operator use. The system text of every stage call (`run_stage_for`, from the main checkout, so in force from the first reset) and, at more length, `scripts/bureau-stage.md` tell the agents: a path such as `.venv` that is a symlink pointing outside the worktree is the main checkout's shared environment — never delete, recreate or `--clear` it, and do not install into it unless the ticket asks; a missing path or a real directory is handled as usual. Nothing enforces that.

See the [changelog](https://github.com/KaiaK808/bureau/blob/v3.0.2/CHANGELOG.md) for the full entries, [configuration](https://github.com/KaiaK808/bureau/blob/v3.0.2/docs/configuration.md#python-repositories) for `repo.worktree_links` and [troubleshooting](https://github.com/KaiaK808/bureau/blob/v3.0.2/docs/troubleshooting.md) for how to check what a stage will pick.

## Upgrade an existing installation

From **v3.0.1**: select tag `v3.0.2` in the source skill checkout and resync the scripts scope as one set. No configuration change is required. An installation whose spec directories repeat an `NNN-` prefix is affected and should resync before its next implement run; check with `ls specs | cut -d- -f1 | sort | uniq -d` (use `repo.specs_dir` if it is not `specs`). A matcher patched by hand into `implement-pipeline.sh` shows up as a conflict; take the template, the shared function replaces it. After the resync, a branch that fits two spec directories equally stops with `needs-human` instead of picking one — rename or remove the stray directory, then remove the label. A hand-made branch that reuses the number of an unrelated spec and shares no word with any spec directory now runs without a spec directory (implement stops with `13`) instead of receiving that spec.

For a Python installation whose agents need the virtualenv in the stage worktrees, first commit the resynced scripts to `main` (so the stage protocol the agents read in their worktree carries the rule), then add `"worktree_links": [".venv"]` under `repo` in `.bureau.json`, list `.venv` (without a trailing slash) in `.gitignore`, and check `python3 scripts/bureau-doctor.py`: it shows each link as `ok`, `missing in the main checkout`, `tracked in the main checkout`, `not ignored as a symlink` or `invalid`. Decide first whether sharing the main checkout's virtualenv with the stages is acceptable (see above); if not, leave it out and let `repo.test_command` create what the tests need. With an editable install (`pip install -e .`) the linked virtualenv imports the main checkout's `src/`; run the worktree's tests with `PYTHONPATH=src` (see [Python repositories](configuration.md#python-repositories)). Copying `.env` or `.bureau.json` into worktrees is not needed: the stages find both through the main checkout.

From **v3.0.0 or v3.0.0-rc.2**: select tag `v3.0.2` and follow the v3.0.1 notes for the merge stage's exit codes as well ([upgrade section](migration.md#upgrade-to-v3)). From **v3.0.0-rc.1, v2.0.0 or a legacy copy**: follow the [v3 upgrade section](migration.md#upgrade-to-v3) with tag `v3.0.2`.

## Compatibility and rollback

Dependencies and platforms are unchanged (Python 3.9+, Bash 3.2+, Git 2.26+, jq, curl; Node.js 18+ for the shared scheduler; Linux and macOS). Configuration schema versions 1 and 2 stay supported, and the manifest stays at version `1`. To roll back to v3.0.1, point the source at tag `v3.0.1` and resync the scripts scope, or restore the private backup ([rollback](migration.md#rollback)); that brings the old matchers back, and `repo.worktree_links` is then ignored (the links an older reset made are removed by the next reset). Rollback cannot undo commits, pull requests or Linear transitions made in between; the caveats of [v3.0.1](release-notes-v3.0.1.md#compatibility-and-rollback) still apply.

## Validation and known limitations

v3.0.2 is validated by the full Linux/macOS suite on the release commit, the installer fixtures and an independent verification pass per pull request, each followed by a fix round.

- **Spec directory.** The matching rules were checked against a replay of 1,889 real branch/listing pairs from eight installations (every pull request and remote branch, against the listing at its head and at `main`): the new function is right in 1,858, v3.0.1 implement in 1,649 and v3.0.1's loose match in 1,852, with no row where either v3.0.1 matcher was right and the new one is not. The number-only fallback of the June fix was right in no row that nothing else got right and wrong in 7, so it was dropped. The matcher test cuts the functions out of the shipped `bureau-config.sh` and checks 48 cases; it fails against the v3.0.1 implement matcher, the old loose match, the June fix and the first version of the pull request, and 18 of 18 mutations turn it red, including three substring mutations the verification found surviving at first. A second test runs the seven affected stages in the harness against decoy spec directories that sort first, fit as a substring and are newer, plus the tie path of implement, spec review and UX; each stage reverted alone turns it red.
- **Worktree links.** The guard test runs the real function with a main checkout path containing a space: every guard with its effect on disk and in `git status`, an older link, a real directory in the way, glob-like names, nested paths, an entry starting with `-` under `set -euo pipefail`, a parent through a symlink, a bare repository, a separate git directory. A further test sends a prompt through the real `run_stage_for` and provider and checks that Claude and Codex both receive the rule in the stage's system text. An end-to-end case goes through the real `reset_worktree` twice (link present, worker clean, target survives) and once under `set -euo pipefail`; a doctor case covers every status. Both fail against v3.0.1, and 28 of 28 mutations turn them red. The verification also found that no reset, clean or merge cycle writes to the main checkout or its virtualenv, and that installations without the key behave byte-for-byte as on v3.0.1.

**No live ticket has run on v3.0.2 yet.**

Known limitations (in addition to those of [v3.0.1](release-notes-v3.0.1.md#validation-and-known-limitations)):

- A linked virtualenv is the main checkout's own and is shared by all stage worktrees (see above). A copy mode, as `restore_worktree_deps` uses for `node_modules`, does not exist.
- `.specify/feature.json` missing or malformed makes the spec stage abort with jq's exit code before its exit-11 message; a stale `feature.json` (tracked on `main`, kept per branch) is accepted without a staleness check.
- The interactive `/linear-implement` command still tells the agent in words to find "the spec that matches the Linear issue"; it does not call the shared function.
