# Upgrade, migration and rollback

An upgrade that refreshes installed assets has two steps: update the **Bureau source skill**, then resync its assets into **each adopting repository**. Updating the source clone alone leaves installed scripts and commands unchanged. `/bureau-init --update` edits configuration; it does not upgrade installed assets.

This guide upgrades installations from the official [KaiaK808/bureau](https://github.com/KaiaK808/bureau) source: legacy untagged installations, v2.0.0 installations, the v3 release candidates, v3.0.0, v3.0.1, v3.0.2, the v3.1 release candidates, v3.1.0, the v3.2 release candidate, v3.2.0, v3.2.1 and the v3.3 release candidates to the stable **Bureau v3.3.0**. The commands below require the selected release's source skill. See the [v3.3.0 release](https://github.com/KaiaK808/bureau/releases/tag/v3.3.0) and its [release notes](release-notes.md) (the candidates: [v3.3.0-rc.2](release-notes-v3.3.0-rc.2.md), [v3.3.0-rc.1](release-notes-v3.3.0-rc.1.md)), the previous stable [v3.2.1 release](https://github.com/KaiaK808/bureau/releases/tag/v3.2.1) and its [release notes](release-notes-v3.2.1.md), the [v3.2.0 release](https://github.com/KaiaK808/bureau/releases/tag/v3.2.0) and its [release notes](release-notes-v3.2.0.md) (the candidate: [v3.2.0-rc.1](release-notes-v3.2.0-rc.1.md)), the [v3.1.0 release](https://github.com/KaiaK808/bureau/releases/tag/v3.1.0) and its [release notes](release-notes-v3.1.0.md) (the candidates: [v3.1.0-rc.2](release-notes-v3.1.0-rc.2.md), [v3.1.0-rc.1](release-notes-v3.1.0-rc.1.md)), the [v3.0.2 release](https://github.com/KaiaK808/bureau/releases/tag/v3.0.2) and its [release notes](release-notes-v3.0.2.md), the [v3.0.1 release notes](release-notes-v3.0.1.md), the [v3.0.0 release notes](release-notes-v3.0.0.md) (the candidates: [v3.0.0-rc.2](release-notes-v3.0.0-rc.2.md), [v3.0.0-rc.1](release-notes-v3.0.0-rc.1.md)), the previous major [v2.0.0 release](https://github.com/KaiaK808/bureau/releases/tag/v2.0.0) and its [release notes](release-notes-v2.0.0.md), the [changelog](../CHANGELOG.md) and the [release process](releases.md). A Bureau major version marks operational changes (v2.0.0: explicit worker ownership; v3: the exit-code contract, see [Upgrade to v3](#upgrade-to-v3)); it does not require configuration schema v2. v3.1, v3.2 and v3.3 keep that contract; see [Upgrade to v3.1](#upgrade-to-v31), [Upgrade to v3.2](#upgrade-to-v32) and [Upgrade to v3.3](#upgrade-to-v33).

## Select the source release

First update the actual source clone that supplies `/bureau-init`. Its usual location is `~/.claude/skills/bureau-init`, but it may be a symlink or installed elsewhere. Check the loaded skill location; do not pull the adopting project's repository by mistake.

In a terminal, inspect the source checkout:

```sh
BUREAU_SOURCE="$HOME/.claude/skills/bureau-init" # replace with the actual loaded skill path
git -C "$BUREAU_SOURCE" status --short --branch
git -C "$BUREAU_SOURCE" remote -v
git -C "$BUREAU_SOURCE" describe --tags --always --dirty
git -C "$BUREAU_SOURCE" rev-parse HEAD
```

For a Codex-only install, the entry point may be `~/.agents/skills/bureau-init` or a configured skill directory. Follow its link to the actual source clone. Record the previous commit and branch/tag privately for rollback; `describe` alone may name a nearby tag instead of the installed commit.

Confirm that `origin` identifies the official `KaiaK808/bureau` repository (HTTPS or SSH). Preserve local source changes before continuing; do not reset the skill clone. With a clean checkout, select the exact release (`v3.3.0` for the stable release, `v3.2.1` for the previous stable release, `v3.2.0`, `v3.1.0`, `v3.0.2`, `v3.0.1`, `v3.0.0` or `v2.0.0` for an earlier one):

```sh
BUREAU_RELEASE=v3.3.0 # or v3.2.1, v3.2.0, v3.1.0, v3.0.2, v3.0.1, v3.0.0, v2.0.0
git -C "$BUREAU_SOURCE" fetch origin tag "$BUREAU_RELEASE" &&
git -C "$BUREAU_SOURCE" switch --detach "refs/tags/$BUREAU_RELEASE" &&
git -C "$BUREAU_SOURCE" rev-parse HEAD
```

Stop if fetching fails, especially if an existing local tag conflicts with the remote; do not force-replace it. Compare the resulting commit with the commit recorded in the GitHub Release and record it for rollback. This leaves the source on a detached release checkout. A later release upgrade repeats these steps with that release's tag; it does not use `git pull`.

An intentionally `main`-tracking installation can instead use `git pull --ff-only` when its checkout is clean and its upstream is the official `origin/main`. This follows ongoing development rather than pinning a release. If the source is an archive-origin checkout, an unrelated history or a plain copied directory, keep it intact and install a separate official clone from the [installation guide](../README.md#install); review how the loaded skill entry point should move before replacing any link. Do not merge unrelated histories or change the old checkout's remote as an upgrade shortcut.

## Upgrade to v3.3

The stable release **v3.3.0** is a minor release on v3.2.1 and keeps the v3 exit-code contract. It collects two pull requests: the implement gate and private temporary directory for Codex calls without `TMPDIR` ([#60](https://github.com/KaiaK808/bureau/pull/60)), and the QA gate ([#62](https://github.com/KaiaK808/bureau/pull/62)). Claude runs are unchanged. See its [release notes](release-notes.md) for validation and known limitations; its candidates, [v3.3.0-rc.2](release-notes-v3.3.0-rc.2.md) and [v3.3.0-rc.1](release-notes-v3.3.0-rc.1.md), stay published as prereleases, and runtime, installer, templates and tests are identical to rc.2.

**From v3.3.0-rc.2:** select tag `v3.3.0`; no resync is needed, because the runtime is identical (the manifest keeps naming rc.2 as its source until the next resync). There are no file changes beyond what rc.2 had.

**From v3.3.0-rc.1:** select tag `v3.3.0` and resync the **scripts scope as one set** (`--resync-scripts`); `qa-pipeline.sh`, `bureau-config.sh` and `bureau-provider.py` changed together in rc.2. Pause dispatch, preserve unfinished work and customized files, and use [preview and resolve](#preview-and-resolve-asset-conflicts). No configuration, interface or schema migration is needed.

**From v3.2.1:** select tag `v3.3.0` and resync the **scripts scope as one set** (`--resync-scripts`); `implement-pipeline.sh`, `qa-pipeline.sh`, `bureau-config.sh` and `bureau-provider.py` changed together. Pause dispatch, preserve unfinished work and customized files, and use [preview and resolve](#preview-and-resolve-asset-conflicts). No configuration migration is needed; `/bureau-init --update` changes configuration only.

**From v3.1.0 or older:** go through [Upgrade to v3.2](#upgrade-to-v32) and its earlier upgrade steps first, including both the scripts and interfaces scopes and the applicable configuration checks, then follow the v3.3 steps above.

For Codex implement and QA, check that `repo.test_command` holds the full project gate, including the tests the sandbox can deny. For implement, a missing command or a branch with no commits beyond `origin/main` keeps `NEEDS_HUMAN`; a qualifying `SANDBOX_GATE:` result proceeds through the hook and squash-range checks, then the command runs once outside the sandbox after the final push. Green hands off to QA or Build Review, and red keeps the ticket labelled `needs-human`.

Restart queue loops and supervisors after the resync so they read the new scripts: a loop sources `bureau-config.sh` once at startup, and a stage already running keeps the old scripts because the installer replaces files atomically. Run doctor (`python3 scripts/bureau-doctor.py --mode background`) and qualify a representative ticket before dispatch resumes. The implement gate passed a live run in an installation; live QA acceptance remains pending (see [validation](release-notes.md#validation)). Rollback selects tag `v3.2.1` again and resyncs the scripts scope as one set ([rollback](#rollback)); no data migration is needed.

**Operator output:** the implement summary comment records `needs-human names only SANDBOX_GATE reasons: treated as COMPLETE until the shell gate outside the Codex sandbox decides`, followed by `shell gate outside the Codex sandbox green: the run continues as COMPLETE` or `shell gate outside the Codex sandbox red: NEEDS_HUMAN stays`; a missing command or no commits records why `NEEDS_HUMAN` stays.

**QA operator output:** a qualifying `SANDBOX_GATE:` result puts `shell gate outside the Codex sandbox green: QA continues as GREEN` or `shell gate outside the Codex sandbox red: QA continues as RED` first in the QA summary comment; the existing final outside run decides Build Review or Build, with no extra test run or `needs-human` label, unless the squash-range check then holds the ticket and puts its report first.

## Upgrade to v3.2

The stable release **v3.2.1** is a patch on [v3.2.0](release-notes-v3.2.0.md) that removes internal references without behaviour change. v3.2.0 is a minor release on v3.1.0 and keeps the v3 exit-code contract. The [v3.2.1 release notes](release-notes-v3.2.1.md) include the patch, the eleven v3.2 pull requests, validation and known limitations; the v3.2.0 candidate was [v3.2.0-rc.1](release-notes-v3.2.0-rc.1.md).

**From v3.2.0 or v3.2.0-rc.1:** select tag `v3.2.1`; a resync is optional because the scripts and interfaces change only in comments, help texts and example values, with no behaviour change. Installers will report those files as updates. To receive the cleaned text, resync the scripts and interfaces scopes (`--resync-interfaces --resync-scripts`) using [preview and resolve](#preview-and-resolve-asset-conflicts). No configuration change is required; without a resync, the manifest keeps naming the previously installed source.

**From v3.1.0:** select tag `v3.2.1` and resync the **scripts scope and the interfaces scope as one set** (`--resync-interfaces --resync-scripts`). The scripts depend on each other: `bureau-env.sh`, `bureau-config.sh`, `bureau-runtime.py`, `bureau-provider.py`, `bureau-supervision.py`, `bureau-doctor.py`, the stage scripts, `shepherd.sh`, `bureau-worker.sh`, `bureau-status.sh`, `bureau-app.sh`, `bureau-tick.sh`, `crosscheck-specs.sh`, `grab-issue.sh`, `complete-issue.sh`, `queue-loop.sh` and `queue-loop-supervised.sh` among them. A v3.1 supervision helper rejects the new gate-wait arguments, leaving no records and turning retries into full paid reviews; a partial scripts resync is not a working runtime. [#46](https://github.com/KaiaK808/bureau/pull/46) also changes `templates/commands/linear-implement.md` and `templates/scripts/bureau-stage.md`, so include the interfaces. Pause dispatch, preserve unfinished work and customized files, and use [preview and resolve](#preview-and-resolve-asset-conflicts) instead of a blanket overwrite; `/bureau-init --update` changes configuration only. From a v3.1 candidate or older release, go through [Upgrade to v3.1](#upgrade-to-v31) and the earlier sections too, selecting `v3.2.1` and both scopes.

Before the resync and before dispatch resumes, check every item that applies:

- **Git LFS before resync:** set `repo.remote_git_runs_hooks: true` in `.bureau.json` for a repository that tracks files with LFS; its pre-push hook uploads the objects, and v3.2's default leaves them off the remote. Doctor warns when the main checkout uses `filter=lfs` in the top-level `.gitattributes`, a nested `.gitattributes` git lists (tracked, or untracked and not ignored), or `.git/info/attributes`, without the JSON value `true`; it does not read an operator's global `core.attributesFile`. Run doctor after the resync. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **The operator's `.env` location:** every script now reads only `BUREAU_ENV_FILE`, by default the `.env` next to `.bureau.json` in the main checkout. Move an operator file kept elsewhere there or set `BUREAU_ENV_FILE`; a relative value counts from the directory `BUREAU_CONFIG` names, without resolving a link, and an absolute value stays absolute. The scripts export the resolved absolute path so a runtime relaunch reads the same file; branch code under the default `repo.untrusted_env` sees that path (no secret), while `clean` drops it. A branch's tracked `.env` is unread, and a different `.env` next to `.bureau.json` no longer overrides an explicit `BUREAU_ENV_FILE` for the queue or a stage in the main checkout. Doctor follows the same rule for `BUREAU_RUNNER_IMPLEMENT`. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **Unexported keys:** children of stages and drivers no longer see `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN` or `TELEGRAM_ALERT_CHAT_ID` from `.env`. Bureau scripts read the file themselves; a custom script that used those exports must read it too. A key set only in the shell environment that starts Bureau is left as it is and reaches its children; keep the keys only in `.env` to get the protection. The runtime parses the file with the allow-listed reader instead of sourcing it, so shell code in `.env` no longer runs there. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **Shell options and tracing:** Bureau switches `allexport` off, also when inherited through exported `SHELLOPTS`. A traced run (`bash -x`, or inherited `xtrace`) still works and no longer prints the keys; an installation's own script that handles a key must hide it from its trace itself. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **Remote hooks and checks:** Bureau's push, fetch and other remote git commands no longer run hooks in the repository's hooks directory, configuration-defined hooks on git 2.54 and later, or hooks from global configuration. A pre-push check (husky, lefthook, the pre-commit framework or a global secret scanner) no longer checks Bureau's push by default; arrange for CI to run it, or deliberately set `repo.remote_git_runs_hooks: true`, which restores hooks with the GitHub tokens. Local git hooks still run without the tokens as in v3.1. A configuration hook with an event but no command no longer stops Bureau's push, because its name is disabled too. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **Git wrappers:** code that assumes git's first argument is its subcommand must skip the new leading `-c core.hooksPath=/dev/null`, 28 `-c hook.<event>.enabled=false` switches and the shell's per-name `-c hook.<name>.enabled=false` (or `--config-env` for a name with `=`). Supervision's `ls-remote` also carries the core and event switches. Each shell remote command first lists configured hook names with `git config --name-only --get-regexp '^hook\..*\.(command|event)$'`, without an inherited `GIT_CONFIG`. ([#49](https://github.com/KaiaK808/bureau/pull/49))
- **Python isolation:** supervision's eight calls, the reset's ownership check, `bureau-status.sh` and `bureau-app.sh` now start Python with `-I` too. These helpers ignore `PYTHON*` variables (`PYTHONPATH`, `PYTHONHOME`, `PYTHONIOENCODING`, …) and user site-packages; none needs them. ([#47](https://github.com/KaiaK808/bureau/pull/47))
- **Linked-directory doctor errors:** a `repo.worktree_links` directory containing a `.env*` name anywhere below it is now an error (`holds an env file`, naming the first hit); an incomplete search, including a missing `find`, is an error too (`not searched completely`, `ok: false`, exit 1). The stages already skipped these links in v3.1; remove the entry or move the `.env*` file out. A large directory is searched once per doctor run with no depth limit, as the stages search it at each reset. The rule matches names, not the target of a differently named file link; GNU find fails on a link loop, BSD find on macOS skips it. ([#47](https://github.com/KaiaK808/bureau/pull/47))
- **Test-command warning:** doctor warns about missing `repo.test_command` (absent, null, false or empty) only where implement resolves to Codex, including a runner selected only by `BUREAU_RUNNER_IMPLEMENT` in `.env`, and even with implement off because the shepherd can force it on. Claude implement installations no longer see it. Doctor reads only that runner key from the file, never executes it, and its effective-settings report still resolves JSON and the process environment. ([#47](https://github.com/KaiaK808/bureau/pull/47))
- **Implement timeout budget:** passes that time out can now run up to `BUREAU_IMPL_MAX_ITER` (default 3), bounded together by `BUREAU_IMPL_TOTAL_TIMEOUT` (default 5400 s), where v3.1 ended after the first `BUREAU_IMPL_ITER_TIMEOUT` (default 1800 s). `BUREAU_IMPL_MAX_ITER=1` permits one pass of any kind; a total timeout equal to the iteration timeout also caps a productive multi-pass run at one pass's time. A timed-out pass goes through the squash-range check and push like any pass, including the last one; when no pass is left the stage still ends with 124. ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **Failed and interrupted implement pushes:** every way out before the end-of-run push now tries to push what origin lacks in both `agents.implement.push_each_iteration` modes, including the running first pass: a failed provider call, a timed-out last pass, and through the EXIT trap a signal, crash, unusable Linear or failed `/goal` run. v3.1 only pushed returned passes' held-back commits with `false` and an open PR. A failed push is loud, leaves work in the preserved worktree and keeps the original code; stderr gone no longer replaces it with 141. On a stop the push shares the stage's process group and existing stop grace. The trap is armed after the stage merges `origin/main`, so a stop before an implementation commit pushes that merge alone; with `false` and an open PR such a way out can cost one CI run (`pull_request: synchronize`). ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **After a timed-out pass:** the next pass checks the branch and task list first; in a rework it reports `COMPLETE` only when the feedback above is addressed too. Codex leaves Git to the shell; Claude is told to commit work the stopped pass left and to remove `index.lock` only when no git process has the worktree as its working directory, otherwise report `NEEDS_HUMAN` naming the lock. A detached Bash tool shell of the timed-out Claude pass can still hold a live git process. ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **The stage CI rule:** every agent stage now stops once its own work is done instead of waiting for, polling or re-triggering CI or a merge gate, or committing CI results as evidence, even if the repository's CLAUDE.md or AGENTS.md asks it to wait. Missing, pending or failed CI does not decide the status it reports for its work; waiting stays with the merge gate and shepherd. Background stages get the rule from the main checkout's resynced scripts immediately; app stages read it once `scripts/bureau-stage.md` is committed. `/linear-implement` asks for passing tests instead of passing checks. ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **Provider evidence:** `logs/provider-runs/RUN/result.json` gains `session_id`, `transcript`, `transcript_found`, and `transcript_note` when no id is known; the stage log gains `Bureau provider transcript: …`. Claude gets a fresh `--session-id` if supported; otherwise it runs as before without it. `logs/provider-runs/.claude-cli.json` caches the help answer; deleting it is harmless, a downgrade behind an unchanged wrapper is retried without the flag immediately, and an upgrade is picked up within a day. Codex's thread id names its rollout file; a missing transcript does not fail the call. ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **Rework feedback:** QA RED, QA NEEDS_HUMAN, review BLOCK and app-runtime `VERDICT: BLOCK` now reach implement alongside Changes Requested and `FIXES_NEEDED`; v3.1 comments count too, and the newest finding wins. An approval, QA PASSED or halt comment does not retire an older finding; before a restart from build, or a build pass after review/QA returned to Build without a finding, write a later `FIXES_NEEDED` if the pass should use a different list or have nothing to fix. A QA bounce with every task checked still hands to QA without a commit as before; the prompt now includes its findings. The feedback label is `--- Feedback to address (PRIORITY) ---`, with “Address ALL fixes before remaining tasks.” kept. ([#53](https://github.com/KaiaK808/bureau/pull/53))
- **Queued CI grace:** a check with status `queued` past `agents.merge_ci_queued_grace_seconds` (default 3600 s, from the check run's `started_at`) now blocks the gate with 25: the queue alerts hourly per ticket, an inline merge sets `needs-human`, and the shepherd halts. On a single self-hosted runner, measure the jobs' `created_at` → `started_at` waits before keeping the default; readings so far include about 15 minutes for the third run in a busy queue and once 13 minutes queued on an idle runner. A runner outage longer than the grace blocks approved PRs waiting on it; `0` blocks at once, `9999999` keeps v3.1's behaviour. Only `queued` counts; a running check, deployment approval, concurrency wait, pending commit status or unreadable time stays “not yet”. ([#48](https://github.com/KaiaK808/bureau/pull/48))
- **Review and merge picker holds:** while origin stays at the judged head, a ticket with an undecided gate, or a gate blocked at the merge stage without `needs-human`, goes after other candidates of that stage for two poll intervals (at least 300 s), doubling to `agents.merge_gate_recheck_seconds` (default 3600). Alone it is still picked each poll. A push, a deleted remote branch or a future record time ends the hold; an unreadable record or origin warns and holds nothing. Rebase is never held, and the shepherd's named ticket is not delayed by picker holds. A gate that turns green while other work waits can merge up to one hold later; lower the cap or set `0` for every poll, or run that ticket's stage or shepherd for an immediate check. With a poll interval of an hour or longer the default cap is shorter than two intervals and nothing is held; raise it to at least two intervals there. ([#48](https://github.com/KaiaK808/bureau/pull/48))
- **Old records and build-check reuse:** v3.1 gate-wait records have no count, build check or key, count as the first wait and run the build check once more. A v3.2 gate-wait approval keeps a passed check for the same head, base and key (command, `repo.untrusted_env`, `repo.worktree_links`), so its next retry skips the check; a changed key or other reused approval runs it, and a red check is never recorded as passed. Doctor warns when either new gate number is not a plain whole number. Gates not covered by the queued grace (PR hold, required human review, pending commit status, deployment approval) remain “not yet” without an alert. ([#48](https://github.com/KaiaK808/bureau/pull/48))
- **Bounded ticks:** only an all-stage `bureau-tick.sh --allow-merge` now passes over a lone held Build Review or Merge ticket for another stage with work; no later stage of that tick takes it, including rebase. It comes back in stage order only if no other stage has work, or picks the ticket normally once the hold ends. `--stage`, the default `--no-merge` tick and the queue loop keep their behaviour; `logs/bureau-tick.json` still names only the stage and ticket that ran, with unchanged outcomes and codes. A usage throttle ends the tick with result `exit_code` 23 before it comes back, so a held Merge ticket waits for its hold, at most `agents.merge_gate_recheck_seconds`; a DIRTY held Merge ticket is never rebased by an `--allow-merge` tick (as in v3.1), while the queue loop still rebases it. `agents.merge_gate_recheck_seconds: 0` switches holds and passing over off. ([#54](https://github.com/KaiaK808/bureau/pull/54))
- **Hang-ups stop runs:** closing the terminal, ssh session, tmux window or session that runs a shepherd or queue now stops it with 130, preserved work, interrupted leases and the usual nested stop graces. Detaching tmux (`Ctrl-b d`) hangs up nothing; use tmux and detach, or `nohup`, to keep a run going when its terminal closes. No new key or exit code. ([#50](https://github.com/KaiaK808/bureau/pull/50))
- **Inner stops and kept leases:** a child's 130 now counts as interrupted at every runtime wrapper level, including a signal to the shepherd's or worker's group and a helper interrupted during a Linear read. The next pick meets kept leases with 21 and one `needs-human` comment until released; on a queue lane's shared `.worktrees/queue-<lane>` this blocks every ticket of that lane. A stop to the worker's group still produces a `shepherd halt (cancelled-run)` alert. After a hang-up `python3 scripts/bureau-runtime.py status` shows the interrupted leases, but does not check liveness: retry `python3 scripts/bureau-runtime.py release RUN_ID` until it no longer reports “Background process group still alive”, then follow [the resume steps](troubleshooting.md#shepherdsh-bailed-mid-run--how-to-resume) to save/push and drop or adopt the worktree before restarting. The runtime's printed step 1 still says `status`; use `release` as the documentation says. ([#50](https://github.com/KaiaK808/bureau/pull/50))
- **Signal the whole run:** for a manual stop signal the runtime's lease `pid`; use `kill -TERM -- -<pid>` only when the runtime leads its own process group, as [How to stop a run](troubleshooting.md#how-to-stop-a-run) explains. Stop a queue through its pane, session or supervisor's whole group; `kill -TERM <supervisor pid>` alone still leaves its stage running, as in v3.1. Implement's final EXIT trap now tries to push on a signal or dead log pipe in both modes (#46), within the existing grace. ([#50](https://github.com/KaiaK808/bureau/pull/50), [#46](https://github.com/KaiaK808/bureau/pull/46))
- **Implement log watchers:** replace `pushing the deferred commits of <branch> (…)` with `pushing N commit(s) of <branch> that origin lacks before the stage ends (<why>)`, with reasons `provider exit X` or `the stage ends before its end-of-run push`. Every successful end-of-run/failure push confirms `pushed <branch> (<label>): N commit(s) origin lacked, head <sha>`; labels are `end of run`, `end of run, retry`, `provider exit X`, `the stage ends before its end-of-run push`, and `the run's commits, without the hook's rewrite`. An unreadable comparison says the count is unknown, and a dry run confirms nothing. Timeouts appear as `iter N: status=TIMEOUT … (timed out after Ss)`; a final 124 keeps the prefix `Provider pass failed with exit 124 (iter N timed out) and no pass is left: …`. ([#46](https://github.com/KaiaK808/bureau/pull/46))
- **Tick and feedback log watchers:** accept `tick: TEAM-123 waits on its merge gate and is the only code_review ticket that can be picked — passed over while another stage has work`, `tick: no other stage has work — back to code_review`, and `pick: TEAM-123 taken although it waits on its merge gate — no other ticket of the stage can be picked` (the stage can also be merge); the come-back line describes the retry, whatever it picks. Tooling that matched `--- Code Review Feedback (PRIORITY) ---` must follow the new `--- Feedback to address (PRIORITY) ---` label. ([#54](https://github.com/KaiaK808/bureau/pull/54), [#53](https://github.com/KaiaK808/bureau/pull/53))
- **Spec-state confirmation:** after a successful spec stage the shepherd now re-reads a moment-old intermediate Spec through the existing bounded confirmation before its bump to Triage; a real Spec returned by spec review costs no extra wait. The queue loop and tick do not bump, and no setting changes. ([#51](https://github.com/KaiaK808/bureau/pull/51))
- **Long stage text:** a research digest above roughly 64 KB with its marker near the top is now used and posted instead of dropped as “no valid output”; review no longer ends with 141 or 1 taking its verdict's first line, and upstream-port accepts long commit messages while still ending with 18 on a failing `gh`. **From v3.0.0-rc.1:** select tag `v3.0.2` and resync the scripts scope as one set; no configuration change is required. New optional settings are `repo.post_implement_command` (with `BUREAU_POST_IMPLEMENT_TIMEOUT`), `BUREAU_LINEAR_MAX_TIME` / `BUREAU_LINEAR_CONNECT_TIMEOUT` (or `.linear.request.max_time` / `.connect_timeout`) and `BUREAU_SHEPHERD_CONFIRM_SECONDS`; see [configuration](configuration.md). After the resync, a missing or invalid Linear key shows as `27` with an hourly queue alert, a stage whose `needs-human` label cannot be written ends with `25` and holds the ticket locally, a failed final implement push ends with `18` when origin lacks commits, the merge stage ends with `2` or `25` when it does not merge, and every stage finds the spec directory as described above. The rest of this section applies to an upgrade from v2.0.0 or a legacy copy.

v3 changes the exit-code contract between the stages and whatever drives them (the shepherd, the queue loop, ticks, wrappers and repository tests). Check anything that reads these codes before resuming dispatch:

| Situation | v2.0.0 | v3 |
|---|---|---|
| Review ends with BLOCK or an unknown verdict | `0` | `25` (`needs-human-or-paused`) |
| Linear stays unusable after the retries (no answer, not JSON, GraphQL errors, no data) | no dedicated code; some reads failed open | `27` (`linear-unusable`), new |
| An npm project's dependencies cannot be restored after the worktree reset | no restore; the build ran red | `24` (`environment-blocked`, an existing code) |
| `agents.merge_mode` is `manual` without a Merge state | not applicable | code review refuses at its start with `24` |
| Shepherd receives `22` to `26` from a stage | stopped without an alert | halts with an alert; only `0` and `2` carry on, `10` and `16` retry |
| Shepherd receives a `20` that `--no-merge` or `BUREAU_NO_MERGE` asked for | halted with an alert | stops quietly; any other `20` still alerts |
| The shepherd's own read of state, labels or branch fails | read as "no state", "no label" or "no branch" | `27` halts with the fault class, another failure halts with `1` and `needs-human`, Ctrl-C or SIGTERM is a cancelled run (`130`) that writes nothing |

Some installations gave `20`, `21` or `25` local meanings. Rewrite local changes onto the codes in [exit codes](exit-codes.md) instead of copying a code across.

Upgrade one adopting repository at a time, each in its own pull request:

1. **Pause dispatch** and let nothing be in flight. Push any unpushed commit to a branch first.
2. **Branch from the repository's `main` in a fresh worktree**, so dirty files and other branches stay out of the change. Keep a private backup of `scripts/`, `.bureau.json`, `.bureau-install.json` and the instruction files (see [before changing an adopting repository](#before-changing-an-adopting-repository)).
3. **Pin the source** to the release tag as in [select the source release](#select-the-source-release).
4. **Set the configuration the new scripts expect, before the resync:**
   - Where a human merges, set `"agents": {"merge_mode": "manual"}` and make sure `linear.teams[0].states.merge` is set. The resync replaces a hand-edited early `exit` in `merge-pipeline.sh` or `rebase-pipeline.sh`; without the key, automatic merging is on again. See the [recipe](recipes.md#merge-by-hand).
   - Where the review build check ran a local script, set `repo.test_command` to it. `scripts/bureau-test.sh` is found without configuration.
   - Make `.gitignore` cover everything `repo.test_command` writes, such as `__pycache__/` or build output. Otherwise the review leaves untracked files, the worker keeps the worktree as unfinished work, and the next reset refuses with `21`.
5. **Preview the scripts scope and apply it as one set.** `bureau-config.sh` loads `bureau-env.sh`, `merge-pipeline.sh` loads `merge-body.sh`, and `squash-marker-check.sh` reads `ci-skip-markers.txt`; a partial scripts scope is not a working runtime. An installation without `.bureau-install.json` sees every differing file as a conflict. For each one, diff the local file against `templates/scripts/FILE` and decide: take the template (the usual answer where the local hardening is now upstream), express a local policy as configuration, or keep a genuine local need in a separate local file. Then apply with the reviewed `--overwrite` list ([preview and resolve](#preview-and-resolve-asset-conflicts)). Add the interfaces scope only where the repository uses the commands.
6. **Optionally migrate the configuration** ([configuration migration](#optional-configuration-migration)).
7. **Update or retire repository tests** that assert the old pipeline behaviour (exit codes, file layout) in the same pull request.
8. **Verify:** doctor (`python3 scripts/bureau-doctor.py --mode background`), the repository's CI, then qualify one ticket end to end with the shepherd before dispatch resumes. Name the release tag, every carried local change, the preview before and after, and a reason for each `--overwrite` in the pull request.
9. **Rollback** restores the backup and points the source back at the previous commit ([rollback](#rollback)). The manifest stays at version `1`, so an older installer still reads it.

## Before changing an adopting repository

Check the [dependencies](../README.md#install) before using the new helper: Python 3.9+, Bash 3.2+, Git 2.26+, jq and curl. Spec Kit refresh requires 0.7.5; the shared scheduler needs Node.js 18+. Background stages need their selected provider CLIs and GitHub operations need `gh`. Current Codex app tasks do not require background provider CLIs or tmux.

1. Inspect `git status`, the current branch and active worktrees. Record the installed source revision: doctor reports it as `template_source` for installs applied by a helper that records it (see below); older installs report `source not recorded`, so take it from your own notes if known. An old install may have no `.bureau-install.json`; absence of hashes is expected and must not be treated as permission to overwrite.
2. Stop new dispatch and let running stages finish. With the new runtime, use `python3 scripts/bureau-runtime.py pause` and inspect `status`. On an older install, stop its launcher/scheduler normally. A stopped launcher does not prove an existing worker has exited.
3. Preserve tracked changes, untracked work and local customizations. Before applying asset scopes, use their previews to inventory affected paths and keep an exact private backup of all existing assets in those scopes, even files without conflicts. Never put credentials into a commit, PR or public support log.

## Preview and resolve asset conflicts

Run the helper from the refreshed source, with the adopting repository as the current directory:

```sh
python3 "$BUREAU_SOURCE/scripts/bureau_install.py" assets \
  --repo "$PWD" --target both --scope interfaces --scope scripts
```

Preview writes nothing. Exit code `3` means at least one asset conflict. Even with `--apply`, **one unresolved conflict prevents every file in that asset batch from being written**, including new runtime helpers and the manifest. Configuration migration and Spec Kit initialization are separate operations, not part of this transaction.

The preview also prints `source`: the revision of the Bureau source it would install from, with the exact tag if its commit is tagged (`tag`, otherwise `null`), the nearest `git describe --tags` (`describe`), the full `commit`, and `dirty`. Check it before `--apply`, for example that it names the release you pinned. A successful `--apply` records that value in `.bureau-install.json` under `sources`, keyed by what the batch wrote (`scripts`, `ci`, `workflows`, `interfaces/claude`, `interfaces/codex`), next to `sources_files_sha256`, a digest of the recorded file hashes. A later partial apply relabels only the keys it wrote, so a scripts scope installed from one release and a CI scope from another stay distinguishable. When the incoming digest no longer matches the file hashes, the record was carried along by a writer that changed files without recording its source; the apply then drops the whole carried record and keeps only the keys it wrote. `dirty` is true when the source checkout reports modified or untracked files, or when any file this batch reads (the templates it installs and the installer itself) is not byte-identical to its blob at the recorded commit, or when either cannot be read. The second check matters because the installer copies every file in `templates/scripts`, including files Git ignores such as `.env`, `.DS_Store` or `*.log`, which `git status` never shows. Keep such files out of `templates/`: they are installed into the target repository. A source that is not its own Git checkout, such as an unpacked archive or a copy inside another repository, is recorded as `{"git": false, "note": "not a git checkout"}`; the enclosing repository's commit is never used. A preview or an apply stopped by a conflict writes no source. The manifest stays at version `1`: installers without source recording still read it.

```json
"sources": {
  "scripts": {"git": true, "tag": "v3.1.0", "describe": "v3.1.0", "commit": "<40-character SHA>", "dirty": false}
},
"sources_files_sha256": "<sha256 of the files map>"
```

| Preview result | Meaning | Resolution |
|---|---|---|
| `install` / `update` / `unchanged` | New file, unchanged installed baseline, identical content, or an explicitly selected replacement | Review the batch and apply when its conflicts are resolved |
| Existing file differs, no stored hash | The installer cannot distinguish an old generated file from local edits | Compare it with incoming content; preserve anything custom |
| Existing file differs from its stored baseline | Local customization or drift | Preserve it and review the incoming change |
| Legacy or malformed instruction markers | The managed part of CLAUDE.md/AGENTS.md cannot be identified safely | Review the exact generated region and fix its delimiters before retrying |

For plain scripts, compare `scripts/FILE.sh` against `$BUREAU_SOURCE/templates/scripts/FILE.sh`. Codex skills and scheduling workflows are rendered from templates, so compare the actual intended output, not an assumed identical template. You can install the same selected asset scopes into a throwaway Git repository to inspect the generated files. Never copy this source repo's maintenance CLAUDE.md or AGENTS.md into an adopting project as the incoming instruction file. If the old source revision is known, use it as a comparison base; without it, do not claim a reliable three-way merge.

Choose a resolution for **each** conflict:

- **Take upstream:** after reviewing and backing up the old file, name that specific path with `--overwrite`. Review the new preview, then repeat with `--apply`.
- **Keep custom behavior and upgrade:** preserve the original plus the intended custom changes, review the combined result, install the coherent upstream batch using the individually authorized replacements, then selectively reapply those custom changes. Keep dispatch stopped throughout. Do not copy the entire old file back over the new runtime.
- **Defer:** leave the batch unapplied until the conflict can be reconciled. An independent scope can be handled separately, but do not describe an incomplete scripts upgrade as a working new runtime.

Example for a single reviewed script replacement:

```sh
python3 "$BUREAU_SOURCE/scripts/bureau_install.py" assets \
  --repo "$PWD" --target both --scope interfaces --scope scripts \
  --overwrite scripts/qa-pipeline.sh
# After reviewing this preview, repeat the same command with --apply.
```

Other conflicts still block that example. Repeat `--overwrite` only for each reviewed path in the selected scope. There is no blanket force, skip-conflicts or automatic merge option.

For instruction files, Bureau manages only the region from `<!-- bureau-init:begin -->` to `<!-- bureau-init:end -->`. Text outside it is preserved. An older generated section — opened by `<!-- bureau-init managed -->` or a variant such as `<!-- bureau-init managed: regenerate via … -->`, closed by `<!-- end bureau-init managed -->` — must be identified and delimited manually without enclosing unrelated user guidance: put `<!-- bureau-init:begin -->` and `<!-- bureau-init:end -->` in place of its old markers. The installer refuses a file that still carries any of these legacy markers outside a `bureau-init:begin/end` block (the plan names the line), so it never appends a second Bureau block next to an old one. Malformed/legacy boundaries must be repaired first; `--overwrite CLAUDE.md` is not a bypass for invalid markers.

After reapplying customizations, preview may correctly report those paths as conflicts again. Record this as intentional drift and verify the resulting runtime. Do not edit `.bureau-install.json` to disguise the drift: its hashes describe the upstream baseline and protect those customizations at the next upgrade.

## Optional configuration migration

Version 1 configurations remain supported; resync does not replace `.bureau.json` or `.env`. Configuration version `2` is a schema version, not a Bureau release number. To adopt it, preview and then apply:

```sh
python3 "$BUREAU_SOURCE/scripts/bureau_install.py" migrate --repo "$PWD"
python3 "$BUREAU_SOURCE/scripts/bureau_install.py" migrate --repo "$PWD" --apply
```

Migration retains existing IDs, labels, models, switches and extension keys. It makes the existing Claude runner default explicit when absent and adds `agents.model_compatibility: "v1"` when migrating v1 unless compatibility was explicitly selected already. This preserves legacy model ownership: Codex uses Codex-specific settings instead of generic Claude defaults. A repeat migration makes no further changes.

The exact original config is saved with private permissions under `<shared-git-dir>/bureau/config-backups/.bureau.json.pre-v2.<unique>.bak`. This backup covers the configuration only; it does not back up scripts, `.env`, worktrees or external ticket state. Invalid/future config versions are rejected without replacement.

Installing Codex interfaces does not enable Codex background execution. To opt in, configure the desired default/stage runners, Codex-specific model settings and `repo.test_command`. To adopt v2 generic model semantics, first review or relocate legacy Claude model fields, then explicitly set `agents.model_compatibility` to `v2`.

Inspect installed interfaces, `.specify/integration.json`, the final Git diff, retained customizations and run ownership. Check Bash syntax for installed shell scripts. A successful doctor is not a live workflow test.

Doctor is read-only: it reports configuration provenance, effective settings, real Bureau interfaces, managed drift and the recorded template source. `template_source.status` is `recorded` (with the per-scope `sources`), `source not recorded` when there is no manifest, the manifest predates source recording, or no scope is recorded yet (not an error; the next asset `--apply` that installs files records it), or `stale` with a warning when the file hashes changed after the record was written. That is what an installer without source recording leaves behind: it rewrites the hashes and carries the old record along. It resolves JSON and the process environment; it does not execute `.env` (it reads only `BUREAU_RUNNER_IMPLEMENT` from it, with the stages' own reader, for the `repo.test_command` warning), authenticate providers, call Linear/models or run tests. Source trusted overrides before invoking it when needed. App mode does not require background CLIs; background GitHub stages require `gh`. The runtime uses the first configured Linear team's state map; doctor warns on multiple teams. It also warns when an enabled spec, spec review, UX, QA or review stage gets less than 1800 s per provider call, when automatic merging needs CI checks (`agents.merge_mode` auto, `agents.merge_require_green_ci` not `false`, `agents.merge_min_required_checks` at least 1) but no workflow under `.github/workflows` runs on pull requests or on pushes to every branch, and when `agents.merge_require_green_ci`, `agents.merge_require_up_to_date` or `agents.implement.push_each_iteration` is not a JSON boolean, and when `repo.test_command` is missing while implement resolves to Codex; it rejects `.env*` entries in `repo.worktree_links`, and directories in that list that hold a `.env*` name or cannot be searched completely, and judges that list in the main checkout, also from a linked worktree.

Qualify a representative ticket through the intended app/background path with the review-only boundary before enabling unattended dispatch. Authenticate selected providers normally. Resume workers/automations only when requested and the upgrade is coherent. See the [acceptance record](codex-acceptance.md) for what has and has not been exercised.

## Rollback

Stop new dispatch and inspect active owners before restoring anything. Preserve work created since the upgrade. Restore the recorded previous source commit/tag in a clean source checkout; for example, `git -C "$BUREAU_SOURCE" switch --detach PREVIOUS_COMMIT`, replacing the placeholder with the recorded commit. Restore the coherent pre-upgrade project asset set, instruction files and installer bookkeeping from the private backup, then reconcile subsequent local changes. Identify files newly installed by the upgrade and remove only confirmed upgrade additions that are absent from the old baseline and contain no later work.

If the selected older source supports deterministic previews, use a scoped preview to verify its baseline and review every conflict. An older helper does not record its source and carries the existing record along. Doctor reports that record as `stale` only once the older helper has changed a file hash; an apply that changed nothing leaves it `recorded`, which is still true of the files. After a restore of the pre-upgrade manifest from the backup it reports `source not recorded`. The next asset `--apply` by a recording helper drops a stale record and records only the scopes that apply wrote. A legacy source may have no installer helper or manifest support: do not assume the current resync commands work there, or mix selected old scripts with the new runtime. Restore customized behavior from its matching backup. A configuration backup covers configuration only and can be restored after comparing subsequent edits and runtime compatibility. Keep `.env` private and intact. Run the restored project's tests and available diagnostics before considering a restart.

Restoring source/configuration does not undo commits, Linear transitions or already-completed work. Preserve run records, provider logs, issue branches and checkpoints. Older runtimes may not honor new ownership records, so never restart one against unfinished work managed by the newer runtime. Do not delete leases or reset worktrees as a rollback shortcut.
