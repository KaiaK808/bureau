# Exit codes & alerts

Every pipeline script exits with a code that classifies its outcome. `queue-loop.sh` reads the code, maps it to an alert class, and (optionally) fires a Telegram message — throttled so a stuck issue doesn't spam you 30 times an hour.

This page is the complete table + how the alerter behaves.

---

## Exit code table

| Exit | Class | Meaning | Common cause |
|---|---|---|---|
| `0` | ok | Pipeline completed successfully, or configured Done observed at a ticket checkpoint or mandatory background state guard | — |
| `2` | queue-empty | No pickable issue in the polled state; from `merge-pipeline.sh` also: the merge gate is not yet decided (checks pending or not started, GitHub still computing, a gate read that failed, a head that moved after the gate checked it — the merge is pinned to that head with `--match-head-commit` —, a hold label `wip`/`blocked`/`needs-human` on the PR, conflicts the rebase stage resolves — never under the shepherd, whose ticket the queue's rebase stage skips); from `code-review-pipeline.sh` also: an APPROVE whose inline merge found its gate not yet decided — the approval is recorded, and the next run checks the build and the gate again without a model review | Normal — happens every tick when there's no work. The queue loop stays quiet; the shepherd waits for the gate (see below) |
| `10` | linear-down | `LINEAR_API_KEY` missing or invalid | Forgot to set it in `.env`, or the key was revoked |
| `11` | worktree-dirty | Uncommitted changes in the worktree; from `spec-pipeline.sh` also: `.specify/feature.json` unusable after speckit-specify | Manual edits in `.worktrees/queue-<mode>/` — clean up before next tick. The spec stage prepares `feature.json` for the reserved directory before specify; a missing, malformed or redirected pointer afterwards ends with `11` and routes back to Triage through ordinary recovery, without a `needs-human` label. A retry prepares the reserved pointer again. See the troubleshooting guide |
| `12` | no-branch | `bureau-branch` marker missing or points at a non-existent branch | Spec pipeline didn't post a digest, or the branch was deleted |
| `13` | no-tasks | No usable spec for the branch: `tasks.md` missing, no spec directory matches, or the branch fits more than one | `/speckit-tasks` produced an empty file, or the spec directory was renamed or never created: implement and spec review route back to Spec, UX back to Spec Review. On a tie (v3.0.2) implement, spec review and UX name every fitting directory, set `needs-human` and route back, because the stages never guess and re-running Spec cannot resolve a tie: rename or remove the stray directory, then remove the label. When no directory matches the branch at all (v3.1) the three stages also set `needs-human`, and their comment names the branch and the specs directory; a matched directory without `tasks.md` still routes back to Spec without the label |
| `14` | build-failed | Build precondition failed | Test suite red, type-check failed, lint errors, `repo.post_implement_command` failed after an implementation run |
| `15` | no-pr | PR expected but not found | Implement didn't create one, or it was closed manually |
| `16` | provider-unauth | Selected CLI missing or not authenticated | Authenticate the selected Claude/Codex CLI |
| `17` | rebase-needed | Owned merge or rebase conflict repair declined, failed validation or exhausted its durable allowance | Entire operation rolled back to the original branch; needs-human label or durable local hold |
| `18` | gh-failed | `gh` CLI command failed (e.g. `gh pr merge` rejected), or the implement stage's final `git push` failed twice while origin (fetched again) lacks commits of the branch or cannot be read; also: the spec stage could not fetch origin, verify its base or read/reserve a spec number | API rate limit, missing permissions, branch protection, origin rejecting or unreachable |
| `19` | rebase-rejected | `git push --force-with-lease` rejected | Someone else pushed to the same branch concurrently |
| `20` | stopped-before-merge | Review boundary or intentional stage handoff | Expected with `--no-merge`, from shepherd at manual Merge, and for a disabled stage under `--respect-config`. Those handoffs are quiet. Dispatcher base refresh uses `refreshed` metadata to require fresh review; it never reports merge success. Other stage-result 20 exits can alert in standalone shepherd |
| `21` | ownership-conflict | Ticket, checkout or branch held; stale result | Inspect owner/run, preserve work and reconcile. Since v3.1.0-rc.2 a halt over a ticket or worktree an interrupted run still holds, an unregistered or foreign worktree or a branch held by another worktree sets `needs-human` and posts one comment with the way back (not for a live holder or a cancelled run); after an interrupted run, release it and drop or replace its worktree before a rerun. No halt: an unregistered worktree that a non-spec stage can reset without loss (a linked worktree of this repository with no uncommitted or untracked changes and a HEAD on the fetched `origin/<branch>`) is registered again with one line on stderr and the run goes on. See the troubleshooting guide |
| `22` | provider-or-result-error | Provider failed or final result invalid | Inspect provider evidence. Spec Review and UX require schema-valid results with their exact status enums; missing, unknown or wrongly typed statuses and invalid objects preserve edits and hold the ticket for a human. No ordinary push, success comment or Build/Design move follows. A failed needs-human label write leaves a durable local hold. Ticket withdrawal still takes precedence with 25/26 |
| `23` | quota-wait | Selected provider quota reached | Wait for reset; do not switch providers silently |
| `24` | environment-blocked | Permissions or required execution capability missing | Inspect denied operation separately from code/test failures. Also: a Node project's dependencies could not be restored after the worktree reset; the last install log lines appear in stage output and full logs sit beside stamps in the shared Git directory's `bureau-deps/`. npm retains its existing path; pnpm/Yarn Classic require a provisioned manager and offline cache, with two bounded attempts. Modern Yarn/PnP, ambiguous lockfiles and a conflicting `packageManager` are refused; see [Node repositories](configuration.md#node-repositories). The shepherd halts and alerts. Also: `agents.merge_mode` is `manual` but `linear.teams[0].states.merge` is not set — the review stage refuses at its start, before any paid review; configure the Merge state or set the mode to `auto` Also: `repo.untrusted_env` is not absent, `"default"` or `"clean"` — the provider check at the start of each model stage and every command from the branch (build check, QA runs, Codex completion test, app tests) refuse before anything runs; fix the value |
| `25` | needs-human-or-paused | Halt requiring attention, paused dispatch, or ticket parked outside its configured active states | Resolve the blocker or unpause explicitly. `merge-pipeline.sh` ends with 25 when its gate is decided against the merge (a failing check, a head without any check run or status once its commit is older than `agents.merge_ci_start_grace_seconds`, conflicts the rebase stage does not resolve, a stale base, no APPROVE, unresolved threads, a PR that is not open); it posts the blockers on the PR, the queue loop alerts (throttled) and picks the ticket again on the next tick, so a fixed or re-run check still merges without anyone removing a label. The review stage ends every BLOCK (and any unknown verdict) with 25, so a driver never reviews the same commit again; it also ends with 25, sets `needs-human` and comments the gate lines when an APPROVE's inline merge finds the gate blocked, and records that APPROVE, so the run after a human clears the blocker and removes the label merges without a new review. A stage that hands a ticket to a human but cannot write the `needs-human` label ends with 25 where it would have ended with 0 (a stage that already ends non-zero keeps its code) and holds the ticket locally; see the troubleshooting guide. |
| `26` | cancelled-ticket | Ticket at a configured cancelled/canceled/duplicate state ID | Not successful completion |
| `27` | linear-unusable | A Linear answer stayed unusable after every retry; the stage (or the shepherd's own read of the ticket's state, labels or branch, or its own move of the ticket) stopped instead of deciding on an empty result | Linear outage, an error page, or a query Linear rejects. The shepherd halts: Telegram alert with the fault class (`no-response`, `not-json`, `graphql-errors`, `no-data`), then one attempt each at `needs-human` and a halt comment. Re-shepherd once Linear answers. A queue pick that fails with 27 is reported and alerted, not read as an empty queue. |
| `28` | spec-capacity-wait | Spec admission cap is full; holding identifiers and states are printed, never descriptions | Expected wait before picks, mutations or model work. The shepherd polls cancellably every 60 s without stuck ticks, labels or alerts. Queue workers retry at the next poll without alerting; bounded ticks report `waiting` with process/result exit code 28 |
| `29` | file-overlap-wait | Build admission overlaps reserved/in-progress ticket scopes or open Bureau PR diffs; output names holders and intersecting paths or unknown scope | Opt-in `agents.file_overlap_gate`. Quiet cancellable admission wait: no alert, human label, paid pass or stuck increment. Tick process/result exit 29 with `outcome:"waiting"`; queue skips waiters within the poll and retries them next poll, shepherd stage loop every 60 s. Guarded manual moves and shepherd `--from-stage build` return 29 directly. Successful readiness is retained. Service/ownership failures keep their own codes. |
| `124` | timeout | Provider exceeded time bound, or spec allocator lock acquisition exceeded `BUREAU_SPEC_LOCK_TIMEOUT` (default 300 s). Implement (since v3.2): the last pass that could run timed out — a timed-out pass with another pass left goes on to that pass instead | For a spec lock timeout, inspect the printed lock path and stop or release its holder before retrying; the issue returns to Triage without specify work. For provider timeouts, inspect preserved progress and the transcript named in the provider evidence (`session_id`, `transcript` in `result.json`); see the troubleshooting guide |
| `130` | cancelled-run | Process interrupted | Inspect ownership and resume evidence |

Successful mandatory background state reads use the same configured-ID withdrawal protocol as additional checkpoints: Done 0, cancelled/duplicate 26, other inactive IDs 25, never the stage-mismatch exit 2. The observation is latched before routing, so later refresh failures cannot replace it with an error or a needs-human escalation. A failed mandatory read itself retains its existing strict error handling.

Provider silence also uses `25` (`needs-human-or-paused`), with `outcome: timeout` and `timeout_kind: silence` in the provider result metadata and receipt. Owned writers are stopped and drained before reporting; the trusted shell checks withdrawal before adding the human hold, so Done/cancelled/inactive checkpoints keep `0`/`26`/`25` without a new escalation. Implementation starts no further pass on silence. Review cancels and joins sibling specialists, records the interrupted paid round with unknown verdict/usage left null, and starts no verdict merger. Independent signal cancellation remains `130`; sibling cancellation acknowledgments do not replace the originating silence stop. Provider hard timeouts remain `124` with `timeout_kind: wall-clock`; outside-gate handling and quiet overlap waiting (`29`) are unchanged.

If the silence escalation cannot write the human label, the existing local picker hold is retained and the stage still exits `25`, including when Linear is unusable. The parent consumes any withdrawal latched during that attempt before reporting the silence hold.

`bureau-tick.sh` additionally writes a JSON outcome. Capacity waiting keeps process exit 28 and JSON `exit_code:28`, with `outcome:"waiting"`. Quota waiting returns process exit 0 with result `exit_code:23` to allow the next scheduled tick. A stage exiting 0 with unchanged ticket state is `waiting`; only actual Done is `completed`. Shepherd and schedule execution return nonzero for review/human/cancellation boundaries so the next serial ticket does not start as though the first had completed.


File overlap waiting (`29`) has the same quiet consumer treatment as capacity waiting (`28`), including the shepherd exception and bounded tick JSON described below. Reservations and the migration rules are documented in [file admission](stage-protocol.md#file-overlap-admission).

Exit codes outside this table (e.g. `1`) classify as `error-1` — usually a bug in the pipeline script or an unhandled bash error.

`shepherd.sh` halts with a Telegram alert on every code except `0` and `2` (carry on) and `10` and `16` (sleep 60 s, retry), plus `28` and `29` (quiet, cancellable admission waits without stuck ticks); a code added later cannot slip through unannounced. `27` additionally tries `needs-human` and a halt comment once each. The one exception is a `20` that `--no-merge` asked for: the shepherd ends with `20` without an alert, and `queue-loop.sh` logs it without one. Under `agents.merge_mode: "manual"`, `merge-pipeline.sh` and `rebase-pipeline.sh` refuse with `2`, and the shepherd's own stop at Merge is a `20` without an alert. The shepherd's own reads follow the same rule: when reading the ticket's state, labels or branch gives up with `27`, it halts the same way and names the read; any other failed read halts with `1` and `needs-human`. A failed read never counts as "no state", "no label" or "no branch". The shepherd's own moves (`--from-stage`, and the bump from Spec to Triage) follow the same rule, except an overlap refusal (29) returns quietly to the caller without a halt comment, human label or alert. Its start check runs before it claims the ticket: a failure there ends with `10` and an alert naming the fault class, and writes nothing to the ticket. Ctrl-C, SIGTERM or a hang-up (closing the terminal or the tmux session, since v3.2; the runtime forwards it as SIGTERM) during a read, a move, a wait or a stage ends the run as a cancelled run (`130`) that writes nothing to Linear but the release of `shepherd-focused` (one attempt); the shepherd's own waits are cut short at once. The runtime in front of the shepherd counts its `130` as a stop also when the signal went to an inner process group only (since v3.2): it keeps the run's leases interrupted and prints the resume steps ([How to stop a run](troubleshooting.md#how-to-stop-a-run)). A SIGTERM sent to the shepherd alone takes effect when the command in flight returns: the usage-throttle wait before a stage and the retry ladder's waits inside a Linear call run to their end first. `--dry-run` runs without the runtime and without these traps: Ctrl-C there ends with `130`, a SIGTERM with `143`. Linear answering five times in a row without a state halts with `1` and `needs-human`. After `--from-stage` a read that does not yet show its target, and after the bump to Triage or a stage that returned `0` a read that still shows the state the ticket left, is read again up to three times, 5 s apart (`BUREAU_SHEPHERD_CONFIRM_SECONDS`), before the next stage starts. A `--dry-run` whose state read fails prints no route and exits with `27` when Linear stayed unusable, `1` on any other failure. At Merge the shepherd follows the merge stage's gate (v3.0.1): a gate that is not yet decided (`2`) is waited for, `BUREAU_SHEPHERD_MERGE_POLL_SECONDS` apart (default 60), up to `BUREAU_SHEPHERD_MERGE_WAIT_SECONDS` in total (default 1800), without the confirmation re-reads and without counting as stuck; a gate decided against the merge (`25`), or one still not eligible when the wait is used up, halts with `25`, `needs-human`, a comment carrying the gate report and an alert. Before, the merge stage ended with `0` whether it merged or not, and the shepherd reported "still reads 'Merge' after the move" and then stuck (`13`). The review stage's inline merge (`BUREAU_INLINE_MERGE=1`, merge agent off) ends with the same codes since v3.1, and the review stage acts on them: after a gate that is not yet decided it records the APPROVE and ends with `2`, and the shepherd waits the same way at Build Review (each retry reuses the approval without a model review and runs the gate again, since v3.2 without the build check when it passed for the same head, base and command), while the queue's review picker puts such a ticket after the other Build Review tickets for a hold of two poll intervals (at least 300 s) doubling up to `agents.merge_gate_recheck_seconds` (default 3600) unless its branch moves, and still takes it when nothing else can be picked; after a blocked gate it sets `needs-human`, comments the gate lines and ends with `25`, which the shepherd handles like any `25` (alert, halt). Before, the review stage reported Done after an inline merge that did not go through. `merge-pipeline.sh --dry-run` still ends with `0`. Since v3.2 the merge stage marks a gate that ended with `2` or `25`, and the merge picker (not the rebase picker) puts that ticket after the other Merge tickets the same way while its head is unchanged. A check run that stays queued longer than `agents.merge_ci_queued_grace_seconds` (default 3600), for example on an offline runner, is blocked (`25`) since v3.2: the queue loop alerts, the review stage sets `needs-human`, the shepherd halts; before, it kept the gate at `2` for ever, the queue stayed quiet and the shepherd waited its budget. A head with no check run and no status at all is blocked once its commit is older than `agents.merge_ci_start_grace_seconds` (default 1800). The wait settings are read in base 10 and capped at 6 h (wait) and 1 h (poll).

Before it claims a ticket, `shepherd.sh` checks whether a human holds it: `needs-human` or the configured `linear.labels.needs_human.name`, `blocked` or `wip` on the ticket, or a local hold that a stage left when it could not write `needs-human` (`<git common dir>/bureau/needs-human-held/<ISSUE>`, checked first, without a Linear read). A held ticket ends the run with `25` and nothing written — no `shepherd-focused`, no `--from-stage` move, no comment, no alert — and a line on stderr names the hold and how to release it; `--dry-run` answers the same way (the hold instead of a route, `25`). A hold left on a finished ticket changes nothing: without `--from-stage` a Done ticket still ends with `0` and a cancelled one with `26`, as in the loop and without any write (the state is read only then), so an orchestrated chain goes on past it. A label read that fails there writes nothing either: `27` with the fault class and an alert when Linear stayed unusable, `1` and an alert for any other failure, `130` for a signal. The loop keeps the same check before every stage and halts with `25` and a comment, as before, now also on the configured name and on a local hold.

**Token-efficiency flags don't change the table.** Under `agents.use_goal_loop: true`, the implement-pipeline still produces the same terminal STATUS values (`COMPLETE` / `PARTIAL` / `NEEDS_HUMAN` / `STUCK` / `CAP_TIME` / `CI_MARKER`) and exits with the same codes the iter-loop path emits — `/goal` swaps the inner control flow but the downstream PR / Linear / exit-code shape is identical. Same for `agents.headroom_wrap` (wraps the claude binary, not the script's exit logic) and `agents.caveman_level` (only affects per-stage prose, not exit codes). See `docs/token-efficiency.md` for the rationale.

Ticket withdrawal checkpoints classify configured IDs, never display names. A confirmed external Done ends with 0, cancellation/duplication with 26 and every other inactive ID with 25. No recovery transition or new provider/publication follows a confirmed stop. The runtime releases issue/workspace leases normally after writers finish; unfinished work survives, including for Done's 0. Active-to-active stale mutation conflicts remain 21 and signals remain 130 with interrupted ownership. Additional checkpoint refresh failures warn once per run and allow the already authorized unit to continue. Mandatory initial dispatch, mutation and ownership reads keep their strict behavior. Shepherd's existing mandatory iteration reads also remain strict; only its extra checkpoint refresh can fail open.

The continuous dispatcher adds no numeric exit. Lanes yield on 28/29 (quiet admission waits), 23 (one-shot usage throttle), 10/16 (transient retry) and merge-gate 2, with deadlines in `bureau/dispatch-skips.json`. Other 25 outcomes, including silence escalation without a label, remain held across restart; a repository pause defers instead. Terminal 0/26, intentional handoff 20 and unknown failures stay skipped until reconciliation; unknown failures also alert and attempt a human hold. `--respect-config` uses 20 for a disabled stage. Owned base refresh uses 20 plus gate-report `refreshed`/`base_refresh` metadata to continue to fresh Build Review, never to report merge success. Dispatcher/poller lock conflicts return 21, invalid dispatcher configuration returns 24, and interrupted dispatcher/supervisor shutdown returns 130 after cleanup. Standalone shepherd retains its cancellable admission and merge waits.

Optional `build_lessons_context` selection and `agents.lessons_budget_bytes` add no exit code. Expired or invalid entries, unavailable local diff/context and invalid or undersized budgets can warn while the stage continues. Lessons remain advisory: ticket checkpoint exits `0`/`25`/`26`, quiet overlap `29`, silence `25` with `timeout_kind: silence`, review floors/rounds and dispatcher lane outcomes retain their existing meaning.

## Telegram alerts

`alert_telegram` (in `bureau-config.sh`) sends a message when:

1. `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ALERT_CHAT_ID` are both set in `.env`
2. The exit code maps to a non-OK class
3. The same issue, pipeline and exit code has not alerted from this repository in the past hour

Throttling lives in `<git common dir>/bureau/alert-throttle.log` of the repository that holds `.bureau.json`: one log per repository, shared by its worktrees, one line per key and time. Delete a line, or the file, to let an alert through again. `BUREAU_ALERT_THROTTLE_FILE` names another file (tests). Only when no git directory resolves does the log stay `/tmp/bureau-alerts.log`, and the key then starts with the repository's path. Before v3.1 every installation on the host shared that one `/tmp` file, so the same key in one repository (a ticket number both teams use, or `none` for a failed pick) silenced another repository's alert for an hour; right after the upgrade the new log is empty, and an alert sent in the hour before may come once more.

When credentials are unset, `alert_telegram` is a silent no-op. Dev environments never break because of it.

### Alert content

A typical alert includes:

- The repository (`Repo:`, the directory name of its main checkout)
- The pipeline that failed (`spec`, `qa`, etc.)
- The Linear issue identifier (`TEAM-123`)
- The exit code class
- A short reason from the pipeline (`merge_origin_main_or_abort: non-trivial conflict on src/foo.ts`)
- Tail of the queue log when the supervisor gives up (last 30 lines, see [auto-restart supervisor](#auto-restart-supervisor))

## Auto-restart supervisor

`queue-loop-supervised.sh` wraps `queue-loop.sh` and restarts it after a crash with exponential backoff. It only fires a Telegram alert at the *give-up* threshold, not on every restart.

Behaviour:

- Crash 1 → wait 10 s → restart
- Crash 2 → wait 30 s → restart
- Crash 3 → wait 60 s → restart
- Crash 4+ → wait 300 s → restart
- After `BUREAU_SUPERVISOR_MAX_CRASHES` (default 5) consecutive crashes → fire `supervisor` alert with the tail of `logs/queue-<mode>.log` and exit 1
- Counter resets after `BUREAU_SUPERVISOR_STABILITY_WINDOW` seconds (default 1 h) of clean runtime

`SIGINT`, `SIGTERM` and (since v3.2) `SIGHUP` stop the supervisor and its queue loop (the loop gets `SIGTERM`) without triggering the restart logic. `Ctrl+C` in the tmux pane, closing the pane or its session, or `kill -TERM -- -<supervisor pid>` sends the signal to the supervisor's whole process group, which holds the queue loop and the runtime in front of the stage in flight too: everything stops cleanly, and the stage stops with `130` and keeps its work, as under the shepherd ([How to stop a run](troubleshooting.md#how-to-stop-a-run)). A signal to the supervisor's process alone reaches only the queue loop's process: the stage in flight and its runtime get nothing and run to their end (so in v3.1 as well).

To opt out for a debugging session: call `./scripts/queue-loop.sh <mode> <interval>` directly from a workbench pane instead of attaching to the agent window.

## Single-flight observability

When `agents.max_concurrent_issues` is non-zero, `spec-pipeline.sh` exits `28` (`spec-capacity-wait`) at a full cap before picking or mutating a ticket or running a model. The log names the holding issue identifiers and states. The shepherd polls every 60 seconds, cancellably, without accruing stuck ticks, `needs-human` or alerts; the queue waits until its next poll. Bounded ticks report `waiting` and keep 28 in their JSON.

Under manual merge mode, Merge is excluded by default; auto includes it. `agents.max_concurrent_include_merge: true` retains the previous manual-mode behavior. Build Review still counts, including approved `--no-merge` stops there. A failed Linear snapshot returns 27, never an empty count.

```sh
grep "Spec gate:" logs/queue-spec.log
```

## Local learning cause classes

Learning metadata uses `bureau_insight_cause` in `bureau-insights.sh`, independently of the exit vocabulary above. It records `timeout`, `gate_red`, `review_capped`, `ownership`, `provider_error`, `quota`, `human_hold` or `other` from trusted exits/provider metadata/shell signals, never model prose. This changes no exit, alert class, dispatcher lane outcome or routing. Silence retains 25 with `timeout_kind: silence`; wall-clock timeout retains 124. Latched withdrawal 0/25/26 wins over earlier provider failures; quiet overlap exit 29 stays distinct and quiet (`other` cause). See [failure learning records](stage-protocol.md#failure-learning-records) for the exact mapping, local-only ledgers and retention. Resync all scripts including `bureau-insights.sh` and restart drivers; no configuration or backfill.
