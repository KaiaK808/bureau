# Changelog

User-visible changes and upgrade actions are recorded here. Releases use dated version sections and immutable Git tags; see the [release process](docs/releases.md). Earlier changes on `main` were not tagged and remain listed separately below. Configuration schema numbers are not Bureau release versions.

An upgrade requires **updating the source skill and resyncing each adopting repository**. Neither `git pull` alone nor `/bureau-init --update` refreshes installed assets. Follow the [upgrade and conflict guide](docs/migration.md).

## [3.1.0-rc.1] - 2026-09-30

First release candidate for Bureau v3.1.0, published as a GitHub prerelease; v3.0.2 stays the stable release until v3.1.0 is published. v3.1 is a minor release on v3.0.2 that collects six pull requests of fixes, guards and opt-in settings found in the installations and in cross-checks of their pipelines: code a branch controls runs without the Bureau secrets ([#33](https://github.com/KaiaK808/bureau/pull/33)); the review stage acts on the result of its inline merge, and the merge gate honours `false` switches, pins the head it checked, blocks a head without any CI after a grace period and reads its numbers by one rule ([#38](https://github.com/KaiaK808/bureau/pull/38)); the implement loop checks for CI markers after every iteration and can defer its pushes while a PR is open ([#37](https://github.com/KaiaK808/bureau/pull/37)); spec directory handling ([#36](https://github.com/KaiaK808/bureau/pull/36)); operator guards ([#35](https://github.com/KaiaK808/bureau/pull/35)); and doctor checks, a one-hour default stage timeout and installer fixes ([#34](https://github.com/KaiaK808/bureau/pull/34)). The exit codes keep their meaning; some stages use existing codes in new places (the review stage ends with `2` or `25` when its inline merge does not go through, the spec stage with `11` on an unusable `.specify/feature.json`, the shepherd with `25` before it claims a held ticket). No live ticket has run on this candidate yet. See the [v3.1.0-rc.1 release notes](docs/release-notes.md) for validation and known limitations.

**Upgrade:** from v3.0.2, v3.0.1, v3.0.0 or v3.0.0-rc.2 select tag `v3.1.0-rc.1` and resync the scripts scope and the interfaces scope as one set; the interfaces carry `/linear-implement` with the shared spec matcher and the managed block's corrected merge sentence. Before dispatch resumes, check what changes for a running installation, among them: test commands, hooks and agent steps no longer see `LINEAR_API_KEY`, the Telegram keys or `GH_TOKEN` / `GITHUB_TOKEN` in their environment; `.env*` entries in `repo.worktree_links` are skipped by the stages and an error in doctor; the provider's default timeout per call is 3600 s instead of 900 s; `agents.merge_require_green_ci: false` and `agents.merge_require_up_to_date: false` now switch their gates off; a repository that merges automatically without any CI gets a blocked gate and an alert 1800 s after the head commit (set `agents.merge_require_green_ci` to `false` there, or raise `agents.merge_ci_start_grace_seconds`); wrappers that run the review stage must accept `2` and `25` from it; a shepherd run on a held ticket stops with `25` before its claim; the alert throttle log moves into the repository's git directory; an instruction file with a legacy `bureau-init managed` marker stops the resync; tickets that earlier no-match stops parked in Spec without the label keep their state. New opt-in settings are `agents.implement.push_each_iteration` and `repo.untrusted_env: "clean"`. From v3.0.1 or older, the upgrade notes of the releases in between apply as well. See [Upgrade to v3.1](docs/migration.md#upgrade-to-v31).

### Untrusted code runs without Bureau secrets

#### Changed

- Code a branch controls no longer runs with the Bureau secrets in its environment. Since v3 the queue and the shepherd export `.env` to every stage, and each stage exported it again, so the review build check, the QA test runs, `repo.post_implement_command`, the Codex completion test and the agent processes all inherited `LINEAR_API_KEY` and the Telegram keys, plus any `GH_TOKEN` or `GITHUB_TOKEN` of the shell that started Bureau; a verification replay under the shepherd showed the Linear key in the review build check's environment. All of them now start through one helper, `bureau_untrusted_env` in `bureau-env.sh`: `code-review-pipeline.sh` (build check), `qa-pipeline.sh` (initial run, retry, final run), `implement-pipeline.sh` (`repo.post_implement_command`, Codex completion test), `bureau-app.sh test` and `upstream-port.sh` (build and test of the ported code); `bureau-provider.py` gives the agent process and its login check the same environment (`untrusted_env`). By default that is the stage's environment minus `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`, `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN`, minus any other variable that carries one of their values (a value of 6 characters or more anywhere inside — the stage's own `API_KEY` copy of the Linear key, a token inside a remote URL or an `Authorization` header —, a shorter one only as the whole value; a secret of 6 or 7 characters can therefore also remove an unrelated variable that happens to contain it), and minus `BASH_ENV` and `ENV`, which would make the bash child source a file such as `.env` before the branch's command runs; everything else stays, so toolchain variables keep working. The helper calls `env` as `/usr/bin/env`, so a PATH entry such as a branch's `node_modules/.bin` cannot stand in for it. The stage keeps the keys for its own Linear, GitHub and Telegram calls. QA now runs its test command in a child `bash --noprofile --norc -o pipefail -c`, as the review build check does, instead of `eval` in the stage shell, and `upstream-port.sh` runs its build and test commands the same way: a command no longer sees the stage's unexported variables and functions and no longer runs under its `set -u`. A `repo.untrusted_env` value that cannot be used refuses before any branch code runs: the provider check at the start of every model stage and the review, QA, Codex completion and app test runs end with `24`, a post-implement hook is not run and implement halts with `14` after pushing the run's commits, and `upstream-port.sh` stops with `18` before building. **Upgrade:** resync the scripts scope as one set (`bureau-env.sh`, the stage scripts, `bureau-config.sh`, `bureau-worker.sh`, `shepherd.sh`, `codex-stage-runner.sh` and `bureau-provider.py` belong together). A test command, hook or agent step that needed one of the seven variables, or relied on `BASH_ENV`, must get it another way; `gh` inside a test still finds its stored login. Installations that carry a local variant of this hardening in their stage scripts drop it with the resync.
- Bureau's own work in a stage no longer hands the secrets to branch code. Git runs the repository's hooks and filters during Bureau's own checkout, add, commit, merge and rebase, and those can come from the branch (`core.hooksPath` pointing at a tracked directory, the pre-commit framework, `lefthook.yml`, a filter that `.gitattributes` picks); a pull request that changed such a hook received every key. Every script that sources `bureau-env.sh` (`squash-marker-check.sh` now does) has a `git` function that runs each git command without the seven variables, their copies, `BASH_ENV` and `ENV`; `push`, `fetch`, `pull`, `ls-remote`, `clone`, `remote` and `submodule` keep the GitHub token variables a credential helper may read and lose the `.env` keys. A `gh` function does the same for `gh`, which runs git itself (`gh pr create` pushes), keeping the GitHub token variables it logs in with. The git and `gh` processes Bureau's Python starts — `bureau-supervision.py` (the stopped-review check runs `git ls-remote` with the review stage's environment, the workspace and checkpoint checks run `git status`), `bureau-runtime.py` and `bureau-doctor.py` — get the same environment through one helper, `process_env` in `bureau-provider.py`; an fsmonitor hook or a credential helper the operator's configuration points at a file of the branch saw every key before. Hooks and filters keep running; nothing is skipped. The executor's inline Python (`commit_stage_changes`, the worker's cleanup, `free_branch_from_other_worktrees`, `reset_worktree` and the link guard) runs with `python3 -I`: with the stage worktree as working directory, a `subprocess.py`, `pathlib.py` or `hashlib.py` the branch committed used to be imported in its place and ran with every key; `commit_stage_changes` also runs that Python without the seven. The provider (`run_stage_for`, `precondition_runner`, `codex-stage-runner.sh`) starts without the seven, so the agent's parent process does not hold them, and the runtime wrapper (`bureau_stage_enter`, `bureau-worker.sh`, `shepherd.sh`) starts without `BASH_ENV` and `ENV` (the worker changes into the branch's worktree before it starts the stage's bash, where a relative `BASH_ENV` named a file of the branch) and without the `.env` keys the relaunched script reads back from `.env` (a key that only the calling environment holds, and the GitHub token variables the stages' `gh` calls use, pass on). The Linear request gives the key to `curl` on stdin as a config line (`curl -K -`) instead of `-H` on the command line, and the Telegram alert does the same with the bot token, the chat id and the text (its log tail holds whatever a failing tool printed) instead of putting them in the URL and the arguments: `ps` shows a process's arguments to other processes, and on Linux to other users; `curl` also starts without the seven. What stays readable for code that looks deliberately as the same user — files, stored logins, the environments of the processes a stage starts after reading `.env`, the GitHub tokens in a `pre-push` hook — is listed in [SECURITY.md](SECURITY.md#code-from-the-branch-and-bureau-secrets). **Upgrade:** a Git LFS checkout that authenticates only through `GH_TOKEN` in the environment no longer gets it during checkout and reset (the smudge filter runs without the seven); use `gh`'s stored login or a credential helper. Scripts of an installation that source `bureau-env.sh` or `bureau-config.sh` get the `git` function too.
- The stages no longer link a `.env*` file into a stage worktree. A stage worktree holds no `.env` after its reset (`git clean -fdx`), but a `repo.worktree_links` entry such as `.env`, `.env.local` or `.envrc` linked the main checkout's secrets straight back in, next to the code the build check, QA and the agents run. `_bureau_link_worktree_path` in `bureau-config.sh` now skips an entry with one warning line when any path component starts with `.env` in any case, or when any component of the entry's fully resolved path in the main checkout is (a harmless name linking to `.env`, `alias/key` with `alias -> .envdir`), by the same rule `bureau-doctor.py` uses to report it as an error; beyond that rule it also skips a directory with a `.env*` name anywhere below it, and one whose search fails, an unreadable subdirectory for example (the search stops at the first hit; a virtualenv is checked in a moment). Names that only contain `env` (`env/`, `my.env`) are linked as before. When the target cannot be resolved the entry is skipped too. **Upgrade:** remove `.env*` entries, and directories that hold a `.env`, from `repo.worktree_links`; the stages read `.env` from the main checkout.

#### Added

- `repo.untrusted_env: "clean"` runs the same commands in an allow-list environment instead: only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `TEMP`, `TMP`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM`, `TZ` and `CI`, plus `BUREAU_ISSUE` and `BUREAU_BRANCH` for the post-implement hook; an agent also keeps its own login and network variables (`ANTHROPIC_*`, `CLAUDE_*`, `HEADROOM_*` for Claude, `OPENAI_*`, `CODEX_*` for Codex, the proxy variables, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `XDG_CONFIG_HOME`), and its login check runs in that environment, so a missing login fails there with `16`. A test command keeps none of the agent's extras: it also loses an SSH agent, cloud credentials, registry tokens, the proxy variables and a private CA (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`), and so breaks when it needs `CARGO_HOME`, `NVM_DIR`, `VIRTUAL_ENV`, a proxy or a private CA; an agent that logs in through cloud credentials cannot start. Absent, `null` and `"default"` keep the default above. **Upgrade:** opt-in; set `"untrusted_env": "clean"` under `repo` after checking that `repo.test_command` and `repo.post_implement_command` run with only those variables.

### Review and merge outcomes

#### Added

- `agents.merge_ci_start_grace_seconds` (default `1800`): a PR head that carries no check run at all (not even a queued one) and no commit status is blocked once its commit is older than this many seconds (`pr_ci_is_green` in `bureau-config.sh`, measured from the commit's committer time on GitHub). The merge gate read "only 0 completed check(s)" as "not yet" for ever, so a repository without a workflow, or whose workflow never triggers for the PR, kept the ticket waiting without an alert; the shepherd waited out its budget. Now the queue loop alerts (hourly per ticket) and the shepherd halts with `25` and `needs-human`. Within the grace, when a read fails (the status list, the commit time) and when `agents.merge_min_required_checks` is `0`, nothing changes. `0` blocks at once; a value that is not a plain whole number is read by the rule below (default `1800`). The gate line carries no age, so a blocked head that the queue polls gets one PR comment, not one per poll. A check that is queued but never picked up by a runner stays "not yet" as before.

#### Changed

- The review merger's answer carries the review for humans. `bureau-review.schema.json` requires a markdown `comment` (specialist summaries, findings by class with file:line, fixes needed) and a `findings` list of `{file, line, class, msg}` (`line` 0 for a finding without one line; class `CRITICAL`, `BUG`, `MINOR` or `SKIP`). A provider that enforces a schema returns only the schema's object (`bureau-provider.py` prints the structured output, not the prose), and the schema had no room for prose: the PR comment and the Linear REQUEST_CHANGES comment carried the verdict JSON alone, and the specialists' file:line findings never reached the implementer or the human merger (found by a code cross-check in one installation). The stage now posts the comment followed by the rest of the object as the fenced verdict (`review_text_from_merger` in `code-review-pipeline.sh`), on the PR and in the Linear REQUEST_CHANGES and BLOCK comments; the first line implement looks for (`Code Review.*Changes Requested`) is unchanged. The verdict is still read from the object and decided by the same ordered rules (`decide_review_verdict`); nothing in the comment can change it. An answer without a comment, or with a malformed finding, fails schema validation with `22` like any invalid provider result. A reused approval posts the same shape with an empty findings list.

#### Fixed

- The review stage acts on the result of its inline merge (merge agent off, `agents.merge_mode` auto). `merge-pipeline.sh` ended an inline run with `0` whether it merged or not, and the review stage reported "Next: Done" in every case: a PR whose checks had not started stayed in Build Review without `needs-human`, and the next poll paid for a full three-specialist review of the same head. The inline run now ends with the merge stage's own codes, and the review stage follows them: after a merge the ticket is Done as before; when the gate is not yet decided (`2`), the APPROVE is recorded like a `--no-merge` stop (`bureau-supervision.py stop --merge-gate-wait`), the ticket gets one comment naming the gate, and the stage ends with `2` — the next pick reuses the approval without a model call and without new comments, runs the build check and the gate again, and merges once the gate passes; when the gate is blocked (`25`), the stage sets `needs-human`, comments the gate lines, writes an escalation record, records the APPROVE as well and ends with `25` — once a human clears the blocker (re-runs a flaky check) and removes the label, the next run reuses the approval instead of paying a new review; a push, a moved base or an edited ticket still means a new review. A red build check on a reused approval still posts its REQUEST_CHANGES on the PR. The shepherd waits on the review stage's "not yet" as it does at Merge (`BUREAU_SHEPHERD_MERGE_POLL_SECONDS`, `BUREAU_SHEPHERD_MERGE_WAIT_SECONDS`, not counted as stuck) and halts on a blocked one through its general handling. In a disposable worker the stage resets its worktree to the reviewed head before ending with `2` or `25`: the worker keeps a worktree that is ahead of origin (the local validation merge) or dirty as unfinished work and refuses to reset it, so the next gate run could not have started. `merge-pipeline.sh --dry-run` still ends with `0`.
- `agents.merge_require_green_ci: false` and `agents.merge_require_up_to_date: false` switch their gates off. The gate read both with `jq '.x // true'`, which turns `false` into `true`, so the documented opt-out for repositories without CI never took effect (`merge_gate_required` in `merge-pipeline.sh`). Absent, `null` and `true` keep a gate on; any other value keeps it on with a warning (the doctor reads them the same way). That includes the string `"false"`, which v3.0.2 read the other way round: `jq -r` printed it as `false` and the gate was switched off, so a quoted `"false"` merged on red CI. No other boolean setting in the template is read this way.
- `agents.merge_min_required_checks` can no longer let the CI gate pass with fewer checks than written. In v3.0.2 a word (`"abc"`) made the count test fail and `pr_ci_is_green` fall through to "green", and a negative number (`-1`) counted as "no check needed": both merged a head without any check. The gate's numbers (`merge_min_required_checks`, `merge_ci_start_grace_seconds`) now follow one rule, applied the same way by the gate and by the doctor: absent or null is the default; a string that reads as a number is that number (ASCII blanks around it and one leading `+` are dropped, then digits with an optional fraction and exponent: `" 2"`, `"+2"`, `"2.0"`, `"1e3"`), a fraction is rounded up (never fewer than written), a number above 9999999 is 9999999, and a negative number or any other value is the default, each with a warning from the merge stage and the doctor (one rule: `_merge_gate_number` in `bureau-config.sh`, `gate_number` in `bureau-doctor.py`).
- The merge is pinned to the head the gate checked. `gh pr merge` ran without `--match-head-commit`, so a push that landed between the just-in-time gate and the merge call was merged without any gate having seen it (the inline merge after a review included). Every merge call now passes `--match-head-commit` with the head the gate judged (`pr_ci_is_green` checks CI on that same commit); GitHub refuses the merge when the head moved, and the merge stage then ends with `2` ("not yet", gate line `merge_head: the PR head moved …`), never with a merge and never as blocked; the next run judges the new head, and the review stage reviews it again. A head that cannot be read is "not yet" as well (`head_read:`), with no merge call.
- Linear and GitHub comments are fitted to 60,000 bytes (`bureau_cap_comment` in `bureau-config.sh`, used by `post_comment` and by the review stage's PR comment). Linear refuses a comment body over its limit with an error answer, which the transport retried and then reported as `27` "Linear unusable", so one long model answer halted a stage as if Linear were down (on Linux a body over 128 KB failed earlier still: it does not fit the single argument `jq` builds the request from); GitHub refuses a PR comment over 65,536 characters, and the review stage swallowed that failure, leaving the merge gate without the verdict comment it reads. A longer comment keeps its beginning and its end, and a note in the middle says how many bytes were left out and that the stage output has the full text. The first line (a branch marker, the review header) survives, and the last fenced JSON block (the review's verdict) is kept whole with everything after it whenever it fits; the review posts a verdict block over 16 KB without its findings list, with their count (the comment names them), so the verdict always fits. A cut moves to a line break only when one is within 4 KB, otherwise it falls between two characters, never inside a UTF-8 character. Bytes that are not UTF-8 become U+FFFD. One installation carried such a cap before v3 and lost it in the v3 resync.

**Upgrade:** resync the scripts scope as one set (`code-review-pipeline.sh`, `merge-pipeline.sh`, `bureau-config.sh`, `bureau-supervision.py`, `shepherd.sh` and `bureau-review.schema.json` belong together). Wrappers that run the review stage must accept `2` (an approved PR whose merge gate is not yet decided; nothing is wrong, run it again later) and `25` from it, as they already do from the merge stage; `bureau-tick.sh` reports them as `waiting` and `blocked`. `merge_require_green_ci: false` and `merge_require_up_to_date: false` now switch their gates off: check that a `false` in `.bureau.json` is meant. A repository without CI that merges automatically now gets a blocked gate and an alert 30 minutes after the head commit instead of waiting silently: set `agents.merge_require_green_ci` to `false` there, or `agents.merge_ci_start_grace_seconds` higher for a slow runner. A local review prompt or schema that removes `comment` or `findings` makes the merger's answer fail with `22`. A `merge_min_required_checks` or `merge_ci_start_grace_seconds` written as a string of digits now counts as that number, and a negative one as the default: `bureau-doctor.py` names the number the gate uses.

### Implement loop

#### Added

- `agents.implement.push_each_iteration`: with `false`, implement no longer pushes after every iteration and after the `/goal` run while a PR is already open for the branch when the run starts; the end-of-run push carries the whole run at once. Every push to a branch with an open PR is a `pull_request: synchronize`, so a review round that re-picks a ticket and runs three iterations started three CI runs over unfinished work, each a full run on a self-hosted runner without `concurrency` (about 12 minutes in installation A). The open-PR state is read once per run, before the `/goal` and the iteration paths split (`OPEN_PR_AT_START`, the name installation A used before v3). An empty answer, the literal `null` that `gh pr list --jq '.[0].number'` prints when nothing matches, and a failing `gh` count as no open PR, and then the stage pushes after every iteration as before: without an open PR a push starts no PR run, and it keeps the work on origin should the stage die. The end-of-run push is unchanged: retried once, and the stage ends with `18` before any hand-off when origin still lacks commits. A stage that ends before its end-of-run push pushes the deferred commits first, once and best effort, without changing its exit code: after a provider that fails, times out, runs out of quota or is interrupted, and through an EXIT trap after an unusable Linear, a crash under `set -e`, SIGTERM or SIGHUP. Otherwise the held-back iterations would sit only in the worktree, where the next run on the branch stops at the kept worktree and a run outside the worker checks the branch out again from origin. A `repo.post_implement_command` that moves HEAD off the commit it started from still gets no push of HEAD; with deferred pushes, that starting commit is pushed instead, as the per-iteration pushes would have. Only a process killed outright (SIGKILL, a host crash) leaves the commits in its worktree alone. The key is read only when `agents.implement` is an object; `agents.implement: true`, an absent key and `null` mean `true`, today's behaviour, and any other value means `true` with a warning. **Upgrade:** nothing changes by default. To defer the pushes, make `agents.implement` an object: `"implement": {"enabled": true, "push_each_iteration": false}`. An installation that carries its own copy of this behaviour drops it on resync, together with any strict xfail tests that waited for it: they now pass, and a strict XPASS fails the suite.

#### Changed

- The squash-range check now also runs inside the implement loop, after every iteration and before that iteration's push. A commit message in `origin/main..HEAD` that carries an entry of `scripts/ci-skip-markers.txt`, or a range the check cannot read, ends the loop after the iteration that wrote it with `CI_MARKER` (draft PR, `needs-human`, report on the ticket and the PR, no post-implement hook) instead of after the remaining paid iterations; the iteration log in the summary names the iteration and carries that check's report, which matters when a one-off read failure stops the loop and the final check then reads the range as clean. The check before the hand-off stays and still writes the report, the end-of-run push still puts the work on origin, and the `/goal` path, which has no iterations, keeps its single check after the run. A marker already on the branch from an earlier run now stops the loop after its first iteration. Found in a cross-check of installation A, whose pipeline checked inside the loop before v3. **Upgrade:** resync the scripts scope; no configuration change.

#### Fixed

- A `repo.post_implement_command` that changes a file which was already uncommitted before it ran, and does not commit it, now halts the stage with `14` like any other change it leaves behind. A path the agent left modified (` M a.txt`) or untracked keeps the same `git status` line however much the hook adds to it, so the line comparison could not see the change. The stage now also records the content of every such path before the hook (`git hash-object` over the paths of `git status -z --no-renames`, in one batch) and names each one that is still uncommitted afterwards with other content, under its own heading in the halt report. A symlink counts by its target text, as git stores it, so a hook that changes and commits the file a link points to leaves the link alone. A path that still changes during the 2 s after the command ended is being written by something else that is still running, typically a process the agent left behind (the provider stops its process group only on a timeout or an interrupt): it is named in the log and not counted; a slower writer can still be counted against the command. The wait happens only when there is a path to name. A pre-existing change that the hook leaves alone, rewrites with the same bytes or commits still passes. Listed as a known limitation since v3.0.0-rc.2. **Upgrade:** resync the scripts scope. A hook that edits such a file without committing it now halts the ticket; make it commit what it changes.

### Spec directory handling

#### Fixed

- The spec stage ends with `11` when `.specify/feature.json` is missing or malformed after speckit-specify, as its message always said. It read the file with jq under `set -euo pipefail`, so jq's own status ended the stage first: `2` for a missing file, `5` for invalid JSON, and `2` means "queue empty" to `queue-loop.sh` and the shepherd. The recovery trap moved the ticket back to Triage, the queue logged a quiet "queue empty" and took the ticket again on the next tick (another paid specify run), and the shepherd read `2` as ok and paid one more spec run before its stuck detector halted. A file that jq cannot parse now counts as missing, including one that holds a valid object followed by garbage. The ticket goes back to Triage without a label, as before, because a re-run may succeed.
- The spec stage refuses a stale `.specify/feature.json` instead of planning in another ticket's spec directory. The file is tracked and kept per branch, so a fresh spec worktree starts with the last value merged to `main`, and when speckit-specify did not record its new feature the stage accepted that old directory: plan and tasks wrote into another ticket's spec, and the digest posted a `bureau-branch` marker naming that ticket's branch. Stale means all three: the file holds byte for byte what it held before the specify call (compared by checksum, so a stale value written back during the call counts too), the directory it names existed before the call, and that directory is not the ticket's own. The ticket's own directory is the one in the specs directory named exactly like the last segment of the ticket's newest `bureau-branch` marker, or of the branch checked out before the call; nothing is matched loosely, because on a re-spec the worker starts on `main`, where the ticket's own directory is missing and its marker would fit a sibling by slug. Linear's generated branch name does not count. On a stale file the stage stops before plan and tasks with `11`, routes the ticket back to Triage, sets `needs-human` (a re-run reads the same file) and alerts; a Linear read that fails during the marker lookup ends the stage with its own code through the recovery trap. A file whose content speckit-specify changed is trusted. A ticket without a marker whose own directory is on `main` and named by the file is held the same way when speckit-specify records the same value again; the troubleshooting guide says how to release it (post the marker comment, remove `needs-human`).
- The `bureau-branch` marker readers skip comments whose body is empty or null. With one such comment anywhere in the list, jq failed: `get_issue_branch` (where the failure sits inside a pipe) returned Linear's generated branch name although the ticket carried a marker, and `get_issue_branch_and_comments` failed with `5`. Every stage resolves its branch through one of them.

#### Changed

- Implement, spec review and UX set `needs-human` when no spec directory matches the branch, and their comment names the branch and the specs directory. They routed the ticket back (Spec, Spec, Spec Review) without the label, where it stayed: nothing picks a ticket in Spec, the shepherd halts on `13` before its bump to Triage, and a spec run by hand does not repair a branch whose name fits no directory. A directory that matches but lacks `tasks.md` still goes back to Spec without the label, because `/speckit-tasks` can repair that; the tie case (v3.0.2) is unchanged.

### Every stage finds the ticket's own spec directory

#### Fixed

- The stages no longer hand a ticket another ticket's spec. Spec directories and branches share the form `NNN-<slug>`, but the number is not unique: some installations mint `001-<slug>` for every ticket, others repeat a number now and then, and hand-made branches reuse the number of an unrelated spec. Implement matched the number first and took the first alphabetical `NNN-*/tasks.md`, so in an installation whose spec directories all start with `001-` every ticket was built from the same, wrong tasks (branch `001-retry-queue` got `specs/001-audit-trail/tasks.md`). All of these now ask one function, `bureau_spec_dir_for_branch` in `bureau-config.sh`. It first drops everything up to the branch's last `/` (`codex/`, `exp/`, a user name) and a leading issue key such as `exp-1444-`. Then it takes a directory named exactly like the branch or its last segment, else the one directory whose slug fits the branch slug: equal, or the branch slug is its start up to a `-` (a truncated branch name), or it is a run of whole `-`-separated words inside the branch slug (a branch with extra words). When several fit, it takes the one of them that carries the branch's number. A number alone never selects a directory any more, and anything ambiguous yields no directory: QA, review and copy continue without spec context, and implement, spec review and UX stop with `13`, name the tied directories, set `needs-human` and route back (Spec, Spec, Spec Review), because running Spec again cannot resolve two fitting directories. The implement fix was first written in June 2026 on a branch that never reached `main`; this change carries it, extends it to every stage and to prefixed branch names, and drops its number-only fallback, which in a replay of 1,889 real branch/listing pairs from eight installations made 7 answers wrong and none right. **Upgrade:** resync the scripts scope as one set. Installations whose spec directories repeat an `NNN-` prefix (check with `ls specs | cut -d- -f1 | sort | uniq -d`) are affected and should resync before the next implement run; a hand-patched matcher in `implement-pipeline.sh` is replaced by the shared function. A branch that fits two spec directories equally now stops with `needs-human` instead of picking one — rename or remove the stray directory. ### Stage worktrees get their virtualenv back after each reset

#### Added

- `repo.worktree_links`: a list of relative paths, for example `[".venv"]`, that `reset_worktree` symlinks from the main checkout into every stage worktree after its `git clean -fdx` (`bureau_link_worktree_paths` in `bureau-config.sh`). The reset removed every ignored path, a Python virtualenv included, and only `node_modules` came back (`restore_worktree_deps`); agents following a spec that says `.venv/bin/python` failed, and tickets were parked for a human (seen in installation A, which linked `.venv` by hand after the reset). The default is an empty list, which changes nothing. A path is skipped with one warning line when the entry is not a plain relative path (absolute, `.`, `..`, `.git` in any case, or an empty component; a leading `-` is fine), when the branch tracks it, when its parent is missing in the worktree, leads outside it or runs through a symlink in it, when it does not exist in the main checkout, when the worktree's gitignore does not ignore it as a symlink (an untracked link leaves the worktree dirty, the worker preserves it and the next reset stops with `21`; a directory-only pattern such as `.venv/` does not match a symlink), or when a real file or directory is at that path; an older link is replaced. The next reset removes the link, never its target; the main checkout itself and worktrees of a bare repository are never linked. **The link is the main checkout's own copy**: every stage and parallel worker shares it, and commands in a stage worktree act on it (`python3 -m venv --clear .venv` empties it, `rm -rf .venv/` deletes it, and pull-request code that QA or the review build check runs can change it); the configuration reference says so, and `scripts/bureau-stage.md` tells stage agents never to delete, recreate or clear a linked path and not to install into it unless the ticket asks. `bureau-doctor.py` reports `worktree_links` with a status per entry, asks git about each path the way a stage worktree sees it (as a symlink, not as the main checkout's directory), warns about missing, tracked or not-ignored paths, rejects entries that are not plain relative paths, and treats `false` like an absent key, as the stages do. The configuration reference has a note for Python repositories with editable installs, whose linked virtualenv imports the main checkout's `src/` unless the worktree's comes first (`PYTHONPATH=src`). The copies of `.env` and `.bureau.json` that the same installation made are not needed: the stages find both through the main checkout. The stage agents also get a one-sentence version of that rule in the system text of every stage call (`run_stage_for`), which comes from the main checkout and so applies from the first reset on; the rule is tied to what an agent can see (a path that is a symlink pointing outside the worktree), so installations without links are not affected. A repository whose git directory is kept outside the main checkout (`--separate-git-dir`) is skipped with its own message. **Upgrade:** resync the scripts scope as one set and **commit the resynced scripts to `main` before enabling `repo.worktree_links`**, so that the stage protocol the agents read in their worktree carries the full rule; then add `"worktree_links": [".venv"]` under `repo`, list `.venv` (without a trailing slash) in `.gitignore`, and check `bureau-doctor.py`.

QA removes its temp dir when it ends 25 for an unwritten label.
- `queue-loop.sh` reports a pick that fails with 27 (log line and alert, throttled per stage per hour) instead of reading it as an empty queue; any other pick failure is logged and still treated as empty. The picker's own notes (held and blocked tickets, retries) now reach the queue log instead of `/dev/null`.

**Upgrade:** none beyond the scripts resync. A ticket can only stay held when its label can never be written (for example no `needs-human` label for the team or the workspace); fix the label or delete the hold file. Runs that name the ticket explicitly (a shepherd) do not read the hold. An implement halt whose label could not be written now ends with 25; unpushed work in that worktree is preserved and later implement runs there end with 21 until a human resolves it (before, the 0 let the next reset discard it).

### Linear answers checked in transport (EXP-1482)

#### Fixed

- A Linear request now has a time limit (`--max-time` 30 s, `--connect-timeout` 10 s by default; `BUREAU_LINEAR_MAX_TIME` / `BUREAU_LINEAR_CONNECT_TIMEOUT` or `.linear.request.*`). Before, a hanging request never reached the retry ladder. A request cut off at the limit is `no-response` and is retried; with the defaults a Linear that stays unusable ends the stage with 27 after at most 220 s.
- An answer with an HTTP status outside 2xx is unusable even when its body is well-formed JSON. Before, an error page with the body `{"data":{}}` counted as a success, every reader answered "nothing" with exit 0, and the shepherd slept forever or walked past `needs-human`.
- `{"data":{}}` and a root field that is `null` without `errors` are unusable (`no-data`): every root field the template asks for is non-null in Linear's schema.
- A NUL byte in the answer makes it unusable (`not-json`). The shell used to drop NUL bytes while capturing, so a broken answer could reach the check already cleaned.
- The issue readers (`get_issue_detail`, `bureau_issue_snapshot` / `get_issue_state`, `get_issue_branch`, `get_issue_branch_and_comments`, `get_issue_comments`) require the list they read (labels, state, comments) and go through the retry ladder when it is missing, instead of reading a missing list as an empty one. A ticket without labels, without a branch marker, and an issue query that matches no ticket stay usable answers with exit 0.

Upgrade action: none. A repo whose Linear requests legitimately take longer than 30 s sets `BUREAU_LINEAR_MAX_TIME`. A limit of 0 is invalid (it would mean "no limit" to curl): the warning names the key and the next source applies, `.bureau.json` before the default. A halt path makes one attempt per write without retry waits, so a halt with N writes takes at most N × the time limit. Limits: the fault classes stay the four names the shepherd knows; a timeout is logged as "no answer within Ns" and classed `no-response`. A curl double in a test that prints no `-w` status line is judged by its body alone.

### Shepherd outside the stages (EXP-1482)

#### Fixed

- The shepherd's own moves (`--from-stage`, and the bump from Spec to Triage) no longer end it bare under `set -e` when they fail: `27` takes the Linear halt (alert with the fault class, one attempt each at `needs-human` and a halt comment), any other code halts with `1`, `needs-human` and a comment. `--from-stage` now moves the ticket after the shepherd claims it, so the queue keeps away from a ticket that just moved into a stage's waiting room.
- Ctrl-C or SIGTERM ends a shepherd run as cancelled (`130`): the claim is released and nothing else is written. Before, the INT/TERM trap only released the claim and the loop went on, so the next read or stage ran on a ticket nobody held; a SIGTERM sent to the shepherd alone waited out a 60 s sleep first. The shepherd's waits can now be cut short.
- The start check names its cause: a failed Linear check before the claim still ends with `10`, now with an alert naming the fault class, and writes nothing to the ticket.
- Linear answering without a state is no longer waited out forever: the fifth such answer in a row halts with `1`, `needs-human`, a comment and an alert.
- A moment-old read after a move no longer decides the next stage (EXP-1476): after `--from-stage` a read that does not yet show its target, and after the bump to Triage or a stage that returned `0` a read that still shows the state the ticket left, is read again up to three times, 5 s apart (`BUREAU_SHEPHERD_CONFIRM_SECONDS`, whole seconds; anything else falls back to 5 with a warning). A read that already shows the move costs no extra read and no wait; a ticket that really stayed where it was reaches the stuck detector 15 s later than before.
- A typo in `--from-stage` is refused before anything is claimed.
- A relative `shepherd.sh --worktree DIR` (the form its help recommends) is taken from the repo root and made absolute before it is handed on. Before, it reached `bureau-worker.sh` as it was; the worker changes into the worktree, so its cleanup ran `git -C <relative>` from there and the shepherd halted with `128` after a stage that had finished (found by the rc.1 pilot, EXP-1533). `bureau-worker.sh` now makes a relative worktree absolute itself too, for every caller. Workaround on rc.1: pass an absolute `--worktree`.

### From the brainhuggers-cli pilot

#### Added

- `repo.post_implement_command`: an optional hook the implement stage runs wherever it releases the work for review (a run that ends COMPLETE, whether or not it made commits of its own, and a PARTIAL run with commits, whose PR is marked ready; never in a dry run), after the loop and before the squash-range check and the final push. It is for a repository that derives files from an implementation, such as regenerated docs or command contracts, and replaces a local patch to `implement-pipeline.sh`. It runs in the implement worktree via `bash -o pipefail -c` with no stdin, `BUREAU_ISSUE` and `BUREAU_BRANCH` set, and a limit of `BUREAU_POST_IMPLEMENT_TIMEOUT` seconds (default 900, capped at the stage's total time, also accepted from `.env`); a timeout sends SIGTERM to its process group and SIGKILL to whatever is left after 5 s. It commits its own output, and it must be idempotent and exit 0 when there is nothing to commit (a bare `git commit` exits 1 then). A non-zero exit, a timeout, uncommitted changes it leaves (kept in the worktree, not deleted) or a HEAD that no longer contains the commit it started from (then nothing is pushed) halt the ticket like any other halt status and end the stage with `14`. Doctor reports the command and rejects a value that is not a string.

#### Fixed

- A failed final push in the implement stage no longer hands the ticket on while origin lacks commits. The push after the loop was non-fatal, so the PR was marked ready and the ticket moved to QA or Build Review with work that was not on origin. Now a failed push is retried once after 3 s; if it fails again, the branch is fetched from origin (a rejected push does not update the local `origin/<branch>`), and if `origin/<branch>..HEAD` then holds commits, or the fetch or the comparison fails, the stage says so on the ticket, with the hook's report when the hook failed too, and ends with `18` before any hand-off, and the worker keeps the worktree because it is ahead of origin. If origin already has every commit, the usual case after the per-iteration pushes, a failed push changes nothing and the stage goes on. The per-iteration pushes stay non-fatal. **Upgrade:** a driver that treated the implement stage's `0` as "pushed" sees `18` when origin refuses commits it does not have.

## [3.0.0-rc.1] - 2026-09-28

Release candidate for Bureau v3.0.0, published as a GitHub prerelease. It collects the hardening carried over from the installations ([#11](https://github.com/KaiaK808/bureau/pull/11)), source recording in the installer ([#12](https://github.com/KaiaK808/bureau/pull/12)), the review build check via `repo.test_command` ([#13](https://github.com/KaiaK808/bureau/pull/13)), fail-closed shepherd reads ([#14](https://github.com/KaiaK808/bureau/pull/14)) and the merge policy as configuration ([#15](https://github.com/KaiaK808/bureau/pull/15)). The major version marks the changed exit-code contract: a review BLOCK ends with `25` instead of `0`, a Linear that stays unusable ends a stage with the new code `27`, and the shepherd halts with an alert on every code except `0`, `2`, `10` and `16`. v3.0.0 follows once a pilot installation has qualified one ticket with this candidate. See the [v3.0.0-rc.1 release notes](docs/release-notes-v3.0.0-rc.1.md).

### Merge policy as configuration

#### Added

- `agents.merge_mode` (`"auto"` default, `"manual"`): with `manual` a human merges. The merge and rebase agents are off for every dispatcher; `merge-pipeline.sh` and `rebase-pipeline.sh` exit `2` before any Linear, gh or git call; an APPROVE parks the ticket in the Merge state; the shepherd ends at Merge with `20`. **`manual` needs `linear.teams[0].states.merge`**: without it the review stage refuses at its start with `24`, and doctor reports an error. The mode holds regardless of `agents.merge`, `agents.rebase` and the shepherd's forced stages; any value but exactly `auto` or `manual` falls closed to `manual` with a warning. `bureau-status.sh --config` and `bureau-doctor.py` (`merge_mode`) show the mode in effect. See the [recipe](docs/recipes.md#merge-by-hand).
- **Upgrade action:** installations that disabled merge and rebase by hand (an early `exit 2` at the top of both scripts, as in installation C and installation A) check that `linear.teams[0].states.merge` is set, then set `"agents": {"merge_mode": "manual"}` in `.bureau.json` **before resyncing** the scripts. The resync replaces the local block; without the key automatic merging is on again, and without the Merge state code review refuses with `24`.

#### Changed

- The shepherd and the queue loop no longer alert on a stage's exit `20` (stopped before merge) when `--no-merge` / `BUREAU_NO_MERGE` asked for it. A `20` nobody asked for still halts with an alert.

### Hardening carried over from the installations

The hardening list from installation A and installation B in `docs/2026-09-25-drift-inventar.md`, each item with a test that runs the real code and a negative control against the broken form. Two items were already closed by the v2 runtime (model values reach the provider as one argument; `reset_worktree` returns its status and finds `.env` and `.bureau.json` via the main checkout) and now have a test or a note instead of a change. **Resync each adopting repository** to receive them.

#### Changed

- A review BLOCK (and any unknown verdict) ends the review stage with exit `25` instead of `0`. `shepherd.sh` now halts with an alert on every exit code except `0`, `2`, `10` and `16`; codes it did not list before (`22` to `26`) used to stop without an alert.
- A Linear answer that is unusable (no response, not JSON, GraphQL `errors`, no `data`) is retried after 10, 30 and 60 seconds and then ends the stage with the new exit code `27` (`linear-unusable`); the shepherd halts, alerts with the fault class and tries `needs-human` and a halt comment once. Tune with `BUREAU_LINEAR_RETRIES` / `BUREAU_LINEAR_RETRY_WAIT_1..3` or `.linear.retry.*`.
- The implement stage no longer writes `[skip ci]` into iteration commits and no longer adds an empty "CI re-trigger" commit. With a PR open, each iteration's push now runs CI.
- `agents.max_concurrent_issues` counts leaf issues of the configured `linear.projects`: sub-issues count, epics and other projects do not.
- The cross-check of a new spec against open PRs runs under macOS's `/bin/bash` 3.2 and reports clean, conflicts or incomplete; anything but an explicit clean posts a warning on the ticket.

#### Fixed

- `.env` is parsed, never sourced, by all sixteen pipeline scripts.
- A red build can no longer soften a review BLOCK into rework.
- Squash and merge set their own sanitised subject and body, so no CI suppressor reaches `main`; the implement and QA stages halt (`CI_MARKER` / `needs-human`) when a commit message in the squash range carries one.
- Labels resolve to the issue's own team (then a workspace label), and a failed lookup is never reported as "no such label".
- An npm project's `node_modules` is restored after the worktree reset (`npm ci --ignore-scripts`, clone on identical manifests); a failure stops with `24` instead of building red.
- A failed implement push is reported with branch, exit code and git's output, and a detached HEAD pushes to `refs/heads/<branch>`.
- The review build check runs `repo.test_command`, then `scripts/bureau-test.sh`, then `npm run build`. The first two steps are the QA stage's; QA's further fallbacks (`npm test`, `cargo test`, `pytest`, `go test`) are not used in review. It used to run only `npm run build`, so a repo without `package.json` was never checked and the review comment still said "Passed"; now it says "not checked" and warns on stderr, and the verdict is left alone. A red check goes through the verdict floor like a red npm build; the command runs under pipefail as QA's does, and its status is the command's own, not that of a pipe into `tail`. New files the check leaves that git does not ignore, and tracked files it changes, are named on stderr, each with its own advice. **Upgrade:** an installation that ran another local script in the review build check sets `repo.test_command` to it before resyncing (installation A's `scripts/bureau-test.sh` is found as it is). A repo with both `repo.test_command` and `package.json` now runs the test command in review instead of `npm run build`. The command runs in the review worktree, so its output must be ignored by git.
- `shepherd.sh` no longer reads a failed Linear read as "no state", "no label" or "no branch" (EXP-1528). When its own read of the ticket's state, labels or branch gives up with `27`, it halts like a stage that gave up: alert with the fault class, then `needs-human` and a halt comment tried once each. Any other failed read halts with `1` and `needs-human`; a read cut short by Ctrl-C or SIGTERM ends as a cancelled run (`130`) and writes nothing. Before, an unusable Linear walked past `needs-human`, left the state loop waiting forever, ended a stage as `12` (no-branch) under the wrong name, and let `--dry-run` report success with the state "unknown". The label list is now read once per iteration instead of up to three times, and the dry run removes its fault file on every way out.

### Installer records its source

#### Added

- An asset `--apply` records in `.bureau-install.json` which Bureau source revision it installed from: under `sources`, per scope it wrote (`scripts`, `ci`, `workflows`, `interfaces/claude`, `interfaces/codex`), the exact tag or `null`, the nearest `git describe --tags`, the full commit and whether the source was dirty (checkout changes, or any file the batch reads that differs from its blob at that commit, gitignored files included); a source that is not its own Git checkout is recorded as `not a git checkout`. The preview prints the same `source` before anything is written. A preview or an apply stopped by a conflict records nothing, and an apply that finds the carried record stale drops it and records only the scopes it wrote.
- Doctor reports `template_source`: `recorded`, `source not recorded` (no manifest, one written before this change, or no scope recorded yet; not an error), or `stale` with a warning when file hashes changed after the record was written, as an installer without source recording leaves it once it changed a file.

Upgrade action: none. The manifest stays at version `1` and installers without source recording still read it; the next asset `--apply` records the source.

### Upgrade actions and known limitations

- Select source tag `v3.0.0-rc.1`, then resync the scripts scope in each adopting repository as one set, one pull request per repository. Set `agents.merge_mode: "manual"` (with a Merge state) and `repo.test_command` **before** the resync where they apply, make `.gitignore` cover what `repo.test_command` writes, and update repository tests that assert the old exit codes in the same pull request. See [Upgrade to v3](docs/migration.md#upgrade-to-v3).
- Exit code `24` (`environment-blocked`) already existed; it is now also used when an npm project's dependencies cannot be restored after the worktree reset and when `merge_mode` is `manual` without a Merge state. `27` (`linear-unusable`) is new. A read of the shepherd's own cut short by Ctrl-C or SIGTERM ends as a cancelled run (`130`).
- Validation: the full Linux/macOS suite, the installer fixtures and one independent verification pass per pull request #12–#15. No adopting repository has run this candidate on a live ticket yet.
- Known limitations: under `manual` nothing moves a ticket from Merge to Done after the merge by hand; a `manual` repository without a Merge state refuses review with `24` on every tick until it is configured; the review build check does not use the QA stage's further fallbacks; a genuinely empty ticket state still makes the shepherd retry every 60 seconds; a file Git ignores inside `templates/scripts` (such as `.env`) is copied into the target, and the source is then recorded as dirty.

## [2.0.0] - 2026-09-07

### Claude Code and Codex support

Bureau v2.0.0 includes the Claude/Codex integration and its review fixes ([#9](https://github.com/KaiaK808/bureau/pull/9)). It is the first versioned release; the public initial snapshot was labeled v1.0.0 but had no corresponding tag or GitHub Release. The major version marks the operational changes for existing workers and upgrades. Installing a source update still requires a target-repository resync. See the [v2.0.0 release notes](docs/release-notes-v2.0.0.md).

#### Added

- Claude/Codex/both installation targets, native Codex skills and AGENTS.md, plus a `$bureau` operator that works in the current app task. Existing Claude commands remain available.
- Deterministic asset previews, installation hashes, per-file conflict handling and preservation of project instructions, active Spec Kit integration and constitution.
- Shared Claude/Codex provider adapters, bounded background ticks, quiet supervision, read-only diagnostics and additive config migration with an exact private backup.
- An upgrade/conflict guide, an explicit source-update versus target-resync procedure, and a release process for dated notes, immutable tags and GitHub Releases.
- Linux/macOS qualification and an acceptance record that distinguishes fixtures, live provider smoke and the limits of live adopting-ticket validation.

#### Changed

- Background workers require explicit registration and issue/workspace ownership. Old unregistered worktrees and app-owned checkouts refuse automatic reset. Interrupted runs retain ownership for inspected recovery.
- App review and bounded ticks stop before merge by default. Continuous pipelines retain gated merging; use `--no-merge` when that boundary is required.
- Legacy generic model settings retain their Claude meaning. V1-to-v2 config migration records `model_compatibility: v1`; opting into v2 generic model semantics is a separate choice. Installing Codex interfaces does not switch the background provider.
- Completed review stops persist across ticks. New ticket/remote inputs or explicit resume reopen review; preserved clean review checkpoints can be retained while another verified worker proceeds.

#### Fixed

- Background code review uses the pull request's actual target branch, including dependent PRs. It pins the fetched base and head for review; changing the target or either remote commit invalidates a saved review stop. Missing or invalid target metadata stops review before provider calls.

- Provider timeout and cancellation now stop descendants that ignore termination after the immediate CLI process exits. Cleanup covers the whole process group before the bounded invocation returns, preserving timeout/cancellation exit codes.

- Setup now selects one active Linear team, matching runtime support. Model-update guidance preserves v1 Claude defaults when configuring Codex and verifies effective provider settings. Historical analysis links point to the reviewed source baseline; public qualification claims stay within the documented evidence.

- Explicit review-only requests remain enforced when a pipeline loads an older environment file. Review and merge gates retain the captured caller boundary even if that file clears user-facing stop flags; an ordinary run without a stop request keeps its existing behavior.

- Adding Codex to a legacy installation now registers an existing Git extension's native hook skills through the pinned Spec Kit CLI, preserving customized skills and hook settings. Refreshed instructions map dotted hook names and explicitly select feature directories across retained and current helper versions.

- Symlinked worker paths (including macOS `/tmp`) resolve to their physical checkout before branch-owner comparison, preventing a worker from falsely conflicting with itself while retaining protection for other checkouts.

- Surviving nested workers can no longer release a checkout for an unsafe automatic reset. Human blockers remain visible to scheduling and notifications.
- App finish retries cannot publish contradictory results; routing uses current labels and background implementation consumes app review feedback.
- Newly created QA/spec-review/copy files are published, rejected pushes prevent advancement, and staged private files refuse publication without losing staged work.
- Legacy Spec Kit active integrations survive adding a second host. Diagnostics reject generic instruction files as installation evidence and detect missing GitHub dependencies.

#### Upgrade actions and limitations

- Select source tag `v2.0.0` first, then use `/bureau-init --resync-interfaces --resync-scripts --target both` in each adopting repo (or `--target claude` to stay Claude-only). In Codex, use `$bureau-init` with the same arguments. Refresh Spec Kit separately with `--resync-speckit`; refresh installed planning workflows with `--resync-workflows` if used. CI scaffolding stays opt-in.
- Pause dispatch, preserve local/ignored files and reconcile conflicts before starting the new runtime. Differing files without a prior manifest are conflicts, not disposable generated output. See the [per-file resolution procedure](docs/migration.md#preview-and-resolve-asset-conflicts).
- Configuration migration is optional while v1 is supported. Review dependencies, model ownership, old worker checkouts and rollback limits in the [upgrade guide](docs/migration.md).
- A representative live adoption exercised app stages, a bounded Codex route, a mixed-provider route, interruption/resume, real project tests and durable review stops. This is not a qualification of arbitrary projects or recurring unattended dispatch; private evidence is summarized separately from reproducible source checks in the [acceptance record](docs/codex-acceptance.md).
