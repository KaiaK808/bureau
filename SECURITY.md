# Security policy

## Reporting a vulnerability

Do NOT open a public GitHub issue for a security vulnerability. Public issues are indexed and searchable immediately.

Instead, email the maintainer directly:

- **Kai Ebert** — 808.meets.303@gmail.com

Include:
- A clear description of the vulnerability
- Steps to reproduce (a minimal repro, ideally against a fresh `/bureau-init` install)
- What you believe the impact is (e.g., "an operator running `/bureau-init` in a repo controlled by another user could exfiltrate the operator's `.env`")
- Any suggested fix, if you have one

You should get an initial acknowledgement within a few days. If the vulnerability is confirmed, a fix will land on `main` and the reporter is credited in the release note unless they prefer anonymity.

## Supported versions

Only `main` is supported. Bureau doesn't cut tagged releases; every merged PR ships to every installed clone the next time an operator runs `git pull` in `~/.claude/skills/bureau-init/` or `/bureau-init --resync-scripts` in a target repo.

If you're pinned to an older SHA, upgrading to current `main` is the fix. There's no LTS branch.

## Scope

**In scope:**
- The templates in `templates/scripts/` (the shell scripts installed into target repos)
- The `/bureau-init` skill logic in `SKILL.md`
- The upstream-port fast-path in `templates/scripts/upstream-port.sh`
- The `docs/site/` HTML docs

**Out of scope:**
- Vulnerabilities in target repos' own code (that's the repo owner's responsibility)
- Vulnerabilities in Claude Code itself (report to Anthropic)
- Vulnerabilities in Linear, GitHub, or the `gh` CLI (report to the respective vendors)
- Vulnerabilities in [caveman](https://github.com/JuliusBrussee/caveman), [Headroom](https://github.com/headroomlabs-ai/headroom), or [speckit](https://github.com/github/spec-kit) — those are third-party dependencies with their own security policies

## Code from the branch and Bureau secrets

Bureau runs code a branch controls before any human has reviewed it: the review build check (`repo.test_command`, `scripts/bureau-test.sh` or `npm run build`), the three QA test runs, `repo.post_implement_command`, the Codex completion test, the app `test` action, the build and test commands of `upstream-port.sh`, and the agent processes, which run the branch's tests themselves (Claude with `--dangerously-skip-permissions`) and load the branch's own agent settings and hooks. Since v3.1 each of them starts in a reduced environment (`bureau_untrusted_env` in `scripts/bureau-env.sh`, `untrusted_env` in `scripts/bureau-provider.py`). By default it lacks `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`, `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN`, every other variable that carries one of their values (a value of 6 characters or more anywhere inside, such as the stage's `API_KEY`, a remote URL with a token in it or a copied `Authorization` header; a shorter one only as the whole value, because matching two to five characters inside other values would remove variables that merely contain them), and `BASH_ENV` and `ENV`, which would make a bash child source a file such as `.env` before the branch's command runs. It also lacks `BUREAU_ENV_FILE` and `BUREAU_CONFIG`: no secrets, but the absolute paths to the operator's `.env` and `.bureau.json`, which until v3.3.0 only `clean` removed; Bureau's own scripts keep reading them, and none of the commands above needs them. With `repo.untrusted_env: "clean"` it holds only a short list of base variables (see the [configuration reference](docs/configuration.md)). The stage itself keeps the keys for its own Linear, GitHub and Telegram calls; since v3.2 it holds the three `.env` keys as shell variables it never exports (see "Bureau's own processes" below).

Branch code also gets in through Bureau's own work, and there the keys are kept out as well:

- **Git hooks and filters.** Bureau's own git commands in a stage (checkout, add, commit, merge, rebase, reset, cherry-pick and the rest) run the repository's hooks and filters, and those can come from the branch: `core.hooksPath` pointing at a tracked directory, the pre-commit framework's `.pre-commit-config.yaml`, `lefthook.yml`, husky v4's `package.json`, a filter that `.gitattributes` picks. Every git command in the stage scripts goes through a `git` function (`scripts/bureau-env.sh`) that runs it without the seven variables, their copies, `BASH_ENV` and `ENV`; the git and `gh` processes Bureau's Python starts (`bureau-supervision.py`, `bureau-runtime.py`, `bureau-doctor.py`, through `process_env` in `bureau-provider.py`) get the same environment, so an fsmonitor hook or a credential helper they run sees no key either; `gh`, which runs git itself, goes through a `gh` function that removes the `.env` keys and keeps the GitHub token variables it logs in with. Hooks and filters of local commands keep running; since v3.2 Bureau's git commands that talk to a remote run without hooks (see "Git commands that talk to a remote" below).
- **Python modules in the branch root.** Every start of Python in the scripts runs with `python3 -I`: inline code and Bureau's own helpers (`bureau-supervision.py`, which the review stage and the worker's cleanup run in the branch's worktree, `bureau-runtime.py`, `bureau-provider.py`, `bureau-doctor.py`), so a `subprocess.py`, `json.py`, `pathlib.py` or `hashlib.py` the branch commits cannot stand in for the standard library, also when the operator's `PYTHONPATH` has an empty or relative entry, which names the working directory.
- **Bureau's own processes.** The stages, the drivers (`queue-loop.sh` and its supervisor, `bureau-tick.sh`, `shepherd.sh`, `bureau-worker.sh`) and the runtime's own Linear calls read `.env` through `bureau_load_env` (`scripts/bureau-env.sh`), which since v3.2 sets `LINEAR_API_KEY`, `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ALERT_CHAT_ID` as shell variables of the reading script and never exports them, even when a parent shell exported them; the other `.env` keys are exported as before. The processes a stage or driver starts — its `gh`, `jq`, `date` and Python helpers, the next stage — therefore start without them; a Bureau script that needs a key reads `.env` itself, and the stages' copy `API_KEY` is not exported either. The runtime read `.env` for its own Linear calls by running it as shell code (`set -a; source`); it parses it with `bureau_load_env` now. An operator shell that ran `set -a` and exported `SHELLOPTS` starts every Bureau bash with allexport on, which would export each later assignment, the `API_KEY` copy included, and every function Bureau defines: `bureau-env.sh` and `bureau-config.sh` switch it off before they define anything, and `bureau_load_env` again. A shell traced with `bash -x` or with `xtrace` in an exported `SHELLOPTS` prints each command with its words expanded; the stages look at and copy the keys through `bureau_secret_set` and `bureau_secret_copy`, and the Telegram alert reads them only inside its traceless subshell, so the trace on stderr and in the queue logs shows no key (tracing a stage is otherwise supported). `bureau-provider.py`, the agent's parent, starts without the seven. The runtime wrapper `bureau-runtime.py`, an ancestor of every stage, starts without `BASH_ENV` and `ENV` — the worker changes into the branch's worktree before it starts the stage's bash, so a relative `BASH_ENV` would name a file of the branch — and without the `.env` keys that the stage it relaunches reads back from `.env`. The Linear and Telegram requests give the key, the bot token, the chat id and the alert text (whose log tail can hold whatever a failing tool printed) to `curl` on stdin (`curl -K -`), never in its argument list, which `ps` shows to other processes and on Linux to other users, and `curl` starts without the seven. The helpers call `env` as `/usr/bin/env`, so a PATH entry such as a branch's `node_modules/.bin` cannot stand in for it.

This closes the accidental paths — a dependency or build step that reads, logs, uploads or bundles its environment, a test that prints its environment into a log that ends up in Linear or on a pull request — and the ways in listed above. Code that deliberately looks for the keys while running as the same Unix user as Bureau can still find them. What stays open, stated so nobody relies on more:

- **Files.** The main checkout's `.env` (the file the stages read, `BUREAU_ENV_FILE`) and `.bureau.json` are readable by the same user. Since v3.2 every script reads `.env` only from `BUREAU_ENV_FILE` — by default the `.env` next to `.bureau.json` in the main checkout; a relative value counts from that directory — and never `./.env` of its working directory. Before, the stages read `./.env` first, and the worker starts them in the branch's worktree: the reset (`git clean -fdx`) removes only untracked files, so a `.env` the branch committed supplied the Linear key, the Telegram bot and chat, and settings such as `BUREAU_RUNNER_*`, `BUREAU_NO_MERGE` or `BUREAU_DRY_RUN`. Such a file now stays in the worktree unread, and `bureau-doctor.py`, which reads `BUREAU_RUNNER_IMPLEMENT` from `.env` for its `repo.test_command` warning, reads the same file by the same rule, also when it runs in a linked worktree. Stage worktrees hold no untracked `.env` after their reset, and the stages skip a `repo.worktree_links` entry that is a `.env*` file (any path component starting with `.env` in any case, or an entry whose fully resolved path in the main checkout passes through such a name, as `alias/key` with `alias -> .envdir`) with one warning line; `bureau-doctor.py` reports such an entry as an error. The stages also skip a directory with a `.env*` name anywhere below it, and one they cannot search completely (an unreadable subdirectory; with GNU find also a link loop, which the BSD find of macOS skips); doctor runs the same search and reports both as errors too. The search matches names and follows links into directories, so a link under another name that points at a `.env` file (`creds -> ../.env` inside a linked directory) is not detected. Removing `BUREAU_ENV_FILE` and `BUREAU_CONFIG` from branch code hides only where an operator put a `.env` or `.bureau.json` outside the default place; the default place is the main checkout, which `git rev-parse --git-common-dir` names from any stage worktree.
- **Stored logins.** Removing `GH_TOKEN` and `GITHUB_TOKEN` does not remove `gh`'s own login: `gh auth token` prints the token stored in `~/.config/gh/hosts.yml` or the system keychain, and a git credential helper (`git credential fill`, the macOS keychain helper) hands out the GitHub credential the same way. The same holds for any tool that keeps its login under `~/.config` or in the keychain.
- **Git commands that talk to a remote.** `push`, `fetch`, `pull`, `ls-remote`, `clone`, `remote` and `submodule` keep `GH_TOKEN`, `GITHUB_TOKEN` and the enterprise variants, which a credential helper may read; they lose only the `.env` keys. Since v3.2 Bureau runs them without the repository's hooks, so a hook from the branch no longer sees the GitHub tokens during them: no `pre-push` on a push, no `reference-transaction` on the ref updates a fetch or a push makes, no merge hooks during a pull. The `git` function adds `-c core.hooksPath=/dev/null` (hooks in a hooks directory) and switches off the hooks the configuration defines (`hook.<name>.command` with `hook.<name>.event`, git 2.54 and later; the pre-commit framework sets up its `pre-push` stage this way, running hooks from the branch's `.pre-commit-config.yaml`), which `core.hooksPath` does not reach: `hook.<event>.enabled=false` for every event git knows (git 2.55) and `hook.<name>.enabled=false` for every name `git config` lists for the command, the empty name `[hook ""]` included and an inherited `GIT_CONFIG` (which only `git config` reads) ignored (git 2.54, and git 2.55 where a hook named like an event turns the event switch into a per-name one). `repo.remote_git_runs_hooks: true` runs them with hooks again, as in v3.1; then such a hook sees the tokens, a hook the branch supplies through `core.hooksPath` pointing into the working tree (husky's `.husky`, a tracked `.githooks`) included. `repo.remote_git_runs_hooks: "operator"` runs only the hooks in the main checkout's own hooks directory, `hooks/` in the git common directory, which no commit can write: the `git` function sets `core.hooksPath` to that directory's absolute path in place of `/dev/null`, whatever `core.hooksPath` the configuration names, and keeps the per-name switches for the hooks the configuration defines; it leaves out the event switches, because git 2.55 reads `hook.<event>.enabled=false` as "no hook for this event", the hooks directory's included. Those operator hooks see the GitHub tokens like any hook under `true`. When git cannot name the common directory (a command outside a repository) and for `clone`, `"operator"` keeps every hook off. With the hooks restricted (`"operator"`, and the default where they are off) Bureau's remote git never recurses into submodules: every call carries `-c push.recurseSubmodules=no -c fetch.recurseSubmodules=no -c submodule.recurse=false` (`fetch.recurseSubmodules` defaults to on-demand), and a call that asks for recursion itself (`git submodule`, `--recurse-submodules` other than `=no`, a recursion key in git's own `-c` or `--config-env`) is refused with exit 128 before git runs; no Bureau script makes one. A child git in a submodule reads that submodule's own configuration, where a hook the configuration defines (also through an included tracked file) has a name Bureau cannot list beforehand; git 2.54 has no event switch, and on git 2.55 a hook named like an event (`hook.pre-push.command`, even without an event) turns the event switch into a per-name one, so such a hook would run with the tokens in either mode. Turning recursion off is the one rule that covers every such child, where switching off each child's hooks by name would need git to ask Bureau for every submodule. Bureau's push therefore neither pushes nor checks submodule commits unless the key is `true`. The forced `core.hooksPath` is a command-line option, which git ranks above every configuration file, an `include` or `includeIf` that names a file in the working tree, and `GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS` in the environment. What this covers, and what not:
  - Covered: every git command in the stage and driver scripts (and `upstream-port.sh`), which all go through the `git` function. The remote git commands Bureau's Python starts, the two `git ls-remote` of `bureau-supervision.py` (a stopped review's check and the pickers' gate waits), carry `core.hooksPath` and the event switches; `ls-remote` updates no ref and fires no hook event, so they change nothing there and `repo.remote_git_runs_hooks` has nothing to bring back.
  - Local commands (commit, checkout, merge, rebase, reset, update-ref and the rest) still run the hooks, `reference-transaction` included, which fires on every local ref update. They run without the GitHub token variables and the `.env` keys, so those hooks see no secret.
  - The switches turn off hooks only. A credential helper, a filter (`.gitattributes` with its command in the configuration) or an fsmonitor that the repository's configuration names still runs during a remote command; the credential helper with the GitHub tokens. A hook the configuration defines only once the command runs (a `clone`'s template configuration, a file a `pull` checks out that an `include.path` names) is switched off on git 2.55 by its event, not on git 2.54, where only the names listed beforehand are; Bureau's stages run no `pull` and no `clone`.
  - Branch code that can write the repository's `.git/config` (a hook during one of Bureau's tokenless local commands, the agent, a test, all as the same user) can name a command there that Bureau's next push or fetch runs with the GitHub tokens: `remote.<name>.receivepack` or `remote.<name>.uploadpack`, `credential.helper`, `core.sshCommand`, `gpg.program` together with `push.gpgSign`, or an `ext::` remote URL together with `protocol.ext.allow`. These are not hooks, so the switches leave them alone; this is the same-user limitation below. The same holds for the hooks directory under `"operator"`: such code can also write a script into `.git/hooks`, which the next push or fetch then runs with the tokens; `"operator"` keeps out the hooks a commit supplies, not code that already runs as the operator's user. A hook the configuration defines under a name that is also an event name (`hook.pre-push.command`) makes the per-name switch an event switch on git 2.55, so the operator's hook for that event does not run either.
  - `gh` keeps the tokens it logs in with and runs git itself (to find the repository; `gh pr create` can push a branch that is not on the remote yet). The hooks of those git processes run with the tokens; Bureau pushes before it calls `gh pr create`.
- **Environments of other processes.** A process's environment as it was started can be read by the same user: on Linux through `/proc/<pid>/environ`; on macOS through `ps -E`, checked on macOS 26 for Homebrew's `python3` and for `node`, while `/bin/bash`, `/bin/zsh`, `/bin/sleep` and `/usr/bin/jq` showed nothing. Since v3.2 neither the ancestors of branch code (the runtime wrapper, the stage and worker shells it relaunches, the provider) nor the processes a stage or driver starts hold the `.env` keys, with one exception: a key that the shell which starts Bureau exported itself. The driver started from that shell (the queue loop, the shepherd) holds it in the environment it started with. When `.env` defines the key too, Bureau keeps it from everything the driver starts. A key that only the operator's shell sets, and `.env` does not define, Bureau leaves as it is — it does not change values from the operator's shell — so it reaches every process below that shell, Bureau's own children included. Keeping the keys only in `.env`, and out of the shell environment, closes this. The GitHub token variables from the operator's shell stay in the runtime, the stage shells and the processes they start (other than branch code, the agent and its provider), because the stages' `gh` calls use them; a branch process left running in the background (a test that starts a server) can read them on Linux, and on macOS where the executable is not an Apple platform binary (a Homebrew `gh` or `python3`).
- **Everything else in the default environment.** The default removes only the Bureau-owned secrets and the GitHub token variables. An SSH agent (`SSH_AUTH_SOCK`), cloud credentials and registry tokens from the operator's environment stay; `repo.untrusted_env: "clean"` drops them.
- **Short secrets inside other values.** A secret shorter than 6 characters is removed only from a variable whose whole value it is, not where it is embedded in another value; real Bureau secrets are far longer (a Linear API key has about 48 characters, a Telegram bot token about 46, a chat id usually 9 digits or more).
- **The agent's own login.** `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` or `OPENAI_API_KEY`, when the agent logs in through them, reach what the agent runs: the agent cannot run without its login.
- **Relative PATH entries.** `python3`, `git`, `jq`, `gh` and `curl` are found through PATH; a relative entry such as `node_modules/.bin` in the operator's PATH would let the branch put its own program there. Keep PATH free of relative entries on a Bureau host.

Not a path: the dependency restore after a worktree reset runs `npm ci --ignore-scripts` on copies of `package.json` and `package-lock.json` only, so no code from the branch runs there.

Closing the remaining paths needs isolation at the operating-system level — a separate Unix user, a container or a virtual machine for the stages — which Bureau does not provide. Where the branch may come from someone who could not already read the operator's files, run the stages in such an isolated account.

## What to expect

Bureau is a solo-maintained project. Response times are best-effort. If a vulnerability is confirmed and material, the fix will be prioritized above whatever feature work is in flight.

For questions about this policy, use the email above.
