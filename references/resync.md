# Resync

Resolve `BUREAU_INIT_ROOT` from the loaded skill, and use the target git root as `--repo`. Targets default to those recorded in `.bureau-install.json`; older installations default to Claude unless the user selects `--target codex|both`.

| Flag | Helper arguments |
|---|---|
| `--resync-interfaces` | `assets --scope interfaces` |
| `--resync-scripts` | `assets --scope scripts` |
| `--resync-workflows` | `assets --scope workflows` |
| `--resync-ci` | `assets --scope ci` |
| `--resync-speckit` | `speckit` |

Update the source skill before asking it to resync an older installation, and refresh host skill discovery. Updating the clone does not update adopting repositories. For a legacy upgrade or customization conflicts, follow the [upgrade guide](../docs/migration.md); check [release notes](../CHANGELOG.md) for required scopes and remaining limitations.

When multiple asset flags are requested, combine their scopes into one helper preview/apply batch. For example, `/bureau-init --resync-interfaces --resync-scripts --target both` maps to `assets --target both --scope interfaces --scope scripts`. Spec Kit is a separate operation; CI and workflows are included only when requested. Pause dispatch and preserve active/unfinished work before changing scripts.

Example: `python3 "$BUREAU_INIT_ROOT/scripts/bureau_install.py" assets --repo "$PWD" --scope scripts`.

Preview first, read changed files and then repeat with `--apply` for authorized changes. Compare each conflict with its source under the installed skill. Unchanged files are adopted without a prompt; previously installed unmodified files can update automatically. Customized files or files from an installation without hashes report conflicts. To replace one after review, append `--overwrite scripts/FILE.sh` (repeat for multiple paths). If one conflict remains, the entire asset batch writes nothing. To retain custom behavior while installing a complete batch, first back up conflicting originals privately and review the intended merge. Apply the coherent upstream batch with each authorized replacement named, then selectively reapply the reviewed custom changes before resuming dispatch. Those files will intentionally conflict on the next preview; report that drift instead of editing the manifest to hide it. If a resolution is deferred, leave the batch unapplied. The helper has no skip-conflicts or automatic three-way merge mode. Never set blanket overwrite flags.

Instruction files manage only `<!-- bureau-init:begin -->` through `<!-- bureau-init:end -->`. Text outside the block is preserved. For the old `<!-- bureau-init managed -->` format and its variants (`<!-- bureau-init managed: regenerate via … -->`, closed by `<!-- end bureau-init managed -->`), first identify the exact generated section and delimit it with the new markers in place of the old ones, without including user guidance; review it before adoption. The helper refuses the file while a legacy marker sits outside the new block. Do not replace the whole file to resolve a block conflict.

Spec Kit resync uses the pinned CLI (1.2.2; install with `uv tool install specify-cli==1.2.2`). Before upgrading, back up `.specify/templates`, `.specify/scripts` and extension skills under `.claude/skills/speckit-*` and `.agents/skills/speckit-*`, along with the integration assets covered by the [upgrade guide](../docs/migration.md#before-changing-an-adopting-repository).

First run the read-only `specify integration status`: it lists the installed hosts and the modified, missing and unchecked managed files, including modified helpers on a 0.7.5 install. **Do not run `specify integration upgrade` while any `.specify/scripts/**` helper is reported modified, even with `--force`.** The upgrade can keep a modified shared helper while advancing the shared manifest to 1.2.2, leaving incompatible old and new helpers together. Back up and resolve those edits first: rebase onto the pristine 1.2.2 helpers or remove the modified helpers so they can be replaced. Do not treat the shared version number as compatibility evidence.

After resolving helpers, run `specify integration upgrade <integration>` for each installed integration (`claude` and/or `codex`). With 0 modified files it needs no `--force`; modified host skills may block it, so review those changes and authorize their overwrite before using `--force`. Then run `specify extension update`. An extension update reinstalls extension sources and registered commands and keeps configuration, not arbitrary edits; review and reapply customized extension skills from the backup. Run `status` again and inspect any modified or missing files before running Bureau's doctor; an unmodified upgrade should report 0 modified and 0 missing files. These update commands never touch `.specify/memory/constitution.md`. Keep the previous active integration unless a switch is explicitly requested.

If the manifest-aware upgrade cannot be used, initialize the first host with `specify init --here --integration <first> --force --non-interactive --ignore-agent-tools`, add every further host with `specify integration install <host>`, then select the active host with `specify integration use <active>`. Process non-active hosts first and the active host last. Repeating `init` forgets previous host registrations. Forced initialization can overwrite customizations, so back them up first and review any restoration. Never change the constitution.

Bureau's `speckit` helper uses this lifecycle with drift snapshots to restore customized skills/templates, always including `recovered_files` entries even when their recorded hashes match. Preview also requires the pinned CLI and renders pristine 1.2.2 helpers in a temporary directory. Before any Spec Kit call that writes the adopting repository, it compares every existing `.specify/scripts/**` file by content: pristine 1.2.2 bytes are safe, and an unmodified managed file matching its existing shared-manifest hash can be replaced. Recovered helpers count as customized regardless of hash. All other customized helpers are named and refused, even if the shared manifest already says 1.2.2. Back them up and rebase onto the 1.2.2 helpers or remove them before retrying. `--overwrite` applies to Bureau asset scopes and does not bypass this check. Extra helpers absent from the pinned set are listed as preserved in preview; they cause a refusal only if a pinned helper sources them. Legacy Markdown templates remain preserved; the checked 0.7.5 plan/tasks templates still copy and resolve through the 1.2.2 helpers. Review other project-specific template edits separately. See the [acceptance record](../docs/codex-acceptance.md#spec-kit-installer-evidence) for the operator's 2026-10-21 live verification of the pristine render/content guard, including refusal after manual manifest advancement; recovered-file handling and the complete pipeline remain outside live qualification.

The helper refreshes all discovered installed integrations and keeps the previous active one unless `--active-integration` requests a switch. It verifies both host registrations and the active default after apply. Existing constitution bytes are restored even if initialization fails. On failure, active metadata is restored but partial new assets may remain: inspect before retrying. Do not silently reinstall a different CLI version.

Bureau's Spec Kit apply always attempts to repair execute permission on every safe, regular `.sh` under `.specify/scripts/` after CLI writes and drift restoration, including newly created helpers and partial failures, using `(mode & 0o777) | 0o111` without changing content. Each restore and helper repair is independent: cleanup errors are reported separately on stderr, preserve the primary failure, and make an otherwise successful apply exit non-zero. Mode repair is attempted even if a restore fails. Run `/bureau-init --resync-speckit` after a direct CLI upgrade or forced init to apply the repair; mode-only drift does not count as customization, and doctor warns with each non-executable helper's path.

Preview's `existing_helper_mode_drift` (renamed from `helper_mode_fixes`) lists only existing regular `.sh` helpers under `.specify/scripts/` that lack one or more execute bits before apply. It does not predict helpers that init will create or executable helpers whose modes init will reset. An empty list still leads to mode repair during apply.

When Codex is selected and the Git extension is already installed, resync also renders its native Codex skills in a temporary directory using the pinned CLI. It installs only missing skills and merges Codex command registrations after the files exist. Existing skills, hook settings, extension configuration, metadata and other host registrations are preserved. Preview reports this separate registration step; a renderer failure occurs before core initialization. This repairs legacy installations whose core resync alone omitted mandatory Git hooks.

Resolve the exact approved spec directory before using existing-feature helpers on every branch, including numeric feature branches, `codex/*` and detached checkouts. Always pass both `SPECIFY_FEATURE=NNN-approved-feature` and `SPECIFY_FEATURE_DIRECTORY=specs/NNN-approved-feature` to each invocation, using the real configured path. Fresh worktrees lack the ignored `feature.json`, and 1.2.2 no longer derives the directory from the Git branch. `SPECIFY_FEATURE` alone does not supply the directory and can leave a stale pointer in control. Do not infer a feature from a duplicate numeric prefix or rename an issue branch to satisfy a helper.

CI is opt-in and remains on `runs-on: ubuntu-latest`; preserve an existing workflow unless replacement is authorized. Do not switch public fork PR workflows to self-hosted runners (fork-PR-RCE).

Resync does not modify `.bureau.json` or `.env`, and each scope excludes unrelated assets. Re-run the preview to verify the final state and report retained local differences.
