# Background supervision from the app

Use `$bureau` for work in the current task. Use these commands only when the user wants to supervise the independent background pipeline. Background runs use the CLI provider configured in `.bureau.json`, which can differ from the model selected in the app.

- Inspect ownership and compact run records: `python3 scripts/bureau-runtime.py status`.
- Pause new dispatch across this repository's worktrees: `python3 scripts/bureau-runtime.py pause`. Existing work is allowed to finish; this is not process cancellation. Resume dispatch with `unpause`.
- Run at most one eligible stage: `bash scripts/bureau-tick.sh --no-merge`. Optionally restrict with `--stage implement`. It uses a claimed worker per issue and stage, not this app checkout. Preserved unfinished work on one issue does not occupy another issue’s worker. `--allow-merge` requires the user's merge authorization and still uses all existing merge gates.
- Inspect `logs/bureau-tick.json`. Outcomes distinguish waiting, advanced, completed (actual Done), stopped_for_review, paused, blocked and failed. A successful stage with unchanged state is waiting only when the fresh ticket has no human-attention label. A newly parked ticket is blocked (exit 25), including stages that themselves return zero. Exit 20 is the review boundary, 25 needs human attention, 26 a cancelled ticket. Quota waits return process success with result exit_code 23; they do not sleep through the next scheduling interval.
- Approved reviews stopped before merge are remembered in the shared Git directory. Later ticks skip the unchanged PR head, base and ticket inputs and can select another review or a lower stage. `skipped_reviews` lists these skips in the tick result. The stage rechecks the boundary under its issue claim to handle concurrent picks without repeating model calls. If validation created an unpublished local merge, the completed clean review checkout is retained at that HEAD and detached from its own branch; a resumed review uses a fresh checkout. Dirty or failed workers keep their existing protection and may require reconciliation.
- Inspect these boundaries with `python3 scripts/bureau-supervision.py status`. New PR/base commits, a changed title/description/material labels, or an observed PR closure invalidates the old boundary. To request another review at the same head (for example after a new review comment), run `python3 scripts/bureau-supervision.py resume TEAM-123`, then run the next tick. Resume only clears the local review boundary; it does not change Linear, start work, or authorize merging. An explicitly authorized `--allow-merge` tick follows the regular review and merge gates.
- Compare outcomes with `python3 scripts/bureau-monitor.py logs/bureau-tick.json --previous logs/bureau-monitor.previous.json`. Notify only when `notify` is true; unchanged outcomes stay quiet. Use one monitor per result file.

When the user explicitly requests recurring supervision, use the app's available automation tool and its current schema, preferring a heartbeat in this task. The prompt should run one bounded tick, compare the result, and notify only on a meaningful change, completion, failure or required user action. Preserve the requested cadence and merge boundary. Do not invent scheduler config or install a second cron daemon. Local execution requires the computer and app to be available; do not promise unattended execution while offline.

For scheduling several tickets, predict repository-relative changed paths in the current task and save `{ "tickets": [{"ticket":"TEAM-1","title":"..."}], "predictions": [{"ticket":"TEAM-1","predicted_paths":["src/file.py"]}] }`. Run `node scripts/bureau-schedule-cli.mjs input.json > schedule.json`, then inspect the output. Missing, invalid or failed predictions are visible in `blocked`; resolve them before executing `bash scripts/orchestrate.sh --execute --schedule schedule.json --no-merge`. The partition algorithm is shared with the installed Claude workflow. Predictions are advisory; repository ownership and Git checks still apply at execution time.

Provider evidence lives under `logs/provider-runs/` with invocation stage, model, run ID, issue, outcome, duration and available token usage. `estimated_cost_usd` is a CLI estimate when supplied; actual billed cost and account usage are unavailable (`null`), not zero. The app's account usage tool is separate from per-run evidence. Codex throttling reads `BUREAU_CODEX_USAGE_FILE` or a `BUREAU_USAGE_FILE` explicitly tagged `"provider":"codex"`; it never reads ClaudeWatch. Without an appropriate signal, dispatch proceeds and a provider quota failure is recorded as exit 23.
