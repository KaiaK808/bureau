# Shared Bureau stage protocol

Use the configured issue, state UUIDs, specs directory and branch. Read project instructions (AGENTS.md and CLAUDE.md), the constitution, SPEC.md and relevant prior review feedback before working. LESSONS.md is advisory; do not overwrite it while running a stage.

For app work use `bureau-runtime.py prepare ISSUE STAGE`, perform the stage in the current task, and supply a result to `finish RUN --result FILE`. The prepare response identifies the run, entry state, workspace, HEAD and context. It claims the issue and checkout until finish or explicit release. Do not call a background pipeline from an app checkout. Resume existing work without reset/clean; if the canonical issue branch is held elsewhere, report that owner and use an explicit handoff.

- `spec`: use the installed Spec Kit specify, plan and tasks skills. Read the issue and comments; preserve the constitution. Produce spec.md, plan.md and tasks.md on an issue branch. Stop before implementation.
- `spec_review`: review spec/plan/tasks against actual code and project constraints. Repair spec artifacts within scope. Route UI work through configured Design/Copy stages when needed; do not begin implementation.
- `ux` / `copy`: produce design artifacts or requested copy changes using project conventions and the configured voice guide. Keep changes scoped to the stage.
- `implement`: execute the accepted tasks in dependency order. Preserve stable task IDs, prior completed work and human decisions. Run relevant tests and record actual results. Commit with the issue identifier and `Bureau-Generated: true` trailer. Open/update a draft PR for partial work, ready PR for complete tested work. Do not merge.
- `qa`: independently run the test suite, add missing tests within scope, and report implementation defects as blocked. Do not silently alter product behavior to make a test pass.
- `code_review`: review correctness, security and performance against the spec and current diff. Report concrete findings. Return APPROVE, REQUEST_CHANGES or BLOCK. Review applies only to the HEAD captured by prepare. Do not commit fixes during this stage.

Result contract (JSON object): `run_id`, `stage`, `head` (current Git HEAD), `outcome` (`complete`, `partial`, `blocked`), `summary`, `artifacts` (existing repository-relative files), and `tests` (objects with `command`, integer `exit_code`). Code review also requires `verdict`. Spec completion requires all three spec artifacts; implementation/QA completion requires successful test evidence. Evidence must describe checks actually run. Missing prerequisites or permission failures are blockers, not product defects.

`finish` validates identity, ownership, HEAD and unchanged entry state before posting a canonical `<!-- bureau-branch: BRANCH -->` comment and moving to a configured state. Repeating the same result is idempotent; a changed result or externally changed state is rejected. Partial/blocked results retain state and progress. Blocked outcomes and BLOCK reviews apply the configured needs-human label before releasing ownership, preventing background queue picks. Resolve the blocker and explicitly remove that label before resuming background work. Results are retained in the shared Git directory for resume. Default review completion stops before merge. `--allow-merge` authorizes a handoff to the Merge queue; actual merging still requires the existing complete merge gate. No merge state means no automatic merge through the app protocol.

Local locks coordinate worktrees on one machine. They do not provide distributed Linear locking or a transactional state compare-and-swap across machines. Do not run the same issue simultaneously on another host. `status` is read-only. Inspect a stale owner's run before `release RUN`; a live background owner or recorded process group must be stopped first. Interrupted background runs retain ownership and revoke disposable registration so a surviving child cannot race a reset. After inspecting processes and preserved work, release explicitly; recover in the unregistered checkout or retire it explicitly before worker reuse. App leases do not expire silently.
